# Aphel

Aphel is an open source platform for composing business systems from plugins. The core knows no business domain; a blueprint (`blueprints/<key>`) chooses the plugins, configuration and navigation of a system, and a blank system is possible. Today's product is the `crm` blueprint and its variants (freelancer, agency, real estate, consultancy, SaaS, B2B sales); fields, workflow, automations and plugins adapt each installation without changing the code.
It runs as a single Rust binary with the React frontend embedded; each company (the "organization") has its own database, and one process serves either one company (`DATABASE_URL`) or many (`CONTROL_DATABASE_URL`, multi-tenancy). What goes into the binary is chosen in `back/aphel.modules.toml`.

## Platform rules

Aphel is a system composition platform: the CRM is one blueprint among others.

- A blank core is the baseline: no plugin is required and only the kernel is always on.
- WebAssembly plugins may declare `managed` entities, with real columns and indexes generated by the host from the definition, never plugin SQL; unique indexes cover only records that are not deleted (generated column `_live`), so trashing a record frees its values.
- Capability modules carry generic names: `workflow`, `tasks`, `assignment`.
- Governing rules: plugins depend on contracts, never on each other; the core knows no domain; each table has one owner; no foreign keys or SQL across plugins.
- **Core points:** the kernel never reads a plugin's table. Plugins contribute `FileReferenceSource` (what generated a file), `HealthSource` (recent failures for the system screen), `DigestSource` (owned by `notifications`, tasks due for its digest) with `app.contribute::<dyn ..>`; core traits are re-exported by `aphel_sdk::points`; capability traits are imported from their owner. Domain permission and `RecordType` constants live in the contract crate `back/contracts/crm` (`CrmPermissions`, `CrmRecordTypes` traits and the CRM field helpers).
- **Open vocabulary:** `FieldTypeDefinition` contributions register custom field keys over native storage, validators, configuration schemas and supported operators. `Actor::Service { kind, id }`, `EventCausation::executor_kind` / `executor_id` and `AccessScope::acting_as(kind, id)` identify service work. Entity support is an open JSON trait map (`EntityTraits`, `EntityDefinition::with_trait`, `registry.with_trait`). `ReferenceProvider` contributes existence and stable-key resolution by `ReferenceKind`; config keys and apply contexts use the same kind. Definition labels use `LocalizedLabels` and each owner keeps its translations in `locales/labels.json`; `label` remains the default text projection. The platform catalog exposes field types and reference kinds.
- **Entity engine:** `EntityDefinition` unifies native, runtime and administrator entities. `EntityStorage` selects native `table`, host-generated `managed` columns/indexes or EAV `dynamic` storage; `EntityDeclaration` is the shared declarative contract. Keys use `<plugin>.<entity>` and administrator objects use `custom.<key>`. Generic routes are `/api/v1/entities/{entity}/records`; native writes explicitly opt in. `people` uses `GenericRecordHandler` with `EntityWriteBehavior` for its normalization, duplicates and company links. Soft references target an entity or trait, with transactional `restrict`, `clear`, `cascade` policies and validation on writes/restoration. `RecordTypeExtension::side_table` gives each extender its own nullable columns and automatic joins; `leads` and `lead_pro` no longer alter foreign tables. Generate DDL with `aphel entity-schema --key <plugin>.<entity> <declaration.json>`; the managed example and its generated SQL live in `docs/plugins/examples`.
- **Capability extraction:** `cargo check -p aphel --no-default-features` compiles the production binary with only the kernel. Default builds enable the generated `plugins` Cargo feature. Schemas belong to their owners; profiles and templates live under `blueprints/`.
- **Schema policy:** there is no production installation or existing data to preserve. Rewrite schemas for fresh installations. Do not add migration adoption, legacy identity aliases, old-checksum exceptions or compatibility transports. Keep normal schema creation/migration bookkeeping.
- **SDK door:** plugins import kernel modules only through `aphel_sdk::platform::*` and reach the runtime through `aphel_sdk::Runtime` (`ctx.runtime()`, `env.runtime()`, `aphel_sdk::runtime()`); peers' record keys come from `aphel_contract_crm::keys`. The arch check fails on `aphel_kernel::<a>::<b>` paths, `ctx.state()` / `runtime_state()` / `env.state()` and foreign dotted record keys in plugin code.
- **Blueprints:** `blueprints/<key>/blueprint.toml` (crate `aphel-blueprint`, `back/blueprint`: `extends`, `plugins.required|recommended|exclude`, `navigation`, `[[roles]]`, `configuration.packages`);  `required` is a blueprint property, no plugin is required and only the kernel is always on. The installer reads blueprints (`InstallerBlueprintSource`), enables the chosen blueprint's required plugins, applies its configuration packages after install (`BlueprintConfigurator`, implemented by `config_packages`; `crm` ships the default pipeline and lost reasons) and stores the choice in `organization_settings.settings.installer`; `GET /api/v1/blueprint` returns it and the shell home redirects to the blueprint home or shows a blank page. `DefaultsSeed` runs only for enabled modules. A plugin that provides a contract a built-in module declares holds that module. Guide: [`docs/blueprints`](docs/blueprints/README.md).
- **Module notes:** how individual modules and domains are built is in [`docs/architecture/module-notes.md`](docs/architecture/module-notes.md); `CLAUDE.md` keeps the platform rules.
- **Architecture ratchet:** `cargo run -p xtask -- arch check` (part of `make lint`) compares counts against `back/xtask/arch-baseline.json` and fails if any rises. When a count falls, run `cargo run -p xtask -- arch baseline` and commit the lower baseline. The accounting rules are in `docs/architecture/platform-capabilities.md`. Use `--details` to list the findings.

## Code rules

- All code, documentation (`.md`), commit messages, API descriptions and JSON schemas in English. UI texts always via i18n, in both pt-BR and en.
- No explanatory comments in the code, and no docstrings. Only `TODO`/`FIXME` and directives required by tools.
- Follow the layering pattern from [`back/README.md`](back/README.md).

## Backend

- **Kernel × plugins:** the kernel owns the host, HTTP/security, identity/access, entity/query/pipeline engine, reliability, resources, installer and generic settings. Optional capabilities live in `back/modules/<key>` and register routes, workers, hooks and typed contributions. Dashboard contracts/adapters belong to `dashboard`; notifications/push and their catalog projection belong to `notifications`; the automation contract is `aphel-contract-automation`. Configuration package sections and fragment layouts are owner contributions. The object engine and dynamic record APIs stay in the kernel; object/relationship administration belongs to `objects`. See [`docs/architecture/platform-capabilities.md`](docs/architecture/platform-capabilities.md).
- **One company per database:** code always works on one company. There is no `organization_id`, no `organizations` table and no organization switching. The company data (name, logo, color, locale, time zone, currency, `settings`, `custom_schema_version`, 2FA policy, `installed_at`) lives in `organization_settings` (single row, `id = 1`; read through `OrganizationRepository::find()`). Single-configuration tables use the same pattern (`id TINYINT = 1`, `INSERT .. ON DUPLICATE KEY UPDATE`). The company and the first admin are only created by the installer (`/api/v1/installer`, with optional backup restore at `/api/v1/installer/restore`); the other users join by invitation. Member = user (`users.role_id`, `users.status` = `invited`/`active`/`deactivated`).
- The access scope is the `AccessScope` (`kernel/domain/access/access_scope.rs`: user, role, expanded teams, permissions, `api_token`, `automation_id`, enabled extensions), with no organization. Repositories and use cases that read business data receive `&AccessScope`; jobs and consumers without an actor use `AccessScope::system()` (all permissions) and, when the actor matters, build the scope with `build_access_scope` (`kernel/application/access`).
- **Authorization: explicit call in the use case.** The handler extracts `AuthContext` (single extractor: rejects invited or deactivated users and sessions pending 2FA) and passes `&tenant.scope` to the use case, which calls `scope.require(&Permission::X)?` or `scope.record_filter(&Permission::X)?` (trait `Authorizer` in `kernel/application/access`). There is no `Require<P>` extractor. New permissions become constants in `kernel/domain/access/permission.rs` and enter the catalog through the module's `app.permission(PermissionDefinition::record|administrative(..))` (the core ones in `builtin_permission_catalog()`, registered by the `kernel` module); `permission_catalog()` reads the `App`. Operations routes (`/api/v1/system/*`: health, jobs, updates, system audit) require `system.manage` (granted to the admin role); there is no platform administration.
- Non-GET requests require the `X-Requested-With: aphel` header (the web client already sends it), except with `Authorization: Bearer` and on public routes (`/api/v1/public/*` and `/api/v1/hooks/*`, via `csrf::is_public_path`). Session in the `aphel_session` cookie; API tokens `aphel_<prefix>_<secret>` go through the same `AuthContext` with permissions = scopes ∩ the creator's current permissions and actor `Actor::ApiToken` (via `Actor::from_scope`). Session/account routes use `SessionContext` (rejects tokens).
- **API style guide:** [`docs/api/style-guide.md`](docs/api/style-guide.md) (item `{ data }`, list `{ data, meta }`, `filter[field][op]` via `RecordListQuery`, `include=` via `IncludeQuery`, `If-Match` via `IfMatch` + `ensure_version` → 409 `version_conflict`, rechecked inside the transaction with `aphel_kernel::records::lock_version` (row locked with `FOR UPDATE`), codes in [`docs/api/errors.md`](docs/api/errors.md)).
- Every route has a `utoipa` annotation and appears in `/api/openapi.json`.
- Every error goes through `AppError` and comes out in the envelope `{ "error": { "code", "message", "details" } }`.
- Listings respond with `Page<T>` = `{ data, meta: { total, page, per_page } }` and items with `Data<T>` = `{ data }`, using the pagination extractor.
- Migrations: platform ones live in `back/kernel/migrations` (kernel, `sqlx::migrate!`); module ones live in `back/modules/<key>/migrations`, numbered within the module and declared in the `Manifest` (`Migration::new(n, desc, include_str!(..))`), applied by `module_migrations` in load order. A module declares `depends_on`/`optional` for every module whose tables it references by FK (the load order comes from the dependencies).
- **Every business mutation publishes a domain event and writes an audit entry in the same transaction.** The use case's port bundle has `type Transactions: TransactionManager`, `type Events: EventPublisher<Tx>` and `type Audit: AuditLog<Tx>` (contracts in `kernel/application/shared`); the write repository receives `&mut Tx`. The use case does `begin` → write → `events().publish(&mut tx, DomainEvent::new(..))` → `audit().record(&mut tx, AuditEntry::new(..))` → `commit`. Reference: `change_member_role` in `kernel/application/organization_admin/members.rs`. Audit diffs with `application::audit::diff_changes` (sensitive fields become `"[redacted]"`). In MySQL the `Tx` is `MySqlTx` and the adapters come from the `AppState` (`state.events`, `state.audit`, `state.jobs`, `state.storage`). In modules following the new pattern the same flow uses `ctx.begin()` → store → `publish_mutation(ctx.events(), ctx.audit(), &mut tx, ..)` → `tx.commit()` (reference: `modules/people/service.rs`).
- **Module kernel:** everything is a module (`trait Module` in `back/kernel/src/modules`: `manifest()` + `register(&mut AppBuilder)` + `on_enable`/`on_disable`/`uninstall`). The `AppBuilder` is the only contribution point (`routes`/`public_routes`/`root_routes`, `on(hook, ..)`/`filter(hook, ..)` on the `HookBus`, `provide`/`decorate` in `Services`, `permission(..).grant_to([..])` (or `grant_organization_wide_to` for organization scope in all roles), `public_event`, `notification_kind`, `openapi_tag`, `widget`, automation `trigger`/`action`, `job`/`consumer`/`schedule`/`worker`); each contribution stores the module key and is ignored when the module is disabled (`EnabledModules` cache), including contributed system fields (`SystemField::is_available`, inactive in the `FieldSet`) and services/decorators (`Services::get` skips layers from disabled modules). `build()` sorts by dependencies (then alphabetically) and freezes into the `App`, which the binary installs with `aphel_kernel::modules::install_app` before the CLI and everyone reads with `aphel_kernel::modules::app()` (`state.app`); the router and `WorkerRuntime::from_app` come from it. The compiled list is `compiled()` in `back/app/src/modules.rs`, generated from `aphel.modules.toml` (`KernelModule` + the modules; `required = true` in the file becomes `AppBuilder::require`). Enablement in `installed_modules` (`module_key`), module migrations in `module_migrations`; `required` modules cannot be disabled. `permission_catalog()`, `NotificationKind` and `PublicResource` are open catalogs read from the `App`. CLI `aphel modules list|doctor|hooks [--markdown]|uninstall <key> [--purge]` (`--purge` exports, drops the `<key>_*` tables and those in `owned_tables`, runs `Manifest::uninstall_sql` and forgets the module's migrations). Hooks enter the catalog with `app.declare_hook(H, &[HookUsage::..], description)` ([`docs/modules/hooks.md`](docs/modules/hooks.md), generated).
- **Module crates:** each module is a crate that depends on `aphel-kernel` (paths `aphel_kernel::…`) and, with an alias equal to the key, on the modules it uses (`leads = { package = "aphel-mod-leads", path = "../leads" }`, used as `leads::LeadQualifying`). Cycles between crates are forbidden: the kernel knows no module, and two modules that need each other talk through a hook, a service or a typed contribution (e.g. `timeline::domain::TimelineEventExtension` contributed by `email`; automation operations `StageOperations`/`NoteOperations`/`ActivityTypeOperations`/`TaskOperations`/`IncomingWebhookOperations` provided by their owners; `ConfigSectionFactory` for package sections; `DefaultsSeed`; `TimeTriggerPlanner`; `ModuleCommand` for CLI subcommands such as `aphel demo`/`aphel org`; hook `SearchPlanFilter` to restrict search). A third-party module follows the guide [`docs/modules/README.md`](docs/modules/README.md) and the example `back/plugins/lead_pro`.
- **Record pipeline:** every record write goes through the `RecordPipeline` port (`fields().pipeline()`, implementation `MySqlRecordPipeline` in `kernel/records`): authorization in the use case → `saving` (hook `RecordSaving`, filter of `values`/`custom_fields`) → `CustomFieldWriter` + write → `validate` (`RecordValidating`, veto) → `saved` (`RecordSaved`) → event + audit → commit → `committed` (`RecordCommitted`); deletions call `deleting`/`deleted` (`RecordDeleting` blocks `restrict`). Queries apply `RecordQueryFilter` (only adds AND conditions) in the executor; `redacted`/`redacted_items` apply `RecordSerializing` before the `record_redactor`; the field schema goes through `RecordSchemaFilter`. Each type has a `RecordTypeHandler` (`create`/`update`/`delete`/`load`/`archive`/`restore` over JSON; core in `kernel/api/records.rs`, custom objects via a factory) used by automations, import and bulk actions via `registry.handler(type)`; no `match record_type { "contact" => .. }`: what applies only to some types is a capability in `EntityDefinition.capabilities`. Types enter via `app.entity(def)` and are extended via `app.extend(key, |t| ..)` (system fields, relations, `member_access`, `managed_field(FieldSpec)` synced at boot with `module_key`, locked with 409 `field_managed_by_module`). `AppState` lives in `kernel/state.rs`. Guide: [`docs/architecture/record-pipeline.md`](docs/architecture/record-pipeline.md).
- **Background jobs:** implement `JobHandler` (`kind()` + `handle(ctx, payload)`) and register it in the module's `register` with `app.job(|env| ..)` or `app.worker(|env| WorkerParts::default().handler(..))` (the platform ones are in `back/kernel/src/kernel_module.rs`); recurring schedules with `app.schedule(ScheduledJobDefinition::new(kind, cron_with_seconds)?)`. Enqueue with `JobQueue::enqueue(&mut tx, Job::new(kind, payload))` inside the transaction (or `enqueue_now`). Handlers must be idempotent.
- **Event consumers:** implement `EventConsumer` (stable and unique `name()`, `accepts(event_type)`, `consume(&event)`) and register it with `app.consumer(|env| ..)` in the module. The `outbox.dispatch` job creates one `event.consume` job per consumer (at-least-once delivery, with retries isolated per consumer).
- **Record listings only via `RecordQuery`; custom field writes only via `CustomFieldWriter`.** Every record type declares itself in the `RecordTypeRegistry` (`kernel/application/fields/registry.rs`: table, owner column, `deleted_at`/`archived_at`, read permission, system fields); listing/filtering/sorting/searching go through `RecordQueryEngine` (filter as an AST validated against the field registry, never SQL built from user text); values are read with `CustomFieldReader`. System fields are seeded when the organization is created and at boot (`sync_system_fields`). Guide: [`docs/architecture/custom-fields.md`](docs/architecture/custom-fields.md).
- **Dashboard widgets:** implement `WidgetProvider` (`modules/dashboard/src/engine`) and register it with `app.contribute::<dyn dashboard::engine::WidgetProvider<dashboard::repository::MySqlDashboardPorts>>(Arc::new(..))` (`WidgetRegistry::builtin()` reads the widgets of enabled modules; on the web, the module's `app.widget`); aggregations build the `QueryPlan` with `resolve_query` (read scope) and reuse `build_query(Count)`.
- **Notifications:** new notices enter as a `NotificationKindDefinition` (channels and defaults) contributed via `app.contribute(Arc::new(..))` (`builtin_notification_kinds()` lives in `modules/notifications/src/domain/kind.rs`) and are generated by the `notifications.events` consumer from domain events (never notify the actor; email always through the `notification.email` job). Long-running user processes finish by publishing an event with `Actor::System` and `requested_by` in the payload (pattern of `export.*`/`import.*`).
- **Configuration packages:** every portable organization configuration is a `ConfigSection<Tx>` section (`modules/config_packages/src/application`: `export`, `validate`, `plan`, `apply`, plan and apply sharing the same reconciliation) registered by the owner through `ConfigSectionFactory` (`modules/config_packages/src/infrastructure/ports.rs`) and described in `docs/config-packages/schema.json`. References always by stable key, never by id; installing never deletes anything nor touches business records. Guide: [`docs/config-packages/README.md`](docs/config-packages/README.md).
- **Secrets** (passwords, signing secrets, integration keys) only via `SecretVault` (`state.secrets`/`WorkerRuntime::secrets()`, `SecretKey { owner_type, owner_id, name }`; company secrets with `SecretKey::organization(name)`, encrypted with `APP_ENCRYPTION_KEY`); they never come back through the API (only "configured"), logs or audit. Events exposed to integrations enter the open catalog via `app.public_event(..)` (the core ones in `builtin_public_events()`, `kernel/application/public_events`; read via `public_event_catalog()`) and `docs/api/events.md`; the public body is built by `ApiPublicEventRenderer`. Integration providers implement `IntegrationProvider` and enter `IntegrationRegistry::builtin()`.
- **Organization configuration × `.env`:** the `.env` only holds infrastructure (`HTTP_*`, `DATABASE_URL` or `CONTROL_DATABASE_URL` with `CONSOLE_HOST`, `TENANT_DATABASE_MAX_CONNECTIONS`, `TENANT_EXPORT_DIR`, `APP_ENCRYPTION_KEY`, `RUN_MIGRATIONS`, `RUST_LOG`, `WORKER_*`, `SCHEDULER_INTERVAL_SECS`, `HEALTH_*`, `METRICS_TOKEN`, `UPGRADE_MIN_FREE_DISK_MB`, `WEBHOOKS_ALLOW_PRIVATE_NETWORKS`, `DEMO_*`; see [`docs/configuration.md`](docs/configuration.md)). Public address, upload limit, file storage (disk/S3), webhook delivery, API token limits and community catalog are organization configuration edited in the UI (`GET`/`PATCH /api/v1/organization/settings`, `settings.manage`; `OrganizationConfigCatalog` in `kernel/application/organization_profile/settings.rs`, `state.organization_config`), with the cache invalidated on write and reread the same way in `serve` and in the worker; every change publishes `organization.settings_updated` with audit (secrets `"[redacted]"`). SMTP is core organization configuration (`mail`, with `mail_password` stored in `SecretVault`), with `SMTP_*` environment fallback, resolved on every send by `state.mailer()` (`SmtpMailerProvider`); without SMTP sending fails with `mail_not_configured` without bringing anything down. Storage is resolved the same way (`DynamicFileStorage` behind `state.storage`). Email links always use the saved public address, never the request's `Host`.
- **Mounts and reserved paths:** Aphel's infrastructure lives under `/api` and `/_aphel` only (built assets `/_aphel/assets`, import map entries `/_aphel/shared`, `sw.js`, manifest, docs at `/_aphel/docs`, `/_aphel/health`, `/_aphel/health/ready`, `/_aphel/metrics`). The internal app is mounted at `organization_settings.mounts.app.base_path` (`/` or one segment such as `/app`, validated by `normalize_app_base_path`; changing it also needs `system.manage`) and always at `/_aphel/app` (`RECOVERY_APP_PATH`); `aphel mounts reset` puts it back at `/`. `web::dispatch` (the router fallback in `kernel/src/api/web.rs`) resolves the mount, strips the prefix and runs the app mount router: modules add routes relative to the app base with `app.app_routes(..)` (`RouteMount::App`, e.g. the plugin public apps `/p/{key}/`), and the rest falls back to `index.html` with `<meta name="aphel-base">`. Links to app screens come from `PublicBaseUrl::app_link`/`app_root` (`Ctx::app_root_url`), never from `get()`, which is the bare public address for API and webhook URLs. On the web, the router `basename` and `appBase`/`appPath`/`appUrl` (`web/src/sdk/app-base.ts`, exported by `@aphel/web-sdk`) read that meta; `window.location` URLs to app screens must go through `appPath`.
- **Public site:** the optional module `site` (`modules/site`) serves plugin pages at `organization_settings.mounts.site` (`base_path`, default `/s`, and optional `host`; on the same host the longer prefix wins and the app wins ties unless the site has a host). The kernel only knows the mount: `web::dispatch` hands site requests to the `dyn SiteRequestHandler` contribution (`aphel_kernel::modules::SiteRequestHandler`, `kernel/src/modules/site_mount.rs`). Content comes from `dyn SiteContentSource` contributions of the contract `aphel-contract-site` (`contracts/site`: `SiteBundle` with pages, public exposures and templates, `PathPattern`, `check_bundle`); `wasm_runtime` builds bundles from `[site]` in `plugin.toml` plus `site/*.html` in the package (`modules/wasm_runtime/src/site.rs`, validated on install: `plugin_site_invalid`, `site_route_conflict`). `site` renders MiniJinja templates (fuel limited, auto-escaped) inside its built-in theme (`modules/site/theme`), reading records with a system scope but always ANDing the exposure's `where` conditions and projecting only exposed fields (`modules/site/src/data.rs`). Pages are cached per process (`cache.rs`, tags `record:<type>:<id>`/`entity:<type>`/`*`); the `site.invalidate` consumer writes tags to `site_cache_invalidations` for events of exposed types, attachments and organization changes, and every process polls that table at most every 2 s. `images = true` exposes image attachments, served and resized (`image` crate, variants in `FileStorage` under `site/variants/`) at `/_aphel/site/files/<type>/<record>/<file>/<original|wN>` through `SiteRequestHandler::serve_reserved` (`images.rs`). SEO: pages declare `seo` (description/image expressions, `noindex`) and the theme writes canonical, description, Open Graph and Twitter tags from `page.seo`; `sitemap.rs` serves a cached `/sitemap.xml` and, at a host root, `robots.txt`; the module's config extension `site.indexing` turns everything to noindex; the consumer stores `site_redirects` when a `match` field changes and the handler answers 301 for unknown values (`redirects.rs`). Themes and menu: `[site.theme]` plugins replace `layout.html` and the error pages with `site/theme/*.html` and serve `site/theme/assets/*` at `/_aphel/site/themes/<owner>/` (`SiteContentSource::asset`); `[[site.menu]]` items reach templates as `site.menu`, ordered and hidden by `site.menu` in the module config; the organization logo is served at `/_aphel/site/logo`. Admin API `GET /site`, `GET|DELETE /site/redirects`, `POST /site/cache/purge` (`http.rs`); web module `web/src/modules/site` (Settings → Site) edits the site address, indexing, theme, tagline and menu. Dynamic parts: manifest routes with `site = true` (`RouteAudience::Site`) answer at `/_aphel/site/api/<plugin>/<path>` through `dyn SiteApiHandler` (installer scope, public rate limits, `X-Aphel-Site: 1` required on unsafe methods, `dynamic.rs`); pages may declare `data` (a GET site route whose JSON becomes `data`, cached 60 s); islands are `site/islands/<name>.js`, placed with `island(name, **props)` and started by `/_aphel/site/islands.js` with an import map (`react`, `react-dom/client`, `@aphel/ui`) allowed by hash in the CSP; `[site.csp]` adds origins for the declaring plugin's pages (and every page for the active theme). Customers: `site.customer` is a native read-only entity on `site_customers` (`customers.rs`: sign-up, Argon2 passwords, opaque sessions in `site_customer_sessions` behind the `aphel_site_session` cookie, single-use tokens for verify/reset/magic link, events `site.customer.*` with audit, privacy source in `privacy.rs`); `account.rs` serves the server-rendered account pages under `/conta` or `/account` (Origin check, rate limits); pages with `requires_customer`/`customer_field` are never cached; accounts turn on when a plugin needs them or with `site.accounts`. WIT: `request.customer: option<customer>` and `response.headers` (allow-listed: cache-control, etag, last-modified, location as a local path, vary, content-language; `private, no-store` by default and forced for signed-in customers). Languages: `site.languages` (module config, codes from `SITE_LANGUAGES`) adds `/<code>` prefixes resolved by `Language::resolve` in `handler.rs`; the effective prefix carries the code, `translated` exposure fields read `<field>_<code>` in `data.rs`, menu items have `labels`, and `aphel/head.html` writes `hreflang` from `site.alternates`. JSON-LD is built in `structured_data` (`handler.rs`) from the page type or `seo.schema` plus the rendered `seo.structured_data` object. Redirects by hand live in `site_path_redirects` (`GET|POST /site/path-redirects`, `DELETE /site/path-redirects/{id}`) and apply only when no page answers. Theme preview: `POST /site/preview` stores a 30-minute token in `site_previews`; `/_aphel/site/preview/<token>` sets the `aphel_site_preview` cookie, redirects to the requested `path` and the handler renders with that theme, uncached, with a banner (`preview.rs`). The same endpoint previews a record draft (`record: { record_type, record_id, fields: { <public field>: <source field> } }`, needs the record's update permission or `settings.manage`): its `match`/`where` pages ignore the exposure conditions for that record only and swap the fields (`data::draft`), and its images are served. Pages may pick one record with `where` instead of `match` (`PageSource::Single`, e.g. the home page `/`), `[[site.menu]]` items with `label_field` (+ `where`, `sort`) list records of a `match` page as items `<owner>.<key>.<record id>` (`handler::record_menu`, every page then carries the entity tag), and the `from_json` filter parses JSON stored in `long_text` fields. Modules contribute `dyn SiteEmbedSource` (contract `site`; `form` from `forms`, `booking` from `booking`) placed with `embed(kind, key)`; `site_list(owner, entity, sort=, limit=)` renders other plugins' records with their `site/cards/<entity>.html`; both leave markers resolved after rendering (`deferred.rs`); `site_path(path)` builds links to site and public app paths; `GET /site/embeds` and `GET /site/collections` serve editors (any signed-in user). Several plugins may declare `/`: install skips the shape conflict for `HOME_PATH`, `SiteRuntime` keeps the extra candidates and `site.home` picks the one that answers (`find`/`effective_routes`, `home_candidates` in `GET /site`); `GET /site/languages` lists the site languages for editors. The service worker version hashes the content of every built file and precaches with `cache: 'reload'` (`web/scripts/pwa`). The official plugin `pages` (repo `plugins/pages`) builds site pages from blocks on top of these. With `site.link_people` (and `people` enabled), `people_link.rs` links confirmed customers (`site_customers.person_id`) to the person with the same email or creates one owned by `site.people_owner`. Person merges move the link (`MergeReferences`) and `people.person.purged` clears it (`invalidation.rs`). `site.links` adds hand-made menu links (ids `link.<id>` in `site.menu`). Templates referencing missing templates are rejected by `check_bundle`. Public app pages: modules contribute `PublicAppPath` (`book`, `quote`, `p`); `web::dispatch` serves those first segments under the site mount with the app shell (`SiteSurface` adds `<meta name="aphel-surface" content="site">`, which turns off the service worker), the shell carries `aphel-public-base` for `publicUrl()` in the web SDK, `PublicBaseUrl::tools_root`/`Ctx::public_tools_url` build emailed links on the site address when `site` is enabled, and site pages may not use those segments. Guide: `web/docs/src/content/docs/plugins/site-pages.md`.
- **Field permissions and privacy:** record queries use `FieldSet::for_scope` (hidden fields disappear from `active()`; filtering/sorting by them → 422 `field_not_accessible`), system field writes go through the `FieldAccessPolicy` check (`kernel/application/fields/permissions`) and record responses go through the `record_redactor`. Fields with personal data carry `is_personal`/`is_sensitive`; data subjects, requests and retention live in `modules/privacy`. Account security events (login, 2FA, password, sessions, tokens, permissions) go through `state.security_events` (`SecurityEventRecorder`), outside the business transaction.
- **Custom objects and relationships:** the `RecordTypeRegistry` is a single installation-wide cache (`state.registry().await?`, `RecordTypeCatalog` in `kernel/application/custom_objects/runtime.rs`), invalidated when objects/relationships change (`organization_settings.custom_schema_version`, `state.record_types.invalidate()`); in the worker, `CatalogJobHandler`/`CatalogEventConsumer` resolve the current registry on each run. Limits hardcoded: `CUSTOM_OBJECTS_MAX` (50) and `CUSTOM_OBJECT_FIELDS_MAX` (200). Code that receives a `record_type` from the user never uses `RecordTypeRegistry::builtin()`. `custom.<key>` dynamic types live in `custom_records` with an `object_id` partition (applied by `push_record_scope_as`/`push_partition`); relationships become `RecordRelation` with `RelationPath::Relationship`. Deletions of core records call `fields().links().ensure_deletable(&mut tx, ..)` (`on_delete = restrict`). Guide: [`docs/architecture/custom-objects.md`](docs/architecture/custom-objects.md).
- **Global search:** the index (`kernel/application/search`) is generic over the `RecordTypeRegistry`; a new type is picked up automatically if it publishes `<type>.*` events with the record and marks fields as `searchable`. Reindex with `aphel search reindex`. Guide: [`docs/architecture/search.md`](docs/architecture/search.md).
- **Automations:** triggers implement `AutomationTrigger` (registered in `TriggerRegistry::builtin()`) and actions implement `AutomationAction` (registered in `ActionRegistry::builtin()`, with `required_permissions`, `retry_safe` and `secret_fields`); what actions do in the system goes through the `AutomationGateway` port, implemented in `kernel/application/automations/gateway_impl.rs` (`HandlerAutomationGateway`: records through the type's `RecordTypeHandler`; the rest through the `AutomationOperations` port, implemented in `kernel/api/automation_operations.rs` reusing the modules' use cases; never direct SQL). Execution in the worker (`automations.trigger` → `automation.run`) with the scope of whoever published the version (`AccessScope::through_automation`, actor `Actor::Automation`) and `causation` in the events (`CausedEventPublisher`). A new module joins the generic triggers by publishing `<type>.created|updated|deleted` with `changes: [{ field, old, new }]`. Guide: [`docs/architecture/automations.md`](docs/architecture/automations.md).
- **Runtime plugins:** third parties ship `.aphelplugin` packages (`plugin.toml` + `backend.wasm` + `web/`), handled by the optional module `modules/wasm_runtime` (not `required`; the build, the backend and the web typecheck work without it) (tables `plugins_installed` with `installed_by`, `plugins_files`, `plugins_data`, `plugins_compiled`, `plugins_state`; declared permissions in the kernel table `runtime_permissions`, owner `plugin:<key>`). Manifest: `entities` become managed custom objects (`CustomObjectAdminUseCases::create_managed`, outside the `CUSTOM_OBJECTS_MAX` user quota; `permission_scope` sets the scope of the default `manager`/`member` grants) locked by `custom_objects.module_key` (409 `custom_object_managed_by_module`); entities may name a `title_field`, and managed fields marked `read_only` are read-only for people and writable only by the owning plugin's backend (checked through the plugin `ExecutionContext` in `FieldAccessPolicy::access_for`); fields may be `unique` (reservations in `custom_field_unique_values` maintained by the `CustomFieldWriter`, released on delete, retaken on restore; 409 `plugin_field_unique_conflict` on install/upgrade); `[[role_presets]]` are offered unchecked in the consent dialog and created only when selected; declared, preset and entity grants are reconciled on install/upgrade and by `POST /wasm-runtime/{key}/grants` (grant counts in `grants`/`ungranted_roles`); `fields` become `field_definitions` with `module_key` (the boot sync `release_undeclared_fields` only releases fields of compiled modules); `requires` (known core or `co_*` permissions) and `[[permissions]]` (`<key>.<action>`, `grant_to`) define the plugin's **capabilities**; `hooks` (`record.saving|validating|saved|deleting|archiving|committed|deleted|restored|purged` or a domain hook from the host catalog), `operations` (module operations called with host `invoke`), `optional_operations` (the same for operations whose provider may be absent: not checked at install, 404 `plugin_operation_unknown` when missing), `events`, `routes` (`public = true` → `/api/v1/public/p/{key}/{*path}`, rate limited), `[http] allowed_hosts`, `[[schedules]]` (cron with seconds), `settings` (`number|boolean|text|secret`), `[[actions]]` (automation actions `plugin.<key>.<action>` with typed `inputs`, via `AutomationActionSource` in `automation.rs`), `[[emits]]` (events `plugin.<key>.<name>` published with host `emit`, automation triggers via `AutomationTriggerSource`; refused in hooks), `[[notifications]]` (kinds `<key>_<name>`, host `notify` in `notify.rs`) and `[[widgets]]` (dashboard widgets `<key>_<name>`, data from `on-widget` with the viewer's scope, `widgets.rs`); kinds and widgets go through the kernel's runtime contributions (`App::replace_runtime`) (`kernel/modules/builder.rs`, `App::replace_runtime`). Entity field keys cannot reuse a custom object's built-in keys; `schema::preflight` refuses every conflict before writing. **Scope:** every call runs as actor ∩ capabilities (`AccessScope::restricted`); hooks, private routes and widgets use the caller, automation actions the automation's scope, events, schedules and public routes use the installer through `AccessScope::through_plugin` (actor `Actor::Plugin(key)`, 503 `plugin_owner_inactive` when the installer is inactive); a plugin never receives the events it caused (the causal chain restarts at an external HTTP response, so a plugin does receive events that follow a provider's answer; every execution counts its depth and stops at 64). Writing a `record` field needs read access to the referenced type. Record writes from in-transaction hooks → 409 `plugin_write_in_hook` (write from events). Retryable callbacks (events, schedules, HTTP responses, actions) write directly only retry-safe changes: `update-record-if`, `apply-records` whose updates are all conditional and whose creates target the plugin's own entities with a unique field or unique index filled, and `invoke` of idempotent operations; anything else goes through `defer-effect` (409 `plugin_effect_required`). Install shows a consent dialog from `POST /wasm-runtime?dry_run=true`. Plugin packs (`.aphelpack`: `pack.toml` + `.aphelplugin` files, built by `aphel-plugin bundle`; `pack.rs`, `POST|GET /wasm-runtime/packs`, table `plugins_packs`, `plugins_installed.pack_key`) install several plugins with one consent: every plugin is validated first (operations, contracts and entities of the other pack plugins count as available), then installed in dependency order, skipping identical packages; pack settings only fill settings without a value. Upgrades reconcile in `schema.rs`: undeclared fields, entities and options are deactivated (data kept), a field type change → 409 `plugin_field_type_changed`. A backend that stops loading shows `backend_error` and fails closed (503 `plugin_failed`) on the record types it hooks. Runtime (`runtime.rs`): `wasmtime` Component Model, epoch timeouts (2 s hooks, 10 s routes, 30 s events, 60 s schedules), 64 MB per instance, one `PluginPre` per plugin, compiled code cached by the SHA-256 of `backend.wasm` in process and in `plugins_compiled` (deserialized by other processes and restarts), WASI from `wasmtime-wasi` with an empty sandbox; host errors keep their HTTP status across the plugin. Contract: WIT world `aphel:plugin@1.0.0` (`modules/wasm_runtime/wit/plugin.wit`, copied to `sdk/rust/aphel-plugin-sdk/wit` and `sdk/js/aphel-plugin-sdk/wit` by `make modules`): exports `on-hook`/`on-event`/`on-route`/`on-schedule`/`on-action`/`on-widget`/`on-operation`/`on-contribution` (`[provides] operations` and `[[contribute]]` in the manifest), imports `host` (records, `update-record-if` (row lock + `version_conflict`), `apply-records` (1–100 creates/conditional updates in one transaction, `{"$ref": n}` to earlier ids), `can`/`permissions` (effective actor ∩ capabilities, also in hooks), kv, `http-fetch`, `notify`, `emit`, `invoke`, `settings-json`, `secret`, `now`, `log`; record values as JSON strings). 1.0.0 is unreleased; from its release, `1.x` only gains functions/interfaces (existing records, enums and signatures are frozen; a breaking change is `2.0.0`, and serving two majors side by side is not implemented). Host API (`host.rs`): records only through `RecordTypeHandler`/`RecordQueryEngine`, key-value storage, settings, secrets (`SecretVault`, `owner_type = "plugin"`, never returned or audited in clear), outbound HTTP through the webhook SSRF policy (`net.rs`, no redirects, 5 MB), clock and log: never SQL. Schedules: `schedule.rs` (`wasm_runtime.tick` every minute → one `plugin.schedule` job per due slot, unique key `plugin.schedule:<key>:<name>:<slot>`). The registry (`registry.rs`) rechecks `plugins_state.version` at most every 2 s in every process. Web: `web/src/kernel/modules/wasm_runtime.ts` imports the enabled bundles (`GET /api/v1/public/wasm-runtime`) before `@/app/App` builds the router; the import map (`vite.config.ts`, `pluginImportMap`) maps `react`, `react/jsx-runtime`, `react-dom`, `react-router`, `@tanstack/react-query`, `react-i18next` and `@aphel/web-sdk` to the stable entries `/_aphel/shared/*.js` built from `web/runtime/*.js` and `web/src/sdk/index.ts` (the public, stable web API: change it only additively); plugin management, consent and settings dialogs in `web/src/features/settings/modules/wasm_runtime`. Reference plugins outside the repo: `aphel-equine`, `aphel-probe` (exercises every host call) and `aphel-hello-js` (JavaScript SDK). Record fields may target custom objects (namespaced entity keys). `deals` reads and writes contributed fields like `people`/`organizations`. Hook argument types of `deals`, `leads` and `quotes` expose public accessors. Also on the host: `kv-increment`, `kv-set-if-absent`, `next-number`, `aggregate-records`, `iterate-records`, `upload-file`, `read-file`, `respond-bytes`, `set-audit-reason` (`audit_logs.reason`), `organization-json`, `list-users|roles|teams`; `defer-effect` also takes `email` (opt-out list in `kernel/application/communication.rs`, routes `/communication/opt-outs`) and `http`; change feed in `changes.rs` (`plugins_changes`, `GET /wasm-runtime/{key}/changes` and `/changes/stream`, `useChangeFeed` in the web SDK); data subject requests through the `DataSubjectSource` contribution (`kernel/application/data_subject.rs`, plugin side `data_subject.rs`, manifest `[privacy] subject_data`, `on-action` named `privacy.<action>`); public web app at `<app base path>/p/{key}/` from `[web] public`. **Plugin bridge** (`kernel/modules/plugin_bridge.rs`): modules reach plugins without `plugins` depending on them. Modules register operations with `app.operation` (files `exposed_operations.rs`) and forward domain hooks with `app.forward_hook(Hook, PluginHook::new(..))` / `app.forward_filter_hook(..)`: the hook's argument type implements `PluginHookArgs` (record id and JSON payload) and, for filters, `PluginHookFilter` (patch merge); a foreign argument type passes a `HookForwarding` to the `_with` variants. The handler runs at `PLUGIN_HOOK_PRIORITY` = 50 with zero cost when no plugin subscribes; `plugins` provides the `dyn PluginHookDispatcher` and implements `invoke` (`bridge.rs`). A new module operation or hook never changes the WIT. Catalog: `GET /api/v1/wasm-runtime/host-catalog`, [`docs/plugins/host-catalog.md`](docs/plugins/host-catalog.md). Guide: [`docs/plugins`](docs/plugins/README.md).
- **Plugins as part of one system:** the manifest `[menu]` (`flat`, `own_entities`) is applied by the web (`applyPluginMenus` in `web/src/kernel/modules/navigation.ts`, `GET /public/wasm-runtime` returns `name`, `menu` and `role_homes`); a plugin that provides (`provides.contracts`) a contract a built-in module declares disables that module while the plugin is active (`plugins_module_conflicts`, `modules/wasm_runtime/src/modules.rs`, kernel `ModuleToggleGuard` keeps them disabled, `ModuleView.held_by`); plugin×plugin overlaps (`conflicts.rs`) need `acknowledge_conflicts=true` on install and enable (409 `plugin_conflicts_unacknowledged`); `entities[].internal` (`custom_objects.is_internal`) hides record types from people-facing lists; settings support `select`, `group`, `options_from` (a text setting picked from the records of an entity) and `settings_permission`. Error codes of a plugin are translated by `errors.<code>` in the plugin's own web namespace (`errorMessage` in `web/src/components/feedback/notify.ts`).
- **UI plugins:** there are no themes or experience profiles: a plugin that declares `[ui]` in `plugin.toml` (optional design tokens, optional `web/` bundle that provides screens through `app.provideComponent`) is an interface every user can choose (`user_preferences.ui_plugin`, organization default in `organization_settings.settings.$.ui_plugin`, `GET /ui-plugins`, `/public/ui/<key>.css`). Contracts selected by the UI plugin: `app.Frame` and `records.Presentation`. Tokens live in `back/modules/wasm_runtime/tokens.json`. Guide: [`docs/architecture/ui-plugins.md`](docs/architecture/ui-plugins.md).
- **Multi-tenancy** (`kernel/src/tenancy`, guide `web/docs/src/content/docs/admin/multi-tenancy.md`): the control database (`ControlPlane`; tables `tenants`, `tenant_hosts`, `operators`, `operator_sessions`, `operator_audit`) lists tenants; `TenantDirectory` maps hosts and `tenancy::router` sends `CONSOLE_HOST` to the console, active tenants to their `TenantRuntime` (pool, `AppState`, router, refreshers) and the rest to 404/503. Tenant code runs inside a `task_local` tenant scope (`tenancy::scope`, kept on streamed bodies) and `runtime_state()`/`aphel_sdk::runtime()` resolve through it; in multi mode everything fails closed outside a scope. Rules: tenant state lives in `AppState` or `TenantLocal<T>` (`aphel_sdk::platform::tenancy::TenantLocal`; one value per tenant, one per process in single mode, `None` outside a scope), never in a plain `static`; spawned tenant work uses `tenancy::spawn` (or `tenancy::bind` for `JoinSet`), never bare `tokio::spawn`; the arch check counts `unscoped_spawns` and `mutable_statics`. In-memory rate limiter keys carry the tenant id. The worker (`tenancy::run_workers`) runs one loop per active tenant over a shared `WORKER_CONCURRENCY` semaphore. Provisioning, migrations of every tenant, host management and deletion live in `tenancy/provisioning.rs` and are shared by the console (`tenancy/console`, API `/api/console/v1` with its own OpenAPI `back/console-openapi.json`, web `web/src/console` on the `console` surface) and `aphel tenants`; commands acting on one company take `--tenant <slug>`. Every operator action writes `operator_audit`. `aphel tenancy-check` verifies isolation with two throwaway tenants.
- Files only via `FileStorage` (`state.storage`, key `<year>/<month>/<id>`; in multi mode `DynamicFileStorage` stores it under `<tenant slug>/`) and authenticated endpoints; attachments reference records via `RecordRef`. New attachable record types go into the `PermissionRecordAccessChecker`.

## Frontend

- **Web module kernel:** the web is assembled by the modules (`web/src/kernel/modules`). Each module is `defineModule({ key, required?, translations, settingsPanel?, register(app) })` in `web/src/modules/<key>/index.ts(x)` and enters `web/src/modules.generated.ts` (generated by `make modules`; import `@modules/<key>`). `app` offers `routes`/`publicRoutes`, `nav`, `settings(area, item)`, `recordTab`, `slot`, `filter`, `override`, `fieldType`, `timelineRenderer`, `eventRenderer`, `widget`, `command`; everything carries the module key and is filtered by the enabled set from `/api/v1/modules` (`required` always active; unknown to the server active after loading; routes behind the `ModuleGate`; signed-out screens load the state from the public `GET /api/v1/public/modules`, so the web never calls a disabled module's route). No central lists: router, sidebar, palette, shortcuts and settings areas read from the registry. Slots (`<Slot name props />`): `record.detail.{header,actions,sidebar}`, `record.fields.panel`, `record.list.{toolbar,rowActions,bulkActions}`, `record.form.sections`, `dashboard.top`, `composer.tools`, `user.menu`, `app.banner` (above the signed-in shell, full-screen pages and sign-in screens). Filters (`applyFilters`/`useFilters`): `records.columns`, `records.formLayout`, `records.detailTabs`, `navigation.items`, `commands`, `settings.sections`. Overrides: `<Overridable id="people.DetailPage" component={..} />`/`useOverride`. `FieldInput`/`FieldValueDisplay` look up the field type registry (native ones registered by the kernel). A module's page does not import tabs or actions from another module: the other module contributes them. Done: `people`, `organizations`, `leads`, `scoring`, the session 33 modules (`currencies`, `workflow`, `deals`, `line_items`, `renewals`, `products`, `pricing`, `quotes`, `approvals`, `tasks` with calendar and inbox, `notes`, `telephony`, `forecast`, `goals`) , the session 34 ones (`email`, `sequences`, `booking`, `automations`, `webhooks`, `integrations`, `imports`, `exports`, `bulk_actions`, `org_export`, `privacy`, `duplicates`, `trash`, `migrations_assistant`, `timeline`, `tagging`, `followers`, `favorites`, `segments`, `dashboard`, `reports`, `onboarding`, `demo`, `assignment`) and the former extensions; what is left in `web/src/features` is platform, registered by the `kernel` web module (`web/src/modules/kernel`). Guide: [`docs/architecture/web-modules.md`](docs/architecture/web-modules.md).
- Web platform (auth, installer, core settings, system, audit, files, notifications, search, custom objects, mobile, record building blocks) in `web/src/features/<feature>/`, registered by the `kernel` web module.
- API calls only via `web/src/api` (generated types in `web/src/api/schema.d.ts`).
- Texts only via i18n. Module namespace = key, in `web/src/modules/<key>/i18n/<locale>.json`; the `kernel` ones in `web/src/i18n/<locale>/<namespace>.json`. After creating or moving JSON files, `npm run i18n:types` regenerates `web/src/i18n/i18next.d.ts`.
- Base UI components in `web/src/components/ui`. They depend on no i18n, session or API: texts come from `UiLabelsProvider` (`UiLabelsBridge` in the app) and every color, radius, height and shadow comes from the tokens in `web/src/sdk/tokens.css`, never from fixed values. The public surface is `web/src/sdk/ui.ts`, served to plugins as `@aphel/ui` (`/_aphel/shared/ui.js`, with `/_aphel/shared/ui.css` for public apps) and re-exported by `@aphel/web-sdk`; it only grows. Guide: [`docs/ui`](docs/ui/README.md).
- Record screens use the generic building blocks from `web/src/features/records` (without knowing about modules): the module calls `registerRecordResource` and assembles `RecordListView` (`table/`), `RecordFormDialog`/`RecordForm`/`InlineFieldEditor` (`form/`, inputs in `components/fields`) and `RecordDetailPage` (`detail/`, `timeline/`). Confirmation dialogs, toasts, error boundaries and the unsaved-changes guard come from `web/src/components/feedback`.


## Commands

```bash
make up          # starts MySQL and Mailpit (docker compose)
make down        # tears down the environment
make modules     # generates the module registries from back/aphel.modules.toml (xtask)
make dev-back    # backend at http://127.0.0.1:3001 (cd back && cargo run -- serve --with-worker to run the worker alongside)
make dev-web     # Vite with /api proxied to the backend
make lint        # modules sync --check, cargo fmt --check, clippy --workspace -D warnings, oxlint, typecheck
make fmt         # cargo fmt
make api-types   # generates web/src/api/schema.d.ts from the OpenAPI
(cd web && npm run i18n:types)  # generates web/src/i18n/i18next.d.ts from the modules' JSON files
(cd sdk/cli && cargo build --release)  # aphel-plugin new [--js]|build|pack for runtime plugins
(cd sdk/js/aphel-plugin-sdk && npm install)  # aphel-plugin-js, used by JavaScript plugins
make build       # release build (web + binary)
```

Details in [`docs/development.md`](docs/development.md).

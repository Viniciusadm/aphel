# Aphel

Aphel is an open source CRM that is modular, configurable and extensible, ready to be used by freelancers, agencies, real estate agencies, consultancies, SaaS companies and sales teams.
The core (contacts, companies, deals, activities and history) is shared; fields, pipelines, automations and modules adapt to each company without changing the code.
It runs as a single Rust binary with the React frontend embedded; each installation serves a single company (the "organization"). What goes into the binary is chosen in `back/aphel.modules.toml` (session 36).

## Global decisions (do not reopen)

| Area | Decision |
| --- | --- |
| Backend | Rust (edition 2024), axum 0.8, sqlx 0.9, hexagonal architecture in `back/` (domain → application → infrastructure/api) |
| Frontend | React 19 + TypeScript + Vite in `web/`, served embedded in the binary via `rust-embed` |
| Database | MySQL 8, one database per installation. One installation = one company; there is no `organization_id` in the tables |
| IDs | UUID v7 in `CHAR(36)` |
| Money | `DECIMAL(18,2)` + ISO currency code; `rust_decimal` in Rust |
| Web authentication | Opaque session in an `HttpOnly`/`SameSite=Lax` cookie, token stored hashed in the database (revocable). The template's JWT is removed in session 02 |
| API authentication | API tokens with scopes, via `Authorization: Bearer` |
| Single installation | No multi-tenancy (session 28). Company data in `organization_settings` (single row, `id = 1`). Every use case receives an `AccessScope` (user, role, teams, permissions) for authorization; system work uses `AccessScope::system()` |
| Custom fields | Fixed tables for core entities + typed custom values (EAV with per-type columns and indexes) |
| Events | Domain events written to an outbox table in the same transaction; consumed by the worker |
| Queues and scheduling | Queue in a MySQL table (`FOR UPDATE SKIP LOCKED`) + scheduler; subcommands `aphel serve`, `aphel worker`, `aphel migrate`, `aphel demo` |
| Files | `object_store` crate: local disk by default, optional S3-compatible storage. Downloads always through an authenticated endpoint |
| Email | `lettre` via SMTP; Mailpit in development |
| API and contract | REST at `/api/v1`, documented with `utoipa`; the frontend generates types with `openapi-typescript` |
| UI | Tailwind CSS v4, in-house components on top of Radix (shadcn style), React Router 7, TanStack Query 5, TanStack Table, react-hook-form + zod, i18next (pt-BR and en; pt-BR is the default), dnd-kit, Recharts |
| Tests | **None for now**: tests were removed in session 11 and writing or running tests is forbidden until the user asks for them. Validation = `cargo check` + `npm run typecheck`/`lint` |
| Architecture | Modular monolith. No microservices |
| Workspace (session 36) | `back/kernel` (crate `aphel-kernel`), `back/modules/<key>` (crates `aphel-mod-<key>`), `back/plugins/<key>` (local plugins), `back/app` (crate `aphel`, the binary with the CLI and the generated registry) and `back/xtask` |
| Build selection | `back/aphel.modules.toml` (`<key> = { path \| git + tag \| version, required? }`); `make modules` generates `back/app/Cargo.toml` (`module-<key>` dependencies), `back/app/src/modules.rs`, `web/src/modules.generated.ts` and the `@modules/<key>` aliases. Generated files are committed. Only the core and official modules are compiled |
| Third-party plugins (session 37) | Runtime `.aphelplugin` packages (WebAssembly backend via `wasmtime` + ES module web bundle via import map), installed from the UI/API without rebuilding, restarting or touching this repository. Host: required module `plugins`; guide [`docs/plugins`](docs/plugins/README.md) |

## Code rules

- All code, documentation (`.md`), commit messages, API descriptions and JSON schemas in English. UI texts always via i18n, in both pt-BR and en.
- No explanatory comments in the code, and no docstrings. Only `TODO`/`FIXME` and directives required by tools.
- Follow the layering pattern from [`back/README.md`](back/README.md).

## Backend

- **Kernel × modules (session 34):** there is no more `legacy`. The platform lives in `back/kernel/src/` (`domain`, `application`, `infrastructure`, `api` = HTTP, plus `modules`, `records`, `context.rs`, `state.rs`), registered by the `kernel` module (`back/kernel/src/kernel_module.rs`: core routes, tags, permissions and notifications, record guards and platform workers); all the business logic is in `back/modules/<key>`. Rule: if the kernel depends on something, it is kernel (that is why `search`, `record_sharing`, `config_packages`, `crm`, `aggregates`, `custom_objects`, `user_preferences`, notifications and push, the contracts for dashboard widgets, automation (`AutomationTrigger`/`AutomationAction`, gateway), webhook transport, integration/SMTP, `SegmentSourceResolver`, `RecordFollowerSource` and `DuplicateDetector` in `kernel/records/duplicates.rs` stayed in it). In the items below, `kernel/<path>` is `back/kernel/src/<path>` and `modules/<key>/<path>` is `back/modules/<key>/src/<path>`. Inside the kernel the layers from `back/README.md` apply: pure `domain`, `application` with use cases over ports, `infrastructure` implementing the ports, `api` as the HTTP layer.
- **Single installation:** one installation serves one company. There is no `organization_id`, no `organizations` table and no organization switching. The company data (name, logo, color, locale, time zone, currency, `settings`, `custom_schema_version`, 2FA policy, `installed_at`) lives in `organization_settings` (single row, `id = 1`; read through `OrganizationRepository::find()`). Single-configuration tables use the same pattern (`id TINYINT = 1`, `INSERT .. ON DUPLICATE KEY UPDATE`). The company and the first admin are only created by the installer (`/api/v1/installer`, with optional backup restore at `/api/v1/installer/restore`); the other users join by invitation. Member = user (`users.role_id`, `users.status` = `invited`/`active`/`deactivated`).
- The access scope is the `AccessScope` (`kernel/domain/access/access_scope.rs`: user, role, expanded teams, permissions, `api_token`, `automation_id`, enabled extensions), with no organization. Repositories and use cases that read business data receive `&AccessScope`; jobs and consumers without an actor use `AccessScope::system()` (all permissions) and, when the actor matters, build the scope with `build_access_scope` (`kernel/application/access`).
- **Authorization: explicit call in the use case.** The handler extracts `AuthContext` (single extractor: rejects invited or deactivated users and sessions pending 2FA) and passes `&tenant.scope` to the use case, which calls `scope.require(&Permission::X)?` or `scope.record_filter(&Permission::X)?` (trait `Authorizer` in `kernel/application/access`). There is no `Require<P>` extractor. New permissions become constants in `kernel/domain/access/permission.rs` and enter the catalog through the module's `app.permission(PermissionDefinition::record|administrative(..))` (the core ones in `builtin_permission_catalog()`, registered by the `kernel` module); `permission_catalog()` reads the `App`. Operations routes (`/api/v1/system/*`: health, jobs, updates, system audit) require `system.manage` (granted to the admin role); there is no platform administration.
- Non-GET requests require the `X-Requested-With: aphel` header (the web client already sends it), except with `Authorization: Bearer` and on public routes (`/api/v1/public/*` and `/api/v1/hooks/*`, via `csrf::is_public_path`). Session in the `aphel_session` cookie; API tokens `aphel_<prefix>_<secret>` go through the same `AuthContext` with permissions = scopes ∩ the creator's current permissions and actor `Actor::ApiToken` (via `Actor::from_scope`). Session/account routes use `SessionContext` (rejects tokens).
- **API style guide:** [`docs/api/style-guide.md`](docs/api/style-guide.md) (item `{ data }`, list `{ data, meta }`, `filter[field][op]` via `RecordListQuery`, `include=` via `IncludeQuery`, `If-Match` via `IfMatch` + `ensure_version` → 409 `version_conflict`, rechecked inside the transaction with `aphel_kernel::records::lock_version` (row locked with `FOR UPDATE`), codes in [`docs/api/errors.md`](docs/api/errors.md)).
- Every route has a `utoipa` annotation and appears in `/api/openapi.json`.
- Every error goes through `AppError` and comes out in the envelope `{ "error": { "code", "message", "details" } }`.
- Listings respond with `Page<T>` = `{ data, meta: { total, page, per_page } }` and items with `Data<T>` = `{ data }`, using the pagination extractor.
- Migrations: platform ones live in `back/kernel/migrations` (kernel, `sqlx::migrate!`); module ones live in `back/modules/<key>/migrations`, numbered within the module and declared in the `Manifest` (`Migration::new(n, desc, include_str!(..))`), applied by `module_migrations` in load order. A module declares `depends_on`/`optional` for every module whose tables it references by FK (the load order comes from the dependencies).
- **Every business mutation publishes a domain event and writes an audit entry in the same transaction.** The use case's port bundle has `type Transactions: TransactionManager`, `type Events: EventPublisher<Tx>` and `type Audit: AuditLog<Tx>` (contracts in `kernel/application/shared`); the write repository receives `&mut Tx`. The use case does `begin` → write → `events().publish(&mut tx, DomainEvent::new(..))` → `audit().record(&mut tx, AuditEntry::new(..))` → `commit`. Reference: `change_member_role` in `kernel/application/organization_admin/members.rs`. Audit diffs with `application::audit::diff_changes` (sensitive fields become `"[redacted]"`). In MySQL the `Tx` is `MySqlTx` and the adapters come from the `AppState` (`state.events`, `state.audit`, `state.jobs`, `state.storage`). In modules following the new pattern the same flow uses `ctx.begin()` → store → `publish_mutation(ctx.events(), ctx.audit(), &mut tx, ..)` → `tx.commit()` (reference: `modules/contacts/service.rs`).
- **Module kernel (session 29):** everything is a module (`trait Module` in `back/kernel/src/modules`: `manifest()` + `register(&mut AppBuilder)` + `on_enable`/`on_disable`/`uninstall`). The `AppBuilder` is the only contribution point (`routes`/`public_routes`/`root_routes`, `override_route`, `on::<H>`/`filter::<H>` on the `HookBus`, `provide`/`decorate` in `Services`, `permission(..).grant_to([..])` (or `grant_organization_wide_to` for organization scope in all roles), `public_event`, `notification_kind`, `openapi_tag`, `widget`, automation `trigger`/`action`, `job`/`consumer`/`schedule`/`worker`); each contribution stores the module key and is ignored when the module is disabled (`EnabledModules` cache), including contributed system fields (`SystemField::is_available`, inactive in the `FieldSet`) and services/decorators (`Services::get` skips layers from disabled modules). `build()` sorts by dependencies (then alphabetically) and freezes into the `App`, which the binary installs with `aphel_kernel::modules::install_app` before the CLI and everyone reads with `aphel_kernel::modules::app()` (`state.app`); the router and `WorkerRuntime::from_app` come from it. The compiled list is `compiled()` in `back/app/src/modules.rs`, generated from `aphel.modules.toml` (`KernelModule` + the modules; `required = true` in the file becomes `AppBuilder::require`). Enablement in `installed_modules` (`module_key`), module migrations in `module_migrations`; `required` modules cannot be disabled. `permission_catalog()`, `NotificationKind` and `PublicResource` are open catalogs read from the `App`. CLI `aphel modules list|doctor|hooks [--markdown]|uninstall <key> [--purge]` (`--purge` exports, drops the `<key>_*` tables and those in `owned_tables`, runs `Manifest::uninstall_sql` and forgets the module's migrations). Hooks enter the catalog with `app.declare_hook::<H>(&[HookUsage::..], description)` ([`docs/modules/hooks.md`](docs/modules/hooks.md), generated). Design: [`docs/architecture/modular-architecture.md`](docs/architecture/modular-architecture.md).
- **Module crates (session 36):** each module is a crate that depends on `aphel-kernel` (paths `aphel_kernel::…`) and, with an alias equal to the key, on the modules it uses (`leads = { package = "aphel-mod-leads", path = "../leads" }`, used as `leads::LeadQualifying`). Cycles between crates are forbidden: the kernel knows no module, and two modules that need each other talk through a hook, a service or a typed contribution (e.g. `timeline::domain::TimelineEventExtension` contributed by `email`; automation operations `TagOperations`/`StageOperations`/`NoteOperations`/`ActivityTypeOperations`/`TaskOperations`/`IncomingWebhookOperations` provided by their owners; `ConfigSectionFactory` for package sections; `CrmDefaultsSeed`; `TimeTriggerPlanner`; `ModuleCommand` for CLI subcommands such as `aphel demo`/`aphel org`; hook `SearchPlanFilter` to restrict search). A third-party module follows the guide [`docs/modules/README.md`](docs/modules/README.md) and the example `back/plugins/lead_pro`.
- **Modules in the new pattern (session 31, reference for 33–35):** `back/modules/<key>/src` with `lib.rs` (`impl Module`: manifest, migrations, `record_type`/`extend_record_type`, routes, tags, permissions with `grant_to`, public events, hooks, `provide`, worker), `domain.rs`, `service.rs` (use cases as `async fn(ctx: &Ctx<'_>, ..)` functions), `store.rs` (concrete structs with SQL over `&mut MySqlTx`, `Store::of(ctx)`), `http.rs` (utoipa routes, DTOs and `RecordTypeHandler`) and `hooks.rs`. No `*Ports`, no repository traits and no `*_use_cases` factories: `Ctx` (`kernel/context.rs`: `scope`, `pool`, `registry`, `events`, `audit`, `jobs`, `app`, `begin()`, `fields()`, `query()`, `pipeline()`, `run_hook`/`apply_hook`) comes from `Ctx::from_state(&state, &scope)` or `Ctx::from_parts(..)`; another module calls `contacts::service::create(&ctx, ..)` directly. All business modules follow this pattern (the session 34 ones were rewritten right after it; the only things still using ports are the kernel's use cases, such as `ConfigPackageUseCases`, `FieldUseCases`, `FileUseCases` and `MySqlDashboardPorts`). Done: `companies` (with `hierarchy/`), `contacts` (swappable service `dyn DuplicateDetector`), `leads` (formerly `lifecycle`; hooks `LeadQualifying`/`LeadDisqualifying`/`LeadConverting`/`LeadConverted`, service `dyn LeadConverter`), `scoring` and, since session 33, `currencies` (service `dyn CurrencyConverter`), `pipelines` (stage guidance/checklist and stage requirements as `RecordValidating` 20/5, rotting), `deals` (with `team/`; veto hooks `DealStageChanging`/`DealWinning`/`DealLosing` and action hooks `DealWon`/`DealLost`, service `dyn AmountCalculator`), `deal_items` (provides `ItemsAmountCalculator` and `quotes::DealItemsWriter`), `renewals`, `products`, `price_lists` (with bundles; services `dyn PriceListResolver`/`DiscountLimits`/`BundleExpander`), `quotes` (veto hook `QuoteAccepting` and filter hook `QuoteTotals`), `approvals` (`RecordValidating` 10, service `dyn ApprovalGate`), `activities` (types, calendar and inbox; hook `ActivityCompleting`), `notes`, `reminders`, `calls` (service `dyn TelephonyRouter`), `forecast` and `goals`. A module that needs another without depending on it uses `registry.handler(type)`, a hook or a service from `Services`. A system field from another module is a **contributed field** (`SystemField.contributed_by`, read/written by the kernel in `kernel/records/contributed.rs`, flattened into the DTOs); `contacts`/`companies` know neither `lifecycle_stage` nor `score`. Generic record-writing helpers (`InputValidator`, `Patch`, `AddressInput`, `publish_mutation`, `RecordMutation`, `archive_change`…) in `kernel/records`. Non-required modules that come enabled use `Manifest::enabled_by_default()`.
- **Record pipeline (session 30):** every record write goes through the `RecordPipeline` port (`fields().pipeline()`, implementation `MySqlRecordPipeline` in `kernel/records`): authorization in the use case → `saving` (hook `RecordSaving`, filter of `values`/`custom_fields`) → `CustomFieldWriter` + write → `validate` (`RecordValidating`, veto) → `saved` (`RecordSaved`) → event + audit → commit → `committed` (`RecordCommitted`); deletions call `deleting`/`deleted` (`RecordDeleting` blocks `restrict`). Queries apply `RecordQueryFilter` (only adds AND conditions) in the executor; `redacted`/`redacted_items` apply `RecordSerializing` before the `record_redactor`; the field schema goes through `RecordSchemaFilter`. Each type has a `RecordTypeHandler` (`create`/`update`/`delete`/`load`/`archive`/`restore` over JSON; core in `kernel/api/records.rs`, custom objects via a factory) used by automations, import and bulk actions via `registry.handler(type)`; no `match record_type { "contact" => .. }`: what applies only to some types is a capability in `RecordTypeDefinition.capabilities`. Types enter via `app.record_type(def)` and are extended via `app.extend_record_type(key, |t| ..)` (system fields, relations, `member_access`, `managed_field(FieldSpec)` synced at boot with `module_key`, locked with 409 `field_managed_by_module`). `AppState` lives in `kernel/state.rs`. Guide: [`docs/architecture/record-pipeline.md`](docs/architecture/record-pipeline.md).
- **Background jobs:** implement `JobHandler` (`kind()` + `handle(ctx, payload)`) and register it in the module's `register` with `app.job(|env| ..)` or `app.worker(|env| WorkerParts::default().handler(..))` (the platform ones are in `back/kernel/src/kernel_module.rs`); recurring schedules with `app.schedule(ScheduledJobDefinition::new(kind, cron_with_seconds)?)`. Enqueue with `JobQueue::enqueue(&mut tx, Job::new(kind, payload))` inside the transaction (or `enqueue_now`). Handlers must be idempotent.
- **Event consumers:** implement `EventConsumer` (stable and unique `name()`, `accepts(event_type)`, `consume(&event)`) and register it with `app.consumer(|env| ..)` in the module. The `outbox.dispatch` job creates one `event.consume` job per consumer (at-least-once delivery, with retries isolated per consumer).
- **Record listings only via `RecordQuery`; custom field writes only via `CustomFieldWriter`.** Every record type declares itself in the `RecordTypeRegistry` (`kernel/application/fields/registry.rs`: table, owner column, `deleted_at`/`archived_at`, read permission, system fields); listing/filtering/sorting/searching go through `RecordQueryEngine` (filter as an AST validated against the field registry, never SQL built from user text); values are read with `CustomFieldReader`. System fields are seeded when the organization is created and at boot (`sync_system_fields`). Guide: [`docs/architecture/custom-fields.md`](docs/architecture/custom-fields.md).
- **Dashboard widgets:** implement `WidgetProvider` (`kernel/application/dashboard`) and register it in the module with `app.widget(Arc::new(..))` (`WidgetRegistry::builtin()` reads the widgets of enabled modules; on the web, the module's `app.widget`); aggregations build the `QueryPlan` with `resolve_query` (read scope) and reuse `build_query(Count)`.
- **Notifications:** new notices enter as a `NotificationKindDefinition` (channels and defaults) contributed via `app.notification_kind(..)` (the core ones in `builtin_notification_kinds()`, `kernel/domain/notifications/kind.rs`) and are generated by the `notifications.events` consumer from domain events (never notify the actor; email always through the `notification.email` job). Long-running user processes finish by publishing an event with `Actor::System` and `requested_by` in the payload (pattern of `export.*`/`import.*`).
- **Configuration packages:** every portable organization configuration is a `ConfigSection<Tx>` section (`kernel/application/config_packages`: `export`, `validate`, `plan`, `apply`, plan and apply sharing the same reconciliation) registered in `builtin_sections` (`kernel/infrastructure/config_packages/ports.rs`) and described in `docs/config-packages/schema.json`. References always by stable key, never by id; installing never deletes anything nor touches business records. Guide: [`docs/config-packages/README.md`](docs/config-packages/README.md).
- **Secrets** (passwords, signing secrets, integration keys) only via `SecretVault` (`state.secrets`/`WorkerRuntime::secrets()`, `SecretKey { owner_type, owner_id, name }`; company secrets with `SecretKey::organization(name)`, encrypted with `APP_ENCRYPTION_KEY`); they never come back through the API (only "configured"), logs or audit. Events exposed to integrations enter the open catalog via `app.public_event(..)` (the core ones in `builtin_public_events()`, `kernel/application/public_events`; read via `public_event_catalog()`) and `docs/api/events.md`; the public body is built by `ApiPublicEventRenderer`. Integration providers implement `IntegrationProvider` and enter `IntegrationRegistry::builtin()`.
- **Organization configuration × `.env`:** the `.env` only holds infrastructure (`HTTP_*`, `DATABASE_URL`, `APP_ENCRYPTION_KEY`, `RUN_MIGRATIONS`, `RUST_LOG`, `WORKER_*`, `SCHEDULER_INTERVAL_SECS`, `HEALTH_*`, `METRICS_TOKEN`, `UPGRADE_MIN_FREE_DISK_MB`, `WEBHOOKS_ALLOW_PRIVATE_NETWORKS`, `DEMO_*`; see [`docs/configuration.md`](docs/configuration.md)). Public address, upload limit, file storage (disk/S3), webhook delivery, API token limits and community catalog are organization configuration edited in the UI (`GET`/`PATCH /api/v1/organization/settings`, `settings.manage`; `OrganizationConfigCatalog` in `kernel/application/organizations/settings.rs`, `state.organization_config`), with the cache invalidated on write and reread the same way in `serve` and in the worker; every change publishes `organization.settings_updated` with audit (secrets `"[redacted]"`). The sending email is the `smtp` integration (password in the `SecretVault`), resolved on every send by `state.mailer()` (`SmtpMailerProvider`); without SMTP sending fails with `mail_not_configured` without bringing anything down. Storage is resolved the same way (`DynamicFileStorage` behind `state.storage`). Email links always use the saved public address, never the request's `Host`.
- **Field permissions and privacy:** record queries use `FieldSet::for_scope` (hidden fields disappear from `active()`; filtering/sorting by them → 422 `field_not_accessible`), system field writes go through the `FieldAccessPolicy` check (`kernel/application/fields/permissions`) and record responses go through the `record_redactor`. Fields with personal data carry `is_personal`/`is_sensitive`; data subjects, requests and retention live in `modules/privacy`. Account security events (login, 2FA, password, sessions, tokens, permissions) go through `state.security_events` (`SecurityEventRecorder`), outside the business transaction.
- **Custom objects and relationships:** the `RecordTypeRegistry` is a single installation-wide cache (`state.registry().await?`, `RecordTypeCatalog` in `kernel/application/custom_objects/runtime.rs`), invalidated when objects/relationships change (`organization_settings.custom_schema_version`, `state.record_types.invalidate()`); in the worker, `CatalogJobHandler`/`CatalogEventConsumer` resolve the current registry on each run. Limits hardcoded: `CUSTOM_OBJECTS_MAX` (50) and `CUSTOM_OBJECT_FIELDS_MAX` (200). Code that receives a `record_type` from the user never uses `RecordTypeRegistry::builtin()`. `co_<key>` types live in `custom_records` with an `object_id` partition (applied by `push_record_scope_as`/`push_partition`); relationships become `RecordRelation` with `RelationPath::Relationship`. Deletions of core records call `fields().links().ensure_deletable(&mut tx, ..)` (`on_delete = restrict`). Guide: [`docs/architecture/custom-objects.md`](docs/architecture/custom-objects.md).
- **Global search:** the index (`kernel/application/search`) is generic over the `RecordTypeRegistry`; a new type is picked up automatically if it publishes `<type>.*` events with the record and marks fields as `searchable`. Reindex with `aphel search reindex`. Guide: [`docs/architecture/search.md`](docs/architecture/search.md).
- **Automations:** triggers implement `AutomationTrigger` (registered in `TriggerRegistry::builtin()`) and actions implement `AutomationAction` (registered in `ActionRegistry::builtin()`, with `required_permissions`, `retry_safe` and `secret_fields`); what actions do in the system goes through the `AutomationGateway` port, implemented in `kernel/application/automations/gateway_impl.rs` (`HandlerAutomationGateway`: records through the type's `RecordTypeHandler`; the rest through the `AutomationOperations` port, implemented in `kernel/api/automation_operations.rs` reusing the modules' use cases; never direct SQL). Execution in the worker (`automations.trigger` → `automation.run`) with the scope of whoever published the version (`AccessScope::through_automation`, actor `Actor::Automation`) and `causation` in the events (`CausedEventPublisher`). A new module joins the generic triggers by publishing `<type>.created|updated|deleted` with `changes: [{ field, old, new }]`. Guide: [`docs/architecture/automations.md`](docs/architecture/automations.md).
- **Former extensions (session 35):** `ai`, `enrichment`, `esign`, `google`, `insights`, `lead_forms`, `messaging`, `microsoft`, `oidc` and `proposals` are regular modules in `back/modules/<key>` (they implement `Module` directly; there is no longer `aphel-extension-api`, `back/extensions`, `back/src/extensions`, `ExtensionModule` or `ext-*` features). They follow the conventions of every module: routes at `/api/v1/<key>` (a key with `_` becomes `-`, e.g. `/api/v1/lead-forms`), public ones at `/api/v1/public/<key>/…` (everything under `/api/v1/public/` is exempt from CSRF), tables `<key>_*`, jobs `<key>.*`, web in `web/src/modules/<key>` (routes `/<key>`, e.g. `/lead-forms`); module administration in `kernel/application/module_admin` (`ModuleUseCases`, codes `module_*`, events `module.*`, secrets `owner_type = "module"`) and in the Settings › Integrations › Modules screen (`web/src/features/settings/modules`, namespace `modules`). `google`/`microsoft` do `depends_on("oidc")` and reuse its code. Extension points with multiple implementations are **typed contributions**: `app.contribute::<dyn Trait>(Arc::new(..))`, read with `App::contributions::<dyn Trait>()` (enabled modules) or `all_contributions` — SSO login providers (`kernel::api::sso::LoginProvider`), email mailboxes (`email::MailboxProvider`), calendar availability (`scheduling::CalendarAvailability`, receives `ctx`), telephony (`calls::telephony::TelephonyProvider`) and configuration package sections (`ConfigSection<MySqlTx>`). Module settings via `kernel::modules::module_settings(pool, key)`, secrets via `module_secret_key(key, name)`; a contract without context uses `kernel::state::runtime_state()`. Manifest types (`ManifestBase`, `Migration`, `SettingField`…) in `kernel/modules/manifest.rs`. Modules and plugins guide: [`docs/modules/`](docs/modules/README.md) (`README.md`, `hooks.md`, `web.md`, `compatibility.md`).
- **Runtime plugins (session 37):** third parties ship `.aphelplugin` packages (`plugin.toml` + `backend.wasm` + `web/`), handled by the required module `modules/plugins` (tables `plugins_installed`, `plugins_files`, `plugins_data`, `plugins_state`). Manifest `entities` become custom objects locked by `custom_objects.module_key` (409 `custom_object_managed_by_module`), `fields` become `field_definitions` with `module_key` (the boot sync `release_undeclared_fields` only releases fields of compiled modules), `hooks` (`record.saving|validating|saved|deleting`) are forwarded by host handlers registered once, `events` by the consumer `plugins.events`, `routes` by the generic route `/api/v1/p/{key}/{*path}`. The runtime (`modules/plugins/src/runtime.rs`) is `wasmtime` with epoch timeouts (2 s hooks, 10 s routes, 30 s events) and 64 MB per instance; the ABI is JSON (`aphel_alloc`/`aphel_call` exported by the guest, `aphel.host_call` by the host) hidden by `sdk/rust/aphel-plugin-sdk`. The host API (`host.rs`) only offers records through `RecordTypeHandler`/`RecordQueryEngine` with the actor's scope, key-value storage, settings, clock and log: never SQL. The registry (`registry.rs`) rechecks `plugins_state.version` at most every 2 s in every process. Web: `web/src/kernel/modules/plugins.ts` imports the enabled bundles (`GET /api/v1/public/plugins`) before `@/app/App` builds the router; the import map (`vite.config.ts`, `pluginImportMap`) maps `react`, `react/jsx-runtime`, `react-dom`, `react-router`, `@tanstack/react-query`, `react-i18next` and `@aphel/web-sdk` to the stable entries `/shared/*.js` built from `web/runtime/*.js` and `web/src/sdk/index.ts` (the public, stable web API: change it only additively). Record fields may target custom objects (`co_*`). `deals` reads and writes contributed fields like `contacts`/`companies`. Hook argument types of `deals`, `leads` and `quotes` expose public accessors.
- **Individual email:** per-user mailboxes (`mailboxes`) with credentials only in the `SecretVault` (`owner_type = "mailbox"`), conversations/messages/participants/links in `modules/email` (concrete stores `MailboxStore`, `MessageStore`, `LinkStore` in `modules/email/store`, services in `modules/email/service`). Providers implement `MailboxProvider` and enter the `MailboxProviderRegistry` (IMAP/SMTP in the `email` module; other modules contribute `dyn email::MailboxProvider`). Visibility `private`/`metadata`/`shared` per mailbox and conversation (`EmailVisibility::access_for`), always combined with read access to the linked record. `email.*` events once per linked record, with no content in the payload. Guide: [`docs/architecture/email.md`](docs/architecture/email.md).
- **Engagement (session 23):** sequences in `modules/sequences` (jobs `sequences.tick`/`sequence.step`, exits through the `sequences.exits` consumer, sending always through the `email::Sender` service (`modules/email/service`)); scheduling links in `modules/scheduling` (public API `/api/v1/public/book/*`, public web in `web/src/public/booking`, `meeting.booked` with `MeetingEventPayload`, busy = activities + `scheduling::CalendarAvailability` contributions); calls in the `calls` module (`call` activity + `activity_calls`, outcomes in `call_outcomes`, VoIP providers only via `calls::telephony::TelephonyProvider` contributions, chosen by the `dyn TelephonyRouter` service). Guides: [`docs/architecture/sequences.md`](docs/architecture/sequences.md), [`scheduling.md`](docs/architecture/scheduling.md), [`calls.md`](docs/architecture/calls.md).
- **Pipeline and revenue (session 24):** computed system fields with `SystemField::computed(ComputedColumn)` (SQL only in `kernel/infrastructure/query/computed.rs`; read-only) — `days_in_stage`/`is_rotting`/`rotting_at` with `pipeline_stages.rotting_days` and the `time.deal_rotting` trigger; base currency = `organization_settings.currency`, `amount_base`/`exchange_rate` written by the `CurrencyConverter` (`currencies` module) on write and frozen on win/loss, revenue aggregations sum `amount_base`; deal team in `modules/deals/team` with read access declared by `RecordTypeDefinition::member_access` (applied in `push_record_scope_keyed` with `ShareReach::Read`); `mrr`/`arr`/`tcv`/`contract_*` in `modules/deal_items/recurring.rs`, renewal per pipeline in the `renewals` module; these fields enter the `deal` type via `extend_record_type` of the owning module (job `renewals.scan`, unique per `renewal_of_deal_id`). Guides: [`docs/architecture/deal-team.md`](docs/architecture/deal-team.md), [`custom-fields.md`](docs/architecture/custom-fields.md), [`automations.md`](docs/architecture/automations.md).
- **Quotes, approvals and validation (session 25):** approval, stage checklist, validation rule and lifecycle are handlers of the `RecordValidating` hook (priorities 10 `approvals`, 20 `pipelines`, 30 validation rule in `back/modules/record_hooks.rs`, 40 `leads`); approvals in the `approvals` module (policies by type/moment/condition, requests with steps, 409 `approval_pending`/`approval_required`, a new module uses the `dyn ApprovalGate` service (`submit`/`checkpoint`)), quotes in the `quotes` module (`quote` type, signed public link, acceptance syncs the deal through the `quote.deal_sync` job), prices/bundles/discount limits in the `price_lists` module, validation rules (error-condition formula, 422 `validation_rule_failed`) in `kernel/application/fields/validation_rules` and stage guidance/checklist in `modules/pipelines/guidance`. Guides: [`docs/architecture/approvals.md`](docs/architecture/approvals.md), [`quotes.md`](docs/architecture/quotes.md), [`price-lists.md`](docs/architecture/price-lists.md), [`validation-rules.md`](docs/architecture/validation-rules.md).
- **Lifecycle, scoring, hierarchy and sharing (session 26):** `lifecycle_stage` validated and tracked in history by `leads::hooks::validate_stage` (hook `RecordValidating`), transitions through the `lifecycle.transitions` consumer, lead inbox at `/api/v1/leads/*` (module `modules/leads`); scoring in the `modules/scoring` module (idempotent signals per record/signal/source, consumer `scoring.events`, jobs `scoring.recalculate`/`scoring.decay`, computed field `score` = primary model, event `score.band_changed`); hierarchy in `modules/companies/hierarchy` (`parent_company_id`, 422 `company_hierarchy_cycle|too_deep`, filter operator `in_group`); sharing in `kernel/application/record_sharing` (`record_shares`, `RecordScopeFilter.shares` = `ShareReach::{None,Read,Edit}` applied in `push_record_scope_keyed` for every type, permission `records.share`) and followers in `modules/followers` (notification `followed_record_activity`). Guides: [`docs/architecture/lifecycle.md`](docs/architecture/lifecycle.md), [`scoring.md`](docs/architecture/scoring.md), [`company-hierarchy.md`](docs/architecture/company-hierarchy.md), [`record-sharing.md`](docs/architecture/record-sharing.md).
- **PWA and push (session 27):** `push` channel in the notification preferences (`dispatch` enqueues `notification.push`, idempotent via `notifications.pushed_at`); subscriptions in `push_subscriptions` per device and session, deleted when the session is revoked (helpers in `kernel/infrastructure/notifications/push/revocation.rs`: every new session revocation must call them) and when the service responds 404/410; the installation's VAPID keys in the `SecretVault` (`reveal_installation`/`store_installation_if_absent`, table `installation_secrets`); `sw.js` generated at build time by `web/scripts/pwa` and never caches `/api/*`. Guide: [`docs/architecture/pwa.md`](docs/architecture/pwa.md).
- Files only via `FileStorage` (`state.storage`, key `<year>/<month>/<id>`) and authenticated endpoints; attachments reference records via `RecordRef`. New attachable record types go into the `PermissionRecordAccessChecker`.

## Frontend

- **Web module kernel (session 32):** the web is assembled by the modules (`web/src/kernel/modules`). Each module is `defineModule({ key, required?, translations, settingsPanel?, register(app) })` in `web/src/modules/<key>/index.ts(x)` and enters `web/src/modules.generated.ts` (generated by `make modules`; import `@modules/<key>`). `app` offers `routes`/`publicRoutes`, `nav`, `settings(area, item)`, `recordTab`, `slot`, `filter`, `override`, `fieldType`, `timelineRenderer`, `eventRenderer`, `widget`, `command`; everything carries the module key and is filtered by the enabled set from `/api/v1/modules` (`required` always active; unknown to the server active after loading; routes behind the `ModuleGate`). No central lists: router, sidebar, palette, shortcuts and settings areas read from the registry. Slots (`<Slot name props />`): `record.detail.{header,actions,sidebar}`, `record.fields.panel`, `record.list.{toolbar,rowActions,bulkActions}`, `record.form.sections`, `dashboard.top`, `composer.tools`, `user.menu`. Filters (`applyFilters`/`useFilters`): `records.columns`, `records.formLayout`, `records.detailTabs`, `navigation.items`, `commands`, `settings.sections`. Overrides: `<Overridable id="contacts.DetailPage" component={..} />`/`useOverride`. `FieldInput`/`FieldValueDisplay` look up the field type registry (native ones registered by the kernel). A module's page does not import tabs or actions from another module: the other module contributes them. Done: `contacts`, `companies`, `leads`, `scoring`, the session 33 modules (`currencies`, `pipelines`, `deals`, `deal_items`, `renewals`, `products`, `price_lists`, `quotes`, `approvals`, `activities` with calendar and inbox, `notes`, `calls`, `forecast`, `goals`) , the session 34 ones (`email`, `sequences`, `scheduling`, `automations`, `webhooks`, `integrations`, `imports`, `exports`, `bulk_actions`, `org_export`, `privacy`, `duplicates`, `trash`, `migrations_assistant`, `timeline`, `tags`, `followers`, `favorites`, `segments`, `dashboard`, `reports`, `onboarding`, `demo`, `lead_distribution`) and the former extensions (session 35); what is left in `web/src/features` is platform, registered by the `kernel` web module (`web/src/modules/kernel`). Guide: [`docs/architecture/web-modules.md`](docs/architecture/web-modules.md).
- Web platform (auth, installer, core settings, system, audit, files, notifications, search, custom objects, mobile, record building blocks) in `web/src/features/<feature>/`, registered by the `kernel` web module.
- API calls only via `web/src/api` (generated types in `web/src/api/schema.d.ts`).
- Texts only via i18n. Module namespace = key, in `web/src/modules/<key>/i18n/<locale>.json`; the `kernel` ones in `web/src/i18n/<locale>/<namespace>.json`. After creating or moving JSON files, `npm run i18n:types` regenerates `web/src/i18n/i18next.d.ts`.
- Base UI components in `web/src/components/ui`.
- Record screens use the generic building blocks from `web/src/features/records` (without knowing about modules): the module calls `registerRecordResource` and assembles `RecordListView` (`table/`), `RecordFormDialog`/`RecordForm`/`InlineFieldEditor` (`form/`, inputs in `components/fields`) and `RecordDetailPage` (`detail/`, `timeline/`). Confirmation dialogs, toasts, error boundaries and the unsaved-changes guard come from `web/src/components/feedback`.

## Commands

```bash
make up          # starts MySQL and Mailpit (docker compose)
make down        # tears down the environment
make modules     # generates the module registries from back/aphel.modules.toml (xtask)
make dev-back    # backend at http://127.0.0.1:3001 (cd back && cargo run -- serve --with-worker to run the worker alongside)
make dev-web     # Vite with /api proxied to the backend
make lint        # modules sync --check, cargo fmt --check, clippy --workspace -D warnings, oxlint, typecheck
make fmt         # cargo fmt
make api-types   # generates web/src/api/schema.d.ts from the OpenAPI
(cd web && npm run i18n:types)  # generates web/src/i18n/i18next.d.ts from the modules' JSON files
(cd sdk/cli && cargo build --release)  # aphel-plugin new|build|pack for runtime plugins
make build       # release build (web + binary)
```

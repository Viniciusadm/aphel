# Modules and plugins

> **Third-party plugins are runtime packages now.** A `.aphelplugin` is uploaded in Settings › Integrations › Modules and works without rebuilding, restarting or touching this repository: see [`docs/plugins`](../plugins/README.md). This guide covers **compiled modules**, the mechanism of Aphel's core and official modules (and of `back/plugins/lead_pro`, kept as an example of a compiled module).

In Aphel **everything is a module**: people, deals, automations, the integrations and also third-party plugins. Each module is a Rust crate (plus, optionally, a web package) compiled together with the binary. There is no dynamic loading and no marketplace: what goes into the binary is chosen by a file, `back/aphel.modules.toml`, and what runs in each installation is chosen in the UI (enable/disable).

- The build's hook catalog: [hooks.md](hooks.md) (generated by `aphel catalog --markdown hooks`).
- Web extension points (slots, filters, overrides, field types): [web.md](web.md).
- Versions, `requires_aphel` and what counts as a breaking change: [compatibility.md](compatibility.md).
- Complete example plugin: [`back/plugins/lead_pro`](../../back/plugins/lead_pro) + [`web/src/modules/lead_pro`](../../web/src/modules/lead_pro).

## Workspace

| Path | Crate | What it is |
| --- | --- | --- |
| `back/kernel` | `aphel-kernel` | Platform: `Module`, `AppBuilder`/`App`, `HookBus`, `Services`, record pipeline, field and query engine, events, jobs, authentication, platform HTTP API, core migrations (`back/kernel/migrations`) and the `kernel` module (`KernelModule`) |
| `back/modules/<key>` | `aphel-mod-<key>` | Modules that ship with Aphel (`people`, `deals`, `leads`, `email`, `automations`, `sso`…), each with `src/` and `migrations/` |
| `back/plugins/<key>` | free (e.g. `aphel-lead-pro`) | Local third-party plugins |
| `back/app` | `aphel` | The binary: `main`, CLI (`serve`, `worker`, `migrate`, `modules`…) and the generated registry `src/modules.rs` |
| `back/xtask` | `xtask` | `modules sync`: generates the registries from `aphel.modules.toml` |
| `web/src/modules/<key>` | — | The module's web package (`defineModule`) |

Dependencies between crates follow Cargo: a module depends on `aphel-kernel` and on the modules whose types, services or hooks it uses (`leads = { package = "aphel-mod-leads", path = "../leads" }`, used as `leads::LeadQualifying`). **Cycles are forbidden by Cargo**: when two modules need each other, one of them talks to the other through a hook, a service (`provide`) or a typed contribution (`contribute`). Examples in the code: `timeline` exposes `TimelineEventExtension` and `email` contributes email visibility; the kernel declares `TagOperations`, `StageOperations`, `NoteOperations`… and the owning modules provide the implementation for the automation gateway.

## Choosing what goes into the build

`back/aphel.modules.toml` lists the modules, one per line, in the order in which the web registers them:

```toml
[modules]
people = { path = "modules/people", required = true }
leads = { path = "modules/leads" }
lead_pro = { path = "plugins/lead_pro" }
crm_extra = { git = "https://github.com/acme/aphel-crm-extra", tag = "v1.2.0" }
billing = { version = "0.3", package = "acme-aphel-billing" }
```

| Key | Use |
| --- | --- |
| `path` | Path relative to `back/` |
| `git` + `tag`/`branch`/`rev` | Crate in a git repository |
| `version` | Crate published to a Cargo registry |
| `package` | Package name when it is not `aphel-mod-<key>` (for `path` the xtask reads the `Cargo.toml`) |
| `required` | The module becomes required in this build: always enabled and cannot be disabled or uninstalled (in addition to those already `required` in the manifest) |

The kernel does not appear in the file: it is always compiled.

`make modules` (`cargo run -p xtask -- modules sync`, called by `make build`, `make dev-back` and `make dev-web`) generates:

- `back/app/Cargo.toml`: the `module-<key> = { package = .., path|git|version = .. }` dependencies at the end of `[dependencies]` (the other lines of the file are yours);
- `back/app/src/modules.rs`: `compiled()` with `Box::new(module_<key>::<Type>)` in file order, and `REQUIRED`;
- `web/src/modules.generated.ts`: the web packages, imported through `@modules/<key>`;
- `web/modules.aliases.json` and `web/tsconfig.modules.json`: Vite and TypeScript aliases for web packages that do not live in `web/src/modules/<key>`.

The generated files are committed (the IDE works without running the xtask). `make lint` and CI run `modules sync --check`, which fails if any of them is out of date.

The module type is `<PascalCase of the key>Module` (`line_items` → `LineItemsModule`), unless the crate declares another one:

```toml
[package.metadata.aphel]
module = "LeadPro"
web = "../../../web/src/modules/lead_pro"
```

`web` is the web package directory, relative to the crate. Without it the xtask uses `web/src/modules/<key>` when it exists; with neither, the module has no web part. A web package outside `web/src/modules` gets the `@modules/<key>` alias, but only imports what Aphel's `web/` already installs (`react`, `@tanstack/react-query`, `@/…`); that package's translations are not included in `npm run i18n:types`.

Installing a plugin means adding the line and running `make build`; removing it means deleting the line and running `make build` again. No kernel file is edited.

## Runtime lifecycle

| Moment | What happens |
| --- | --- |
| `aphel migrate` / startup | Applies the core migrations and then those of **all compiled modules**, in load order (dependencies, then alphabetical), recording `module_migrations (module_key, version, checksum)`. `required` modules are enabled automatically; optional modules are selected in the installer or enabled later in settings |
| Enable (`POST /api/v1/modules/{key}/enable`) | Requires enabled dependencies and required settings. Applies the permission grants (`grant_to`) and calls `Module::on_enable` |
| Disable (`/disable`) | The module's routes respond 404 `module_disabled`; hooks, consumers, jobs, widgets, triggers/actions, typed contributions read with `contributions()`, fields contributed to the record type (they disappear from the schema, responses and filters; writes are ignored), services and decorators and the web package disappear. Nothing is deleted |
| Configure (`PUT /settings`) | Validated by the manifest's `SettingField`s and by `Module::validate_settings`; secrets in the `SecretVault` |
| `aphel modules uninstall <key>` | Disables and calls `Module::uninstall` |
| `… --purge` | Exports the `<key>_*` tables (and those declared in `owned_tables`) to `aphel-module-<key>-<date>.json`, deletes their rows (and whatever `Module::purge_data` does), runs the manifest's `uninstall_sql` and forgets the module's migrations, so that they run again if it is reinstalled |

Module migrations are numbered **within the module** (`0001_*.sql`, `0002_*.sql`…). An applied migration never changes (a different checksum prevents startup); fix it with a new one. MySQL does not roll back DDL in a transaction: if a migration fails midway, fix the database by hand before running it again. Name the tables `<key>_*` so they are included in data export and removal.

## From scratch: the `lead_pro` plugin

`lead_pro` extends the Lead concept (a contact with `lifecycle_stage = lead`, `leads` module) without touching `people` or `leads`: interactions warm up the contact, qualification requires a hot lead and conversion carries the temperature over to the deal.

### 1. Crate

`back/plugins/lead_pro/Cargo.toml`:

```toml
[package]
name = "aphel-lead-pro"
version = "1.0.0"
edition.workspace = true
rust-version.workspace = true
license.workspace = true
publish = false

[package.metadata.aphel]
module = "LeadPro"
web = "../../../web/src/modules/lead_pro"

[dependencies]
aphel-kernel.workspace = true
people = { package = "aphel-mod-people", path = "../../modules/people" }
leads = { package = "aphel-mod-leads", path = "../../modules/leads" }
deals = { package = "aphel-mod-deals", path = "../../modules/deals" }
async-trait.workspace = true
serde_json.workspace = true
sqlx.workspace = true
```

A plugin from another repository uses the same crates via `git` (`aphel-kernel = { git = "https://github.com/…/aphel", tag = "v0.1.0" }`) and cannot use `.workspace = true`.

### 2. Migrations

`migrations/0001_lead_pro.sql` creates only plugin-owned tables:

```sql
CREATE TABLE lead_pro_contact_extension (
  record_id CHAR(36) NOT NULL PRIMARY KEY,
  lead_temperature DECIMAL(24,6) NULL,
  KEY lead_pro_temperature_index (lead_temperature)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

CREATE TABLE lead_pro_touches (
  id CHAR(36) NOT NULL PRIMARY KEY,
  contact_id CHAR(36) NOT NULL,
  kind VARCHAR(64) NOT NULL,
  event_id CHAR(36) NULL,
  created_at DATETIME(6) NOT NULL,
  UNIQUE KEY uq_lead_pro_touches_event (event_id),
  KEY idx_lead_pro_touches_contact (contact_id, created_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
```

The extension is keyed by the parent record without altering its table. The host joins its contributed columns. Migration 2 copies temperature values on upgrades; migration 1 accepts only its explicitly recorded historical checksum. Historical physical columns remain unused. Purge drops only the plugin's own tables.

### 3. Manifest and registration

```rust
pub struct LeadPro;

impl Module for LeadPro {
    fn manifest(&self) -> Manifest {
        Manifest::new("lead_pro", "Lead Pro", env!("CARGO_PKG_VERSION"))
            .requires_aphel("0.1.0")
            .depends_on(people::KEY, "*")
            .depends_on(leads::KEY, "*")
            .depends_on(deals::KEY, "*")
            .migration(Migration::new(1, "lead temperature and touches", include_str!("../migrations/0001_lead_pro.sql")))
            .uninstall_sql(include_str!("../migrations/uninstall.sql"))
            .setting(SettingField::new("hot_threshold", "Temperatura de lead quente", SettingKind::Number { min: Some(0), max: Some(100) }).default_value(json!(70)))
    }

    fn register(&self, app: &mut AppBuilder) -> Result<(), AppError> {
        app.permission(PermissionDefinition::administrative(READ)).grant_to(["admin", "manager", "member"]);
        let field = SystemField::new("lead_temperature", "Temperatura do lead", FieldType::Number, "lead_temperature")?;
        app.extend("people.person", |contact| {
            contact.side_table("lead_pro_contact_extension", "record_id").system_field(field);
        });
        app.filter(RecordSaving, 20, |ctx, saving| Box::pin(hooks::default_temperature(ctx, saving)))
            .on(RecordValidating, 15, |ctx, changed| Box::pin(hooks::validate_temperature(ctx, changed)))
            .on(LeadQualifying, 10, |ctx, lead| Box::pin(hooks::require_temperature(ctx, lead)))
            .filter(LeadConverting, 10, |ctx, conversion| Box::pin(hooks::enrich_deal_values(ctx, conversion)));
        app.decorate::<dyn LeadConverter, _>(|inner| Arc::new(converter::WithTouches(inner)))?;
        app.worker(|env| {
            WorkerParts::default()
                .consumer(Arc::new(TouchConsumer::new(env.pool.clone(), env.record_types.clone())))
                .handler(Arc::new(Cooldown::new(env.pool.clone())))
                .schedule(cooldown_schedule())
        });
        app.public_event(event("lead_pro.temperature_changed", people::CONTACT_RESOURCE, "…"));
        app.notification_kind(NotificationKindDefinition::new(LEAD_HOT))
            .openapi_tag("lead_pro", "…")
            .routes(|_| http::router());
        Ok(())
    }
}
```

What each piece does:

| Piece | Effect |
| --- | --- |
| `extend` + `side_table` + `SystemField` | `lead_temperature` becomes a contributed system field: read and written by the kernel, it appears in the API, on the detail page, in columns, filters and sorting, in import/export and in automations |
| `filter::<RecordSaving>` | Fills in the initial temperature when a contact is created |
| `on(RecordValidating, ..)` | Rejects a temperature outside 0–100 (422 with the field) |
| `on(leads::LeadQualifying, ..)` | Veto: qualifying a cold lead responds 422 `lead_not_hot_enough` |
| `filter::<leads::LeadConverting>` | Enriches the values of the deal created on conversion (`source`) |
| `decorate::<dyn leads::LeadConverter>` | Wraps the original converter to record a `lead.converted` touch (shows up in `aphel modules doctor`) |
| `consumer` | `activity.created`, `note.created`, `email.*`, `meeting.booked` events of a contact warm up the lead; when it crosses the threshold, it notifies the owner |
| `schedule` + `handler` | Daily cooldown (`lead_pro.cooldown`, 3 AM) |
| `public_event` | `lead_pro.temperature_changed` available to webhooks and integrations |
| `notification_kind` | `lead_pro_hot` in the notification preferences |
| `routes` | `GET /api/v1/lead-pro/board`, `GET /api/v1/lead-pro/people/{id}` and `POST …/touches`, with OpenAPI |

A hook runs inside the transaction of whoever triggers it (`ctx.tx()`), with the scope of whoever acts (`ctx.scope`) and access to `ctx.pool` and `ctx.services`. A veto returns `Err(AppError::..)`; a filter returns the changed value. To declare hooks of your own module, create the type (`pub struct MyHook; impl Hook for MyHook { type Args = .. }`), fire it with `ctx.run_hook::<MyHook>(..)`/`ctx.apply_hook::<MyHook>(..)` and declare it with `app.declare_hook(MyHook, &[HookUsage::Veto], "when it runs")` so it enters the catalog.

### 4. Kernel extension points

Besides what is above, `AppBuilder` accepts:

| Method | For |
| --- | --- |
| `record_type`, `extend(..).managed_field(..)` | New record type; custom field managed by code (no migration) |
| `EntityDefinition::capabilities(EntityTraits::default().automatable().validation_rules()..)` | What the type supports (automations, validation rules, import, export, bulk actions, privacy, notifications…; table in [`record-pipeline.md`](../architecture/record-pipeline.md#declared-capabilities)); declared `belongs_to` relations also define the embedded objects redacted by field permissions |
| `provide::<dyn T>` / `decorate::<dyn T>` | Swappable service read with `ctx.services`/`app.services().get::<dyn T>()` |
| `contribute::<T>` | Typed contribution; readers use `App::contributions::<T>()` (enabled modules only) or `all_contributions` |
| `widget`, `trigger`/`action` | Dashboard widget, automation trigger and action |
| `job`, `consumer`, `schedule`, `worker` | Background work |
| `routes`, `public_routes`, `root_routes` | Mount the module's routes (see [Routes: `routes` × `public_routes` × `root_routes`](#routes-routes--public_routes--root_routes)) |

#### Routes: `routes` × `public_routes` × `root_routes`

| Method | Prefix | Use |
| --- | --- | --- |
| `routes` | `/api/v1` | The module's authenticated routes. Authentication comes from the handler's extractor (`AuthContext`, or `SessionContext` for browser-only routes), not from the mounting method |
| `public_routes` | `/api/v1` (the same as `routes`) | Routes without login (forms, public links, provider webhooks, OAuth callbacks). Mounting is identical to `routes`: the difference is declarative (it appears as `public` in `aphel modules doctor`) |
| `root_routes` | none (server root) | Routes outside `/api`, such as `/health` and `/metrics`. They are not under `/api/v1` nor behind Vite's `/api` proxy |

Points that apply to all three:

- All of them go through the `ModuleGate`: with the module disabled they respond 404 `module_disabled` (`required` modules have no gate).
- None of them authenticates anything on its own: a public route is one that does **not** use `AuthContext`/`SessionContext`. A `public_routes` handler that extracts `AuthContext` still requires a session or token.
- The CSRF header exemption (`X-Requested-With: aphel`) depends only on the path, not on the mounting method: everything under `/api/v1/public/` (public module routes at `/api/v1/public/<key>/…`) and `/api/v1/hooks/…`. A public route that receives `POST` from outside Aphel's browser client lives under one of these paths.
- Every public route must apply its own rate limit (`SharedRateLimiter`, below).

#### Rate limiting

`aphel_kernel::api::rate_limit::SharedRateLimiter::new("<key>.<use>", limit, window)` counts in a sliding window shared by all processes (table `rate_limit_counters`); `check(key, message).await` responds 429 `rate_limited` with `Retry-After`, and `hit(key).await` returns the `WindowDecision` for those who want to build `X-RateLimit-*` headers. The scope (first argument) separates the counters of different limits that use the same key (for example the IP). `SlidingWindowLimiter` is still available, but it only counts within the current process: with several `serve` processes the effective limit multiplies. Details and cost in [Configuration](../configuration.md#request-limits).

#### Module tables and data

The `<key>_*` tables belong to the module automatically. Tables with another name (modules that came from the core, such as `export_jobs`, `import_jobs`, `webhook_deliveries`) are declared in the manifest with `Manifest::owned_tables(&["export_jobs"])`. `aphel modules uninstall <key> --purge` exports and deletes the rows of the prefixed tables **and** of the declared ones before running `uninstall.sql`.

Two typed contributions describe data that the kernel and the `privacy` module need to know about without depending on the module:

| Contribution | Declares | Who reads it |
| --- | --- | --- |
| `dyn aphel_kernel::application::files::FileReferenceSource` | Columns (`FileReferenceColumn { table, column }`) that store a `files` id. The platform ones (`attachments.file_id`, `organization_settings.logo_file_id`, `users.avatar_file_id`, `installed_modules.data_export_file_id`) are already included via `declared_file_columns` | Orphan file purge and `privacy` attachment removal: a file referenced by any declared column is never deleted. A module that stores a `file_id` and does not declare the column loses the file under the `purge_orphan_files` policy |
| `dyn aphel_kernel::application::security::PersonalTextSource` | Free-text or JSON columns (`PersonalTextColumn { table, column }`) that may contain personal data copied from records (webhook bodies, headers, logs). The table must have a text primary key `id`. The platform ones (`domain_events.payload`, `audit_logs.changes`) are already included via `declared_personal_text_columns` | Data subject anonymization and erasure in `privacy` (replaces the data subject's values in these columns) |

Both are read with `all_contributions` (including from disabled modules, because the data is still in the database) and columns of tables that do not exist are ignored. Example:

```rust
app.contribute::<dyn FileReferenceSource>(Arc::new(ExportFileReferences));
app.contribute::<dyn PersonalTextSource>(Arc::new(WebhookPersonalText));
```

Typed contributions the kernel already reads:

| Type | Use |
| --- | --- |
| `ConfigSectionFactory` | Configuration package section, with application order (`aphel_kernel::infrastructure::config_packages`) |
| `dyn ConfigSection<MySqlTx>` | Section without a factory (applied after the ordered ones) |
| `DefaultsSeed` | Default data written at installation |
| `dyn FileReferenceSource` | Columns that reference files (above) |
| `dyn PersonalTextSource` | Text columns with personal data (above) |
| `TimeTriggerPlanner` | Plan of an automation time trigger |
| `dyn ModuleCommand` | CLI subcommand (`aphel demo`, `aphel org`) |
| `dyn LoginProvider`, `dyn email::MailboxProvider`, `dyn aphel_sdk::calendar::CalendarAvailability`, `dyn telephony::telephony::TelephonyProvider`, `dyn timeline::domain::TimelineEventExtension` | Login providers, email mailboxes, calendar, telephony and timeline events |

`Services::get` returns the topmost layer of the provider → decorators chain whose modules are all enabled: disabling a decorator also turns off those that came after it; with the provider disabled, the previous replaced provider (if any) applies. Services that modules provide and a plugin can decorate: `leads::LeadConverter`, `deals::AmountCalculator`, `money::CurrencyConverter`, `people` `dyn DuplicateDetector`, `approvals::ApprovalGate`, `aphel_sdk::pricing::{PriceListResolver, DiscountLimits, BundleExpander}`, `telephony::TelephonyRouter`, `email::Sender` and the automation operations (`TagOperations`, `StageOperations`, `NoteOperations`, `ActivityTypeOperations`, `TaskOperations`, `IncomingWebhookOperations`). The build's list is shown by `aphel modules doctor`.

### 5. Web package

`web/src/modules/lead_pro/index.ts` registers a menu item, the `/lead-pro` route, a tab on the contact, a button in the record header (slot), a renderer for the `lead_temperature` field and a palette command, and adds the notification label to the `notifications` namespace. Details in [web.md](web.md).

### 6. Add, test and remove

```bash
echo 'lead_pro = { path = "plugins/lead_pro" }' >> back/aphel.modules.toml
make build            # or make modules && make dev-back
aphel migrate         # applies 0001_lead_pro.sql
aphel modules doctor  # routes, hooks, decorator, consumer, schedule
aphel catalog         # plugins, operations, hooks (with listeners), events, permissions
```

To turn it off in an installation, disable it in Integrations › Modules (`/integrations/modules`; routes return 404, and the menu, tab and hooks disappear). To remove it from the database: `aphel modules uninstall lead_pro --purge` (exports the touches, drops the table and the column). To remove it from the binary: delete the line and run `make build` again.

## Conventions

- Module key: lowercase letters, digits and `_`; it becomes the web i18n namespace and the permission prefix (`<key>.<action>`).
- Tables `<key>_*`; a table with another name goes into `Manifest::owned_tables`; columns in other modules' tables only through the module's own migration, with `uninstall.sql`.
- A column that stores a file id is declared with `FileReferenceSource`; free text that may contain personal data, with `PersonalTextSource`.
- Plugin routes at `/api/v1/<key>/…` (public ones at `/api/v1/public/<key>/…`; a key with `_` becomes `-`, as in `/api/v1/lead-pro`), jobs `<key>.…` and web at `/<key>` (`/lead-pro`).
- Events `<resource>.<action>`; whoever publishes `<type>.created|updated|deleted` with `changes` joins the generic automation triggers and the search.
- No explanatory comments in the code, names in English and UI texts via i18n (repository rules).

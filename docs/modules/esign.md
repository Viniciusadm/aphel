# "Electronic signature" module (`esign`)

Sends PDFs attached to a **deal** (for example, the proposals generated by the [Proposals](proposals.md) module) for electronic signature in **Clicksign** and tracks the status of each signer through webhooks. Code in `back/modules/esign` (crate `aphel-mod-esign`, struct `EsignModule`; `deals` and `activities` optional) and `web/src/modules/esign`. It does not depend on the Proposals module: it only uses the kernel's file and attachment use cases.

> **No legal validity of its own.** Aphel only sends the document and records its progress. The validity of the signature (evidence, timestamp, audit trail) is the provider's (Clicksign). The screen and the API say this explicitly.

## For users

1. In Clicksign, generate an **API access token** (sandbox or production).
2. **Settings → Integrations → Modules → Electronic signature → Configure**: environment, access token and webhook HMAC secret (both secrets are required to enable it). Enable it.
3. The module panel shows the **webhook address** (`https://<aphel>/api/v1/public/esign/webhook`). Register it in Clicksign and copy the webhook's **HMAC SHA256 key** into "Webhook HMAC secret".
4. Grant the permissions to the roles: **Send and cancel signature requests** (`esign.send`) and **View signature requests** (`esign.view`).
5. On the deal, **Signatures** tab → **Send for signature**: choose a PDF attached to the deal, add the signers (the deal's contact appears as a suggestion; you can also type a name and email) and, optionally, a message. Each signer receives the invitation by email and authenticates with a code sent to the email.
6. The tab lists the requests with the status of each signer, the original PDF, the signed PDF (when attached) and the **Cancel** button while it is waiting. The deal's timeline shows the events.

## Settings

| Key | Type | Default | Use |
| --- | --- | --- | --- |
| `environment` | Select (`sandbox`, `production`) | `sandbox` | `https://sandbox.clicksign.com` or `https://app.clicksign.com` |
| `access_token` | Secret, required | | Clicksign API token (`Authorization` header) |
| `webhook_secret` | Secret, required | | Webhook HMAC SHA256 key (`Content-Hmac` header) |
| `attach_signed_document` | Boolean | `true` | When completed, downloads the signed PDF and attaches it to the deal |

The secrets are stored encrypted in the `SecretVault` (`module_secret_key("esign", ..)`: `owner_type = "module"`, `owner_id = "esign"`) and are never returned by the API (`GET /status` only says whether the token is configured), nor do they appear in logs, events or audit.

## Permissions

| Permission | What it allows |
| --- | --- |
| `esign.send` | Sending and cancelling requests (also requires `deals.read` and access to the file) |
| `esign.view` | Viewing the deal's requests and their status |

## Events and triggers

All with `record = deal` and offered as automation triggers ("Document sent for signature", "Document signed by a signer", "Signature refused", "Signature cancelled", "Signature completed", "Signature expired"). Each one writes audit in the same transaction.

| Event | When | Payload |
| --- | --- | --- |
| `esign.sent` | Request created in Clicksign | `request_id`, `deal_id`, `file_id`, `file_name`, `provider`, `status`, `signers` (name and status), `environment` |
| `esign.signed` | A signer signed | same + `signer_name`, `provider_event`, `source` |
| `esign.refused` | A signer refused (the request becomes `refused`) | same |
| `esign.cancelled` | Cancelled from the UI (`source = user`) or in Clicksign (`source = provider`) | same |
| `esign.completed` | Document finalized (all signatures) | same |
| `esign.expired` | Deadline reached | same |
| `esign.signed_file_attached` | Signed PDF attached to the deal | same + `signed_file_id`, `signed_file_name` |

Signers' emails do not go into the events (only the names).

## Routes

Authenticated (`/api/v1/esign`):

| Method | Path | Permission | What it does |
| --- | --- | --- | --- |
| `GET` | `/status` | `esign.view` or `esign.send` | Provider, environment, `configured`, webhook address and legal notice |
| `GET` | `/requests?deal_id=` | `esign.view`/`esign.send` + `deals.read` | The deal's requests (up to 100, most recent first) with signers |
| `POST` | `/requests` | `esign.send` + `deals.read` | `{ deal_id, file_id, signers: [{ name, email, contact_id? }], message? }` → 201 |
| `GET` | `/requests/{id}` | `esign.view`/`esign.send` + `deals.read` | A single request |
| `POST` | `/requests/{id}/cancel` | `esign.send` + `deals.read` | Cancels in Clicksign and publishes `esign.cancelled` |

Public (`/api/v1/public/esign`, no session):

| Method | Path | What it does |
| --- | --- | --- |
| `POST` | `/webhook` | Receives Clicksign's webhooks. Responds `{ data: { status: "applied" \| "ignored" \| "duplicate" } }` |

Webhook rules: limit of 600 requests per minute (`rate_limited`), module enabled (404 `module_disabled`), body up to 512 KB, signature `Content-Hmac: sha256=<hex>` = HMAC-SHA256 of the **raw body** with the configured secret, compared in constant time before anything is read (401 `invalid_webhook_signature`; the secret is read from the `SecretVault` with `module_secret_key`, without a user). The URL contains nothing secret: what protects it is the HMAC. The request is located by the Clicksign envelope or document id; unknown envelopes respond `ignored` without touching anything. Idempotency by the SHA-256 hash of the body (`esign_webhook_receipts`): repeats respond `duplicate`. Changes are made with the scope of whoever sent the request (or, if they were deactivated, of another recent sender who is still active).

When completed, with `attach_signed_document` on, the `esign.attach_signed` job (idempotent, up to 5 attempts) downloads the signed PDF and attaches it to the deal through the kernel's file upload use case (`FileUseCases::upload`).

### Error codes

| Code | HTTP | When |
| --- | --- | --- |
| `esign_invalid_request` | 422 | Invalid data (signers: 1 to 20, name, valid email and no repeats; message up to 1000 characters) |
| `esign_file_not_attached` | 422 | The file is not attached to the deal |
| `esign_file_not_pdf` | 422 | The file is not a PDF |
| `esign_file_too_large` | 422 | PDF larger than 20 MB |
| `esign_provider_rejected` | 422 | Clicksign refused it (provider detail in the message) |
| `esign_request_not_found` | 404 | Request does not exist |
| `deal_not_found` | 404 | Deal does not exist or is not visible |
| `esign_request_closed` | 409 | Cancelling a request that is already closed |
| `esign_not_configured` | 503 | Access token not configured |
| `esign_provider_unauthorized` | 503 | Clicksign refused the token |
| `esign_provider_unavailable` | 503 | Clicksign is down, slow (30 s timeout) or rate limiting |
| `invalid_webhook_signature` | 401 | `Content-Hmac` missing or wrong |
| `esign_invalid_webhook_payload` / `esign_webhook_payload_too_large` | 422 | Non-JSON body or larger than 512 KB |
| `esign_webhook_not_configured` | 503 | HMAC secret not configured |
| `esign_owner_unavailable` | 503 | No active member can act on behalf of the request |

## Data sent to third parties

To Clicksign: the chosen PDF, the envelope name (deal title + file name), the name and email of each signer and the optional message. Nothing else from the CRM is sent.

## Tables

`esign_requests`, `esign_signers` and `esign_webhook_receipts` (the module's migration 1). **Export data** brings all the rows (plus an `export_data` summary); **Remove data** deletes the rows of the three tables and the secrets.

## Clicksign adapter and limitations

The provider sits behind the `SignatureProvider` trait (`send`, `cancel`, `signed_document`); Clicksign is the only implementation (`src/clicksign.rs`, API v3 "envelopes", JSON:API, `Content-Type: application/vnd.api+json`, token in the `Authorization` header):

1. `POST /api/v3/envelopes` (`locale: pt-BR`, `auto_close`, `remind_interval: 3`, `block_after_refusal`).
2. `POST /envelopes/{id}/documents` with `content_base64` (`data:application/pdf;base64,...`).
3. For each signer: `POST /envelopes/{id}/signers` (communication by email) and two `POST /envelopes/{id}/requirements`: qualification `{ action: "agree", role: "sign" }` and authentication `{ action: "provide_evidence", auth: "email" }`.
4. `PATCH /envelopes/{id}` with `status: "running"` and `POST /envelopes/{id}/notifications`.
5. If any step fails, the draft envelope is deleted (`DELETE /envelopes/{id}`, best effort).

Points that have not been confirmed against Clicksign's official documentation (isolated in the adapter; adjust there if the provider differs):

- Cancellation via `PATCH /envelopes/{id}` with `status: "canceled"`.
- Download of the signed document at `GET /envelopes/{id}/documents/{doc}` → `data.links.files.signed` (temporary URL downloaded without the token).
- Webhook format: the event comes in `event.name` (`sign`, `refusal`, `close`/`auto_close`/`document_closed`, `cancel`, `deadline`), the signer in `event.data.signer.email`, and the envelope/document in `envelope.id|key`, `document.key|id` or `document.envelope_key`. Other events are recorded and ignored.
- `Content-Hmac: sha256=<hex>` header.

Other limitations: a single provider (Clicksign); one document per request; signers only with email authentication; no configurable deadline; the PDF must be attached to the deal.

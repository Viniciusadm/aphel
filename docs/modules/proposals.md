# Proposals module (`proposals`)

Generates PDF proposals from **document templates** with variables from the deal, the contact, the company and the items table. The PDF is attached to the deal and the `proposal.generated` event can trigger automations. It is a regular module (former extension, session 35) that follows the [module guide](README.md): it depends only on `aphel-kernel` and, as optional dependencies, on `deals` and `activities`.

| Piece | Where it lives |
| --- | --- |
| Backend | `back/modules/proposals` (crate `aphel-mod-proposals`, struct `ProposalsModule`, in the default build via `back/aphel.modules.toml`) |
| Frontend | `web/src/modules/proposals` (i18n namespace `proposals`) |
| Tables | `proposals_templates`, `proposals_documents`, `proposals_counters` |

## Usage

1. In **Settings → Integrations → Modules**, enable **Proposals**. When it is enabled for the first time, the installation receives the starter template **Proposta comercial** (key `proposta_comercial`, default).
2. Grant the permissions to the roles (admin already has all of them):
   - `proposals.manage` — manage templates (**Proposals** menu).
   - `proposals.generate` — view and generate proposals (the deal's **Proposals** tab). Generating also requires `deals.update` on the deal, because the PDF becomes one of its attachments.
3. In **Proposals** (`/proposals`), create or edit templates. The editor has the **Insert variable** menu, template checking as you type (with the line and column of each problem) and a preview with the data of a chosen deal.
4. On the deal, **Proposals** tab → **Generate proposal**: choose the template (the default one comes selected), preview it if you want and generate the PDF. The proposal receives a sequential number and appears in the tab's list and in the deal's attachments.

Disabling the module hides the menu and the tab and returns 404 `module_disabled` on the routes; templates and generated proposals remain in the database and come back when the module is enabled again.

## Template format

Plain text, line by line:

| Syntax | Result |
| --- | --- |
| `# Title`, `## Subtitle`, `### Section` | Headings (levels 1 to 3) |
| consecutive lines | Paragraph; every line break is kept. A blank line separates paragraphs |
| `- item` or `* item` | Bulleted list |
| `**text**` | Bold (may contain variables) |
| `---` alone on the line | Horizontal rule |
| `{{items_table}}` alone on the line | Items table: item, quantity, unit price, discount, total; then subtotal, discounts and grand total |
| `{{page_break}}` alone on the line | Page break |
| `\*`, `\{`, `\}`, `\\` | The literal character |

There is no HTML and no scripts: the content is always text, which makes the format safe for any user with `proposals.manage`.

### Variables

`{{group.field}}` (spaces inside the braces are ignored). Values come from the core API with the scope of whoever generates the proposal: fields hidden by the role's field permissions are empty.

| Variable | Value |
| --- | --- |
| `{{deal.title}}`, `{{deal.amount}}` | Deal title and amount (`R$ 1.234,56`) |
| `{{deal.<field>}}` | Any deal field, including custom ones (`deal.status`, `deal.expected_close_date`, `deal.stage_id` → stage name, `deal.owner_id` → owner name, `deal.cf_prazo`, …) |
| `{{contact.name}}`, `{{contact.<field>}}` | The deal's contact |
| `{{company.name}}`, `{{company.<field>}}` | The deal's company (or the contact's) |
| `{{owner.name}}` | The deal's owner |
| `{{user.name}}`, `{{user.email}}` | Whoever generated the proposal (in automations, whoever published the automation) |
| `{{organization.name}}` | Organization name |
| `{{proposal.number}}`, `{{proposal.template}}` | Proposal number (`0012`) and template name |
| `{{today}}` | Today's date in the organization's time zone (`21/10/2026`) |
| `{{items.count}}`, `{{items.subtotal}}`, `{{items.discount_total}}`, `{{items.total}}` | Item totals |

pt-BR formatting: currency with symbol (`R$`, `US$`, `€`, `£` or the ISO code), numbers with a decimal comma, dates as `dd/mm/yyyy`, date-time in the organization's time zone, checkboxes as Sim/Não (Yes/No), multiple choice separated by commas. Custom select fields show the stored value.

### Validation

On save, the body is validated against the variable catalog. Problems return 422 `proposal_template_invalid` with `details.fields[] = { field: "body", message: "line 3, column 5: unknown_variable {{deal.foo}}" }`. Problem codes:

| Code | When |
| --- | --- |
| `unknown_variable` | Variable not in the catalog (`GET /variables`) |
| `invalid_variable` | Name with invalid characters (use lowercase letters, digits, `_` and `.`) |
| `empty_variable` | `{{ }}` |
| `unclosed_variable` | `{{` without `}}` on the same line |
| `block_variable_inline` | `items_table` or `page_break` in the middle of a line |

Variables that stop existing later (a deleted custom field) do not prevent generation: they come out empty.

## PDF

Generated by an in-house PDF writer (no external dependencies or binaries), A4, standard Helvetica/Helvetica-Bold fonts with WinAnsi encoding (Portuguese accents, `€`, dashes and typographic quotes; characters outside WinAnsi become `?`). A header on every page with the organization name, "Proposal no. 0001" and the date; a "Page X of Y" footer; automatic line and page breaks; the items table repeats its header when it moves to a new page.

The file (`proposta-0001-<deal-title>.pdf`) is stored by the file core (`FileStorage`) and attached to the deal; downloads always go through the authenticated endpoint `GET /api/v1/files/{file_id}`.

## Events, audit and automations

| Event | Record | Payload |
| --- | --- | --- |
| `proposal.generated` | the deal | `document_id`, `deal_id`, `number`, `template_id`, `template_key`, `template_name`, `file_id`, `file_name` |
| `proposal_template.created` / `.updated` / `.deleted` | — | `template_id`, `key`, `name`, `is_active`, `is_default` |

Every mutation publishes the event and writes the audit entry (`proposal.generated`, `proposal_template.*`) in the same transaction.

- **Trigger** "Proposal generated" (`proposal.generated`, deal records).
- **Action** "Generate proposal" (`proposals.generate_proposal`, deals): configuration `{ "template_key": "proposta_comercial" }` (empty uses the default template). Requires `proposals.generate` and `deals.update` from whoever published the automation; it is not safe to retry (each run generates a new proposal). The step result carries `document_id`, `number`, `file_id`, `file_name` and `template_name`.

## Configuration packages

Section `proposals.templates`, referenced by the template's stable key:

```json
{
  "templates": [
    {
      "key": "proposta_comercial",
      "name": "Proposta comercial",
      "description": null,
      "body": "# Proposta\n\n{{items_table}}\n",
      "is_active": true,
      "is_default": true
    }
  ]
}
```

The plan creates the templates that do not exist and updates the ones that changed; installing never deletes templates or touches generated proposals. Validation applies the same rules as the editor (unknown variables, invalid or repeated key, more than one default).

## API

All under `/api/v1/proposals`, with a session or an API token (`proposals` tag in OpenAPI). Items respond `{ data }`; lists respond `{ data: [...] }`.

| Method and route | Permission | Description |
| --- | --- | --- |
| `GET /variables` | `manage` or `generate` | Variable catalog: `key`, `label`, `group`, `field_type`, `block` |
| `GET /templates` | `manage` or `generate` | Templates (only active ones for users with just `generate`), default first |
| `POST /templates` | `manage` | Creates. Body: `key?`, `name`, `description?`, `body`, `is_active?` (default `true`), `is_default?`. 201 |
| `POST /templates/validate` | `manage` | `{ body }` → `{ valid, issues: [{ line, column, code, variable }] }` |
| `GET /templates/{id}` | `manage` or `generate` | A single template |
| `PATCH /templates/{id}` | `manage` | Partial update (`name`, `description`, `body`, `is_active`, `is_default`); the key is immutable |
| `DELETE /templates/{id}` | `manage` | Deletes; proposals already generated keep the PDF and the template name. 204 |
| `POST /preview` | `manage` (with `body`) or `manage`/`generate` (with `template_id`); `deals.read` with `deal_id` | Renders without generating a PDF: `{ blocks, issues, sample }`. Without `deal_id`, record variables show up as `[deal.title]` |
| `GET /deals/{deal_id}/documents` | `generate` + `deals.read` | Proposals generated for the deal, most recent first |
| `POST /deals/{deal_id}/documents` | `generate` + `deals.update` | `{ template_id? }` (default: the active default template). Generates, attaches and publishes `proposal.generated`. 201 |

Preview blocks (`type`): `heading { level, spans }`, `paragraph { lines }`, `list { items }`, `items_table { table }`, `page_break`, `rule`; `spans` are `{ text, bold, variable }`.

### Error codes

| Code | Status | When |
| --- | --- | --- |
| `permission_denied` | 403 | Missing `proposals.manage`, `proposals.generate`, `deals.read` or `deals.update` |
| `module_disabled` | 404 | Module disabled |
| `proposal_template_not_found` | 404 | Template does not exist (or is inactive, for users with only `generate`) |
| `deal_not_found` | 404 | Deal does not exist or is outside the user's visibility |
| `proposal_template_invalid` | 422 | Invalid fields or problems in the body (with line and column) |
| `proposal_template_required` | 422 | No `template_id` and there is no active template |
| `proposal_template_inactive` | 422 | The chosen template is inactive |
| `proposal_invalid_request` | 422 | Malformed id or preview without `body` or `template_id` |
| `proposal_template_key_taken` | 409 | Key already used by another template |
| `invalid_json` | 422 | Invalid request body |

File core errors when attaching (for example `file_too_large`) are passed through with the same code.

## Data

- `proposals_templates`: templates (unique `template_key`, exclusive `is_default`).
- `proposals_documents`: generated proposals (deal, template and template name, number, file, who generated it and actor type, date). The number is unique.
- `proposals_counters`: single row (`id = 1`) with the last number. The number is reserved before the PDF is generated, so a failure midway can leave a number without a proposal.

All of them are included in the module's data export and removal.

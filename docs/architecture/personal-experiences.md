# Personal experience preferences

The account settings contribution **My experience** at `/account/experience` uses the existing preferences and organization catalog query keys. It has no administrative permission requirement beyond the authenticated application shell. It does not install, enable or admit code, and never PUTs organization configuration.

The profile selector offers enabled, organization-permitted profiles and the option to follow the organization default. Disabled/disallowed entries and a retained missing selection are shown as unavailable. Blocked selection has an explanation and still offers its separate reset. Changes PATCH only `experience.profile`; the server returns current stored/effective preferences and the shared cache updates. The host keeps the existing default/baseline fallback and provider diagnostics. Choosing a profile is not proof that all its providers are available.

Section controls affect only the selected profile's existing record-detail main region. Move-up/down builds a source-priority order; hiding remains independent of ordering. No renderer is mounted to discover availability. A read-only `experience_omittable_sections` field on the existing preference response projects the intersection of the effective profile sources, organization omission allowlist and active owner declarations already used by the write validator. This avoids hardcoded module exceptions or another optionality registry. It is not record authorization or a guarantee of context visibility. The backend still revalidates every PATCH under its existing organization/user row locks.

The section editor starts from policy-filtered effective values, while stored incompatible choices remain untouched until an explicit replacement/reset. Policy-blocked ordering and omissions are disabled with a reason; owner-mandatory/inactive sources cannot be hidden. Local edits retain their original profile/policy/source signature. A changed signature blocks saving until the user discards the local draft or resets the saved surface. Error responses preserve unsaved values and refresh the existing catalog/preferences queries. Successful mutations also refresh the catalog so the screen does not continue assuming an old policy after a successful reset. There is no push or immediate cross-tab revocation guarantee; server checks remain authoritative.

Separate resets use `experience.profile: null` and `experience.record_detail: null`. The latter clears the single saved record surface, including an adjustment retained for a different previous profile. Neither reset changes organization state, navigation, locale, shortcuts, saved views or dashboard layout. Selection changes do not clear the record adjustment. The existing Navigation and language page now disables home/menu edits under a blocking organization policy and offers a distinct `navigation: {}` reset, without resetting language or shortcuts. Views and dashboard widgets continue in their own existing editors.

Native selects, labelled checkboxes, accessible move-button names, loading/offline/error states and the existing unsaved-changes guard support the small interaction. No temporary instance, per-commit test suite or real installation was used. Compilation, probe and build are distinct from still-pending HTTP persistence/reload, tampered request, policy-revocation concurrency, keyboard/focus/mobile and surface-isolation verification.

# Organization experience administration

The existing organization settings area contributes **Experiences** at `/settings/experiences`. Both the menu contribution and the page require `settings.manage`; the page's permission boundary mounts its query/editor only for permitted users. The backend's existing PUT and validation route retain their independent permission checks. This page does not provide personal selection or the personal editor planned for the next step.

## Draft and review

The page reads the existing `['organization', 'experiences']` query. Opening it does not persist a catalog when the organization has none. A local draft starts from the saved configuration; no auto-save or new browser storage is used.

Administrators can add or edit a version-1 profile with an immutable namespaced key, label, record type and existing frame/presentation providers. The choices come from the existing contribution system and record resources, retaining saved missing provider/type references. Alternative presentations can receive an ordered list of published module/key section sources through ordinary inputs and move-up/remove controls. This is reference configuration, not an executable UI language or a field-layout editor. Source eligibility is not inferred by mounting components.

Enablement, the permitted profile list, shared default, personal selection/navigation/order flags and the section-omission allowlist use the existing organization aggregate. Disabling, removing or disallowing a profile cleans dangling default/allowlist references in the local draft; omission references remain only if another enabled permitted profile still supplies them. Removing a source from the draft composition updates that draft's omission references. Missing providers alone never erase references. The page explains that owner-reviewed optionality is also required: an administrator's allowlist cannot hide required content or grant data access.

Import accepts a JSON file up to 512 KiB and sends its untrusted parsed value to the existing server validator. Future versions, malformed/unknown properties or invalid relationships are rejected by the server before the current draft changes. A valid import replaces the whole draft catalog/default/policy. It never installs a package or modifies a saved value until application is explicitly requested. Users are warned about replacement and can compare the saved aggregate with the proposal.

Every save requires a successful `POST /api/v1/organization/experiences/validate` result. Review shows added/changed/removed profiles, before/after provider and ordered source references, shared-default changes and policy differences. Any subsequent draft change clears the review. The apply button submits the reviewed server-returned configuration with the original saved `updated_at` in `If-Match`. The preview's timestamp is not adopted to overwrite an unseen concurrent change. If the current query or preview version differs, application is blocked until the administrator explicitly reloads/discards the local draft and reviews again. A 409 retains the draft and shows a conflict rather than success.

Successful PUT updates the shared organization query and invalidates the existing preferences query to refresh its effective policy projection. No personal preference write occurs. Validation, network and write failures show an error, including server field paths when available; only a successful PUT shows a saved notification. Background query updates do not silently reset local edits. Reload/discard is explicit, and the existing unsaved-changes guard protects navigation away from a draft or open profile form.

## Preview and ownership

Availability review only inspects active registered contributions and the existing presentation compatibility metadata. It never renders provider code or calls record-specific visibility hooks. A matching frame must have exactly one active provider; a nonstandard presentation also needs its declared record type and main-region support. Record resources and source owners are shown along with unavailable/ambiguous/incompatible states. Backend reports remain visible.

This structural preview is not proof of an authorized record journey. Section visibility, filters, record permissions, data and runtime rendering still need verification on an actual authorized record. The page does not claim that a readable fallback fulfills an unavailable experience. It allows dormant references to be saved after an explicit review, matching the existing API and host resolution contract.

Changes are organization-owned and can affect all members. Default changes and withdrawal/fallback implications are stated explicitly. Personal raw selections/adjustments remain stored; the host and server project them under the new policy. Views, dashboards, themes, field layouts, locale, shortcuts, business rules and automations retain their existing owners. No editor for these resources is duplicated. Executable provider admission stays in the existing Modules management flow and requires `system.manage`; the experience page never supplies frontend-code consent or triggers install/enable.

The page uses native selects, labelled controls, ordinary buttons for ordering, existing dialog focus/scroll behavior, status/error announcements and loading/offline states. No new test suite or scratch instance was created. Compilation/lint/build verify integration, but browser keyboard/focus/mobile behavior and real HTTP authorization/concurrency/persistence remain pending under the project's validation restrictions.

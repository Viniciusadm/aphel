# Frontend modules

The web app is assembled by the modules (session 32). There are no central lists of routes, menu, settings or translations: each module declares what it contributes, and the kernel gathers it, filters it by what is enabled in the installation and hands it to the generic building blocks.

- Kernel: [`web/src/kernel/modules`](../../web/src/kernel/modules).
- Modules: `web/src/modules/<key>/` (pilots `people`, `organizations`, `leads`, `scoring`, the former extensions and `calls`) and the `kernel` module (`web/src/modules/kernel`), which registers the platform that lives in `web/src/features` (auth, installer, core settings, system, audit, search, custom objects, mobile).
- Discovery: [`web/src/modules.generated.ts`](../../web/src/modules.generated.ts) imports each module's `index.ts`. Generated by `make modules` from `back/aphel.modules.toml` (import `@modules/<key>`; see [`docs/modules/README.md`](../modules/README.md)).

## Contract

```ts
import { defineModule } from '@/kernel/modules/define'

const leadProModule = defineModule({
  key: 'lead_pro',
  translations: { 'pt-BR': () => import('./i18n/pt-BR.json'), en: () => import('./i18n/en.json') },
  settingsPanel: LeadProSettingsPanel,
  register(app) {
    app.routes([{ path: 'lead-pro', lazy: async () => ({ Component: (await import('./Board')).Board }) }])
    app.nav({ to: '/lead-pro', label: 'nav.board', icon: Flame, permission: 'lead_pro.read', order: 650 })
    app.settings('organization', { group: 'sales', path: 'lead-pro', label: 'settings.title', description: 'settings.description', icon: Flame, lazy: async () => ({ Component: (await import('./Settings')).Settings }) })
    app.recordTab('contact', { key: 'temperature', label: 'tab', render: TemperatureTab })
    app.slot('record.detail.actions', { recordTypes: ['contact'], permission: 'lead_pro.update', render: RecalculateButton })
    app.fieldType('temperature', { Input: TemperatureInput, Display: TemperatureBadge })
    app.filter('records.formLayout', (layout, { recordType }) => (recordType === 'contact' ? withTemperature(layout) : layout))
    app.override('leads.ConvertDialog', LeadProConvertDialog)
    app.timelineRenderer('lead_pro.temperature_changed', TemperatureItem)
  },
})

export default leadProModule
```

| Contribution | Effect |
| --- | --- |
| `routes(routes, { layout })` | Authenticated routes. `layout: 'app'` (default) sits inside the `AppLayout`; `'bare'` only requires a session |
| `publicRoutes(routes)` | Routes without a session (installer, login, public booking, public quote) |
| `nav(item)` | Item in the sidebar, the palette and the `G` shortcuts. `order` sets the position (custom objects go in `NAV_ORDER.customObjects`, modules without `order` in `NAV_ORDER.modules`, administration in `NAV_ORDER.administration`) |
| `settings(area, item)` | Settings item (`account`, `organization`, `integrations`, `data`) in the given group, with the page (`lazy`/`element`) and extra routes (`routes`). The area, the search, the card and the menu come from here |
| `navSection(section)` | Declares a sidebar section (`key`, `label` as `ns:key`, `order`); the `kernel` module declares `work`, `records`, `operations`, `analysis`, `administration`. A `nav` item picks its section with `section` (default `operations`); items pointing at an undeclared section are not shown |
| `traitListView({ trait, key, label, icon, render })` | Adds a view mode to the generic record list of every entity whose catalog traits contain `trait` (the shell never names the trait); `render` gets `{ recordType, traitConfig, search, canEdit }`. `workflow` provides the `stages` board for `workflow.staged` |
| `ruleError(code, formatter)` | Formats a rule violation error code into the message shown to the user (e.g. `stage_checklist_incomplete` by `workflow`) |
| `nav({ shortcut, mobile })` | `shortcut` registers the `G` + key go-to shortcut; `mobile: true` pins the item in the mobile bottom bar |
| `settingsArea(area)` | Declares a settings area (`key`, `basePath`, `titleKey`, `descriptionKey` as `settings` keys or `ns:key`, `icon`, `scope: 'account' \| 'admin'`, `groups`). The shell creates the route, the sidebar and the overview from the registry; `account`, `organization`, `integrations` and `data` are registered by the `kernel` module, and `SettingsAreaKey` is a plain string |
| `settingsGroup(area, group)` | Adds or reuses a group (`key`, `label`, `order`) inside an area; the first declaration of a key wins, so every module may declare the groups it uses (e.g. `sales`) |
| `recordTab(type, tab)` | Tab on the record pages of the type, after the page's own tabs. `render` receives `{ recordType, recordId, readOnly }` |
| `slot(name, contribution)` | Component at a named point (table below), with `recordTypes?` and `permission?` |
| `provideComponent(key, Component)` | Provides a contract component (see below) that other modules render without importing this one |
| `filter(name, fn, priority)` | Transforms a value (table below). Lower priority runs first (default 10) |
| `override(id, Component)` | Replaces a component marked with `<Overridable id="..." />`. The last active contribution wins; with more than one, a console warning in development |
| `fieldType(type, { Input, Display })` | Input and display of a field type. Replaces the native one part by part (e.g. `calls` replaces only the `Display` of `phone`) |
| `timelineRenderer(kind, r)` / `eventRenderer(event, r)` | Timeline items (the event one wins over the `kind` one) |
| `widget(key, r)` | Dashboard widget. With a `<module>.<name>` key, the title comes from `<module>:widgets.<name>.title` |
| `command(c)` | Palette command (`to` navigates, `run` executes) |
| `setupTask(task)` | Automatic work run by the setup wizard right after the workspace is created, while "Create workspace" is busy (`progressLabel`), when the module is among the selected features. `run()` uses the answers already given (never asks again) and returns `{ summary }` for the Ready screen, `null` when there is nothing to report; on failure the Ready screen shows `failureLabel` (e.g. `template` from `onboarding` applies the recommended template) |
| `setupStep(step)` | Interactive step shown at `/setup` when the setup is resumed or reopened (`usePending` tells whether it still has to be done). `render` receives `{ onDone }` and draws itself with `SetupStepFrame` from `@/kernel/setup` (same card, header and footer as the kernel steps); e.g. `template` from `onboarding` lets the administrator pick another template |

Labels (`label`, `description`) are i18n keys in the module's namespace; use `ns:key` for another namespace (the `kernel` uses `layout:nav.*` and `settings:tabs.*`). Permissions accept one or several (any one is enough).

Render a new point with `<Slot name="..." props={..} />` (`kernel/modules/Slot.tsx`) or `useSlot`/`useSlotEntries`, and declare the props by augmenting `SlotPropsMap` from the module that owns the slot (`modules/<key>/slots.ts`, `declare module '@/kernel/modules/slots' { interface SlotPropsMap { 'my.slot': Props } }`). `kernel/modules/slots.ts` only lists the platform slots; domain slots (`reports.library`, `dashboard.source`, `dashboard.top`, `catalog.sections`, `deals.*`, ...) are declared by their owner.

### Cross-module contracts

A module never imports another module's package (`@/modules/<other>`, side-effect imports included; the arch check counts it, now at 0). Three mechanisms replace those imports:

1. **Contract components.** The provider declares the key and props by augmenting `ContractComponentMap` (`modules/<key>/contracts.ts`, props written with types the provider owns or primitives) and registers `app.provideComponent('workflow.RottingBadge', RottingBadge)`. The consumer renders `<ContractComponent name="workflow.RottingBadge" record={deal} fallback={Plain} />` (or `useContractComponent(key, Fallback)` when it needs the component value). With no enabled provider it renders the fallback, or nothing. The first enabled provider by order wins.
2. **SDK contracts.** Pure helpers, hooks and API types that several modules share live in `web/src/sdk` (`workflow.ts`, `rotting.ts`, `period.ts`, and one folder per hoisted surface: `timeline/`, `formulas/`, `approvals/`, `money/`, `email/`, `saved_views/`, `tasks/`, `config_packages/`, `people/`, `dashboard/`, ...), next to the backend `aphel_contract_*` crates. A hoisted folder holds clients, hooks, constants, types and shared components, never a `registerRecordResource` call or a module registration (those stay in the owner so a disabled module registers nothing); the owner module imports its own folder from `@/sdk` too. The owner module imports them from `@/sdk` too, so there is one definition.
3. **Registries.** Navigation to another module's record goes through the record resource registry (`recordDetailHref(recordType, id)`), which returns `undefined` when the owner is disabled, never through the owner's resource file.

### Per-module API types

`npm run api:types` (`make api-types`) also writes `web/src/modules/<key>/api-types.d.ts` for every module that has an `api-tags.json` (a JSON array of extra OpenAPI tags; the module key and its dashed form always count). The file holds only the operations carrying those tags and the schemas they reach, and the module imports `components` from `@/modules/<key>/api-types` instead of the global `@/api` schema. The split is tag based because the OpenAPI document does not name the owning module; a module whose schemas are reached through shared tags (for example `records`) stays on the global types until the backend marks ownership. `line_items` is the first module on its own types.

## Enablement

All compiled modules are registered at boot (`app/modules.ts` → `bootModules`). Contributions are filtered by the set from `/api/v1/modules` (synced by `ModulesSync` inside the session):

- `required: true` (mirror of the backend: `kernel`, `people`, `organizations` and the other `required` ones) → always active, even before login;
- module listed by the server → active if enabled;
- module unknown to the server (e.g. `calls`, which is not yet a module in the backend) → active once the list has loaded.

Routes of non-required modules sit behind the `ModuleGate` (skeleton while loading, 404 if disabled). Translations are only added for active modules and removed when the module is disabled.

## Translations

Each module has a namespace equal to its key, in `web/src/modules/<key>/i18n/<locale>.json` (`pt-BR` and `en`). The `kernel` declares the namespaces of `web/src/i18n/<locale>/*.json` by glob (without `eager`) (`namespaces`). Translations declared as loaders only download the active language and the `pt-BR` fallback (details in [`docs/modules/web.md`](../modules/web.md#on-demand-translations)). After creating or moving a JSON file, run `npm run i18n:types` (`web/scripts/i18n-types`), which generates `web/src/i18n/i18next.d.ts` from both places. For dynamic keys, `useModuleTranslation(key)` returns an untyped `t` in the module's namespace.

`ModuleLocale` is a plain string: any module may ship any locale code in `translations`, and the language menus list `availableLanguages()` (the shipped `pt-BR` and `en` plus every locale a registered module declares). Names come from `navigation-settings:language.options.<code>` when present, otherwise from `Intl.DisplayNames`. `normalizeLanguage` matches an exact code first, then the primary subtag. Missing keys fall back to `pt-BR`.

## Field types

`FieldInput` and `FieldValueDisplay` look up `useFieldTypeRenderers(type)`. The native ones are registered by the kernel (`kernel/modules/native-field-types.ts`, components in `components/fields/native-inputs.tsx` and `features/records/display/native-displays.tsx`); contributions from active modules win. The record being displayed (so the phone knows which contact it belongs to) comes from `useDisplayRecord()` (`features/records/display/display-record.ts`).

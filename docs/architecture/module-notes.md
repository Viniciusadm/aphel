# Module notes

Per-module and per-session implementation notes moved out of `CLAUDE.md`, which keeps the platform rules. Each bullet describes how one module or domain is built; the review documents named in them live next to this file.

- **Party foundation (P5.1):** `aphel-contract-party` owns `party.contact_points` and typed email/phone/web field mappings without kernel or CRM dependencies. Native plugins use `aphel_sdk::party::PartyTraits`; phone/address field helpers and labels also belong to that SDK utility. Contacts/organizations provide the mapping; duplicates, trash and privacy consume it. The people/organizations identity migration is P5.2. Review checklist: [`docs/architecture/p5-party.md`](docs/architecture/p5-party.md).
- **Tasks/calendar (P5.4):** `tasks` owns tasks, types, recurrence and links. `calendar` is an optional source host over `aphel-contract-calendar` and SDK `CalendarSource`; owners enforce read/update scopes, field visibility and versioned rescheduling. The calendar web package uses generic entries and an open creation slot. Review: [`docs/architecture/p5-tasks-calendar.md`](docs/architecture/p5-tasks-calendar.md).
- **Messaging (P5.5):** `aphel-contract-messaging` owns open channel IDs and payload/configuration metadata. The native SDK owns `MessagingChannel`; email contributes its own adapter and messaging consumes enabled providers. Composer limits, threading and reply windows are provider policies. Review: [`docs/architecture/p5-messaging.md`](docs/architecture/p5-messaging.md).
- **Assignment (P5.6):** `assignment` accepts entities with owners, discovers targets from registry metadata and calculates least-loaded workloads through the aggregate engine. Entity owners declare active states with the pure assignment contract; tasks and deals supply their own workload semantics. Review: [`docs/architecture/p5-assignment.md`](docs/architecture/p5-assignment.md).
- **Money (P5.7):** `money` owns currency/rate schemas and the recalculation dispatcher; its contract and SDK own shared decimal conversion data/arithmetic and rate/converter ports. Monetary entities declare their own fields and recalculation sources. Rates use `money.read`, with no CRM permission dependency. Review: [`docs/architecture/p5-money.md`](docs/architecture/p5-money.md).
- **Documents (P5.8):** `documents` owns the shared bounded PDF layout/rendering policy. Quote/proposal owners supply scoped snapshots and localized content through the pure documents model; signing payloads and provider factories use the same contract/SDK. Review: [`docs/architecture/p5-documents.md`](docs/architecture/p5-documents.md).
- **Line items (P5.9):** `line_items` owns polymorphic scoped lines, discounts/taxes, ordering and amount-mode settings. Catalog adapters and owner projections use SDK ports; `deals_revenue` owns recurring calculations and widgets, while deals owns its financial fields and writes. Review: [`docs/architecture/p5-line-items.md`](docs/architecture/p5-line-items.md).
- **Timeline (P5.10):** `timeline` is an optional source host over the pure timeline kind contract and native SDK source/event-scope/decorator interfaces. Owners query, authorize and mask their own records; the host merges bounded namespaced pages and reads core event history. Kind filters and generic change labels use contributed metadata. Review: [`docs/architecture/p5-timeline.md`](docs/architecture/p5-timeline.md).
- **Privacy (P5.11):** privacy coordinates owner-provided discovery, snapshots, erasure, redaction and retention recency through the privacy contract/SDK. Entity policies and the generic record engine replace business-table SQL. Review: [`docs/architecture/p5-privacy.md`](docs/architecture/p5-privacy.md).
- **Reports (P5.12):** reports owns saved aggregate definitions, scoped execution/export and schedules. Entity options come from the registry; deals owns conversion/performance endpoints and contributes its report library cards. Review: [`docs/architecture/p5-reports.md`](docs/architecture/p5-reports.md).
- **Dashboard (P5.13):** owners contribute widget providers, pending/summary sections, event labels/visibility and portable-setting catalogs through SDK interfaces. The host discovers default placement and entity permissions from metadata. Review: [`docs/architecture/p5-dashboard.md`](docs/architecture/p5-dashboard.md).
- **Favorites (P5.14):** record labels use the scoped record engine; saved views owns its visibility source through the SDK. Favorites stores soft targets and includes entity type in target uniqueness. Review: [`docs/architecture/p5-favorites.md`](docs/architecture/p5-favorites.md).
- **Followers (P5.15):** owners contribute followed-event targets, source/recipient visibility and localized headline metadata. Generic updates and owner-following use declared event prefixes; followed titles use the scoped record engine. Review: [`docs/architecture/p5-followers.md`](docs/architecture/p5-followers.md).
- **Imports (P5.16):** entity owners declare aliases, exclusions and reference-creation policy through the imports contract/SDK. Scoped queries and registered handlers perform lookup/write; assignment uses its SDK selector. Import privacy clears owned rows and file references, blocks active jobs and prevents redacted-job reuse. Review: [`docs/architecture/p5-imports.md`](docs/architecture/p5-imports.md).
- **Webhooks (P5.17):** incoming create/upsert actions use enabled entity declarations, scoped unique queries and registered writable handlers. Mapping roots are `payload` and earlier `actions`; assignment uses its SDK selector. Public resources declare nested field-redaction metadata. Review: [`docs/architecture/p5-webhooks.md`](docs/architecture/p5-webhooks.md).
- **SSO (P5.18):** `sso` owns corporate identity/login with no CRM or peer implementation dependency. Task remote-calendar synchronization belongs to `tasks::remote_calendar`; mailbox OAuth belongs to `email::oauth`. Busy intervals and calendar availability use the calendar contract/SDK. Review: [`docs/architecture/p5-sso.md`](docs/architecture/p5-sso.md).
- **Deals (P5.19):** workflow metadata and wire projections use its pure contract/SDK catalog. Deals reads owned rows and combines bound workflow snapshots in commercial reports; related party labels use bounded scoped batches. Workflow contributes opted-in rotting fields through generic registry transforms. Review: [`docs/architecture/p5-deals.md`](docs/architecture/p5-deals.md).
- **Leads (P5.20):** lifecycle fields use owned side tables and registry transforms. Lead actions coordinate transactional owner handlers over scoped snapshots; deals supplies lifecycle lookup through its contract/SDK. Fresh schemas create extensions directly, with no legacy-column copy migration. Review: [`docs/architecture/p5-leads.md`](docs/architecture/p5-leads.md).
- **Remaining domains (P5.22):** `booking` replaces the scheduling module identity. Notification kinds and configuration package/plan metadata use pure contracts; their SDK extension/delivery/key interfaces replace implementation imports. Delivery, installation/version algorithms and SQL remain in their owners. Progress and pending manual acceptance: [`docs/architecture/p5-remaining-domains.md`](docs/architecture/p5-remaining-domains.md).
- **Record response includes (P5.22):** native entity endpoints use SDK `record_includes` and enabled `RecordIncludeSource` contributions after redaction. Sources own scoped lookups and payload schemas; entity DTOs do not import tagging. Taggable targets declare `tagging.taggable`; web controls use entity metadata.
- **Demo seeds, soft references and reference cleanup (P5.22):** `aphel_sdk::maintenance::DatasetSeed` lets each owner seed, back-date, count and clean its own demonstration records; `demo` only orchestrates by `order` and depends on no plugin crate. Cross-plugin links use `SoftReference` (`clear`) or no database key at all: record targets are handled by `RecordPurged` hooks in the referencing plugin, and non-record targets by `aphel_sdk::reference_cleanup::ReferenceCleanup` contributions that the target's store triggers on delete. Details and manual acceptance: [`docs/architecture/p5-remaining-domains.md`](docs/architecture/p5-remaining-domains.md).
- **Modules in the new pattern (session 31, reference for 33–35):** `back/modules/<key>/src` with `lib.rs` (`impl Module`: manifest, migrations, `record_type`/`extend`, routes, tags, permissions with `grant_to`, public events, hooks, `provide`, worker), `domain.rs`, `service.rs` (use cases as `async fn(ctx: &Ctx<'_>, ..)` functions), `store.rs` (concrete structs with SQL over `&mut MySqlTx`, `Store::of(ctx)`), `http.rs` (utoipa routes, DTOs and `RecordTypeHandler`) and `hooks.rs`. No `*Ports`, no repository traits and no `*_use_cases` factories: `Ctx` (`kernel/context.rs`: `scope`, `pool`, `registry`, `events`, `audit`, `jobs`, `app`, `begin()`, `fields()`, `query()`, `pipeline()`, `run_hook`/`apply_hook`) comes from `Ctx::from_state(&state, &scope)` or `Ctx::from_parts(..)`; another module calls `people::service::create(&ctx, ..)` directly. All business modules follow this pattern (the session 34 ones were rewritten right after it; the only things still using ports are the kernel's use cases, such as `ConfigPackageUseCases`, `FieldUseCases`, `FileUseCases` and `MySqlDashboardPorts`). Done: `organizations` (with `hierarchy/`), `people` (swappable service `dyn DuplicateDetector`), `leads` (formerly `lifecycle`; hooks `LeadQualifying`/`LeadDisqualifying`/`LeadConverting`/`LeadConverted`, service `dyn LeadConverter`), `scoring` and, since session 33, `currencies` (service `dyn CurrencyConverter`), `workflow` (stage guidance/checklist and stage requirements as `RecordValidating` 20/5, rotting), `deals` (with `team/`; veto hooks `DealStageChanging`/`DealWinning`/`DealLosing` and action hooks `DealWon`/`DealLost`, service `dyn AmountCalculator`), `line_items` (provides `ItemsAmountCalculator` and `quotes::LineItemsWriter`), `renewals`, `products`, `price_lists` (with bundles; services `dyn PriceListResolver`/`DiscountLimits`/`BundleExpander`), `quotes` (veto hook `QuoteAccepting` and filter hook `QuoteTotals`), `approvals` (`RecordValidating` 10, service `dyn ApprovalGate`), `tasks` (types, calendar and inbox; hook `ActivityCompleting`), `notes`, `reminders`, `calls` (service `dyn TelephonyRouter`), `forecast` and `goals`. A module that needs another without depending on it uses `registry.handler(type)`, a hook or a service from `Services`. A system field from another module is a **contributed field** (`SystemField.contributed_by`, read/written by the kernel in `kernel/records/contributed.rs`, flattened into the DTOs); `people`/`organizations` know neither `lifecycle_stage` nor `score`. Generic record-writing helpers (`InputValidator`, `Patch`, `AddressInput`, `publish_mutation`, `RecordMutation`, `archive_change`…) in `kernel/records`. Non-required modules that come enabled use `Manifest::enabled_by_default()`.
- **Former extensions (session 35):** `ai`, `enrichment`, `esign`, `google`, `insights`, `forms`, `messaging`, `microsoft`, `sso` and `proposals` are regular modules in `back/modules/<key>` (they implement `Module` directly; there is no longer `aphel-extension-api`, `back/extensions`, `back/src/extensions`, `ExtensionModule` or `ext-*` features). They follow the conventions of every module: routes at `/api/v1/<key>` (a key with `_` becomes `-`, e.g. `/api/v1/forms`), public ones at `/api/v1/public/<key>/…` (everything under `/api/v1/public/` is exempt from CSRF), tables `<key>_*`, jobs `<key>.*`, web in `web/src/modules/<key>` (routes `/<key>`, e.g. `/forms`); module administration in `kernel/application/module_admin` (`ModuleUseCases`, codes `module_*`, events `module.*`, secrets `owner_type = "module"`) and in the Settings › Integrations › Modules screen (`web/src/features/settings/modules`, namespace `modules`). `google`/`microsoft` do `depends_on("sso")` and reuse its code. Extension points with multiple implementations are **typed contributions**: `app.contribute::<dyn Trait>(Arc::new(..))`, read with `App::contributions::<dyn Trait>()` (enabled modules) or `all_contributions` — SSO login providers (`kernel::api::sso::LoginProvider`), email mailboxes (`email::MailboxProvider`), calendar availability (`aphel_sdk::calendar::CalendarAvailability`, receives `ctx`), telephony (`telephony::telephony::TelephonyProvider`) and configuration package sections (`ConfigSection<MySqlTx>`). Module settings via `kernel::modules::module_settings(pool, key)`, secrets via `module_secret_key(key, name)`; a contract without context uses `kernel::state::runtime_state()`. Manifest types (`ManifestBase`, `Migration`, `SettingField`…) in `kernel/modules/manifest.rs`. Modules and plugins guide: [`docs/modules/`](docs/modules/README.md) (`README.md`, `hooks.md`, `web.md`, `compatibility.md`).
- **Individual email:** per-user mailboxes (`mailboxes`) with credentials only in the `SecretVault` (`owner_type = "mailbox"`), conversations/messages/participants/links in `modules/email` (concrete stores `MailboxStore`, `MessageStore`, `LinkStore` in `modules/email/store`, services in `modules/email/service`). Providers implement `MailboxProvider` and enter the `MailboxProviderRegistry` (IMAP/SMTP in the `email` module; other modules contribute `dyn email::MailboxProvider`). Visibility `private`/`metadata`/`shared` per mailbox and conversation (`EmailVisibility::access_for`), always combined with read access to the linked record. `email.*` events once per linked record, with no content in the payload. Guide: [`docs/architecture/email.md`](docs/architecture/email.md).
- **Engagement (session 23):** sequences in `modules/sequences` (jobs `sequences.tick`/`sequence.step`, exits through the `sequences.exits` consumer, sending always through the `email::Sender` service (`modules/email/service`)); booking links in `modules/booking` (public API `/api/v1/public/book/*`, public web in `web/src/public/booking`, `meeting.booked` with `MeetingEventPayload`, busy = tasks + `aphel_sdk::calendar::CalendarAvailability` contributions); calls in the `telephony` module (`call` activity + `activity_calls`, outcomes in `call_outcomes`, VoIP providers only via `telephony::telephony::TelephonyProvider` contributions, chosen by the `dyn TelephonyRouter` service). Guides: [`docs/architecture/sequences.md`](docs/architecture/sequences.md), [`booking.md`](docs/architecture/booking.md), [`calls.md`](docs/architecture/telephony.md).
- **Pipeline and revenue (session 24):** computed system fields with `SystemField::computed(ComputedColumn)` (SQL only in `kernel/infrastructure/query/computed.rs`; read-only) — `days_in_stage`/`is_rotting`/`rotting_at` with `workflow_stages.rotting_days` and the `time.deal_rotting` trigger; base currency = `organization_settings.currency`, `amount_base`/`exchange_rate` written by the `CurrencyConverter` (`currencies` module) on write and frozen on win/loss, revenue aggregations sum `amount_base`; deal team in `modules/deals/team` with read access declared by `EntityDefinition::member_access` (applied in `push_record_scope_keyed` with `ShareReach::Read`); `mrr`/`arr`/`tcv`/`contract_*` in `modules/line_items/recurring.rs`, renewal per pipeline in the `renewals` module; these fields enter the `deal` type via `extend` of the owning module (job `renewals.scan`, unique per `renewal_of_deal_id`). Guides: [`docs/architecture/deal-team.md`](docs/architecture/deal-team.md), [`custom-fields.md`](docs/architecture/custom-fields.md), [`automations.md`](docs/architecture/automations.md).
- **Quotes, approvals and validation (session 25):** approval, stage checklist, validation rule and lifecycle are handlers of the `RecordValidating` hook (priorities 10 `approvals`, 20 `workflow`, 30 validation rule in `back/modules/record_hooks.rs`, 40 `leads`); approvals in the `approvals` module (policies by type/moment/condition, requests with steps, 409 `approval_pending`/`approval_required`, a new module uses the `dyn ApprovalGate` service (`submit`/`checkpoint`)), quotes in the `quotes` module (`quote` type, signed public link, acceptance syncs the deal through the `quote.deal_sync` job), prices/bundles/discount limits in the `price_lists` module, validation rules (error-condition formula, 422 `validation_rule_failed`) in `kernel/application/fields/validation_rules` and stage guidance/checklist in `modules/workflow/guidance`. Guides: [`docs/architecture/approvals.md`](docs/architecture/approvals.md), [`quotes.md`](docs/architecture/quotes.md), [`pricing.md`](docs/architecture/pricing.md), [`validation-rules.md`](docs/architecture/validation-rules.md).
- **Lifecycle, scoring, hierarchy and sharing (session 26):** `lifecycle_stage` validated and tracked in history by `leads::hooks::validate_stage` (hook `RecordValidating`), transitions through the `lifecycle.transitions` consumer, lead inbox at `/api/v1/leads/*` (module `modules/leads`); scoring in the `modules/scoring` module (idempotent signals per record/signal/source, consumer `scoring.events`, jobs `scoring.recalculate`/`scoring.decay`, computed field `score` = primary model, event `score.band_changed`); hierarchy in `modules/organizations/hierarchy` (`parent_company_id`, 422 `company_hierarchy_cycle|too_deep`, filter operator `in_group`); sharing in `kernel/application/record_sharing` (`record_shares`, `RecordScopeFilter.shares` = `ShareReach::{None,Read,Edit}` applied in `push_record_scope_keyed` for every type, permission `records.share`) and followers in `modules/followers` (notification `followed_record_activity`). Guides: [`docs/architecture/lifecycle.md`](docs/architecture/lifecycle.md), [`scoring.md`](docs/architecture/scoring.md), [`company-hierarchy.md`](docs/architecture/company-hierarchy.md), [`record-sharing.md`](docs/architecture/record-sharing.md).
- **PWA and push (session 27):** `push` channel in the notification preferences (`dispatch` enqueues `notification.push`, idempotent via `notifications.pushed_at`); subscriptions in `push_subscriptions` per device and session, deleted when the session is revoked (helpers in `kernel/infrastructure/notifications/push/revocation.rs`: every new session revocation must call them) and when the service responds 404/410; the installation's VAPID keys in the `SecretVault` (`reveal_installation`/`store_installation_if_absent`, table `installation_secrets`); `sw.js` generated at build time by `web/scripts/pwa` and never caches `/api/*`, except the plugin list and bundles under `/api/v1/public/wasm-runtime` (cache `aphel-plugins`). Guide: [`docs/architecture/pwa.md`](docs/architecture/pwa.md).
- **Themes (session 38):** the `themes` module (`back/modules/themes`, `web/src/modules/themes`) installs `aphel-theme` JSON packages (tokens + woff2 fonts) that change every design token of the installation, public pages and plugins that use `@aphel/ui` included. Tokens come from `back/modules/themes/tokens.json` (generated into `web/src/sdk/tokens.css`, `tokens.generated.ts` and `docs/ui/tokens.md` by `cargo run -p xtask -- themes sync`, run by `make modules`, checked by `make lint`). The active theme is served as CSS at `/api/v1/public/themes/active.css` (linked in `web/index.html`; `html:root` selectors; primary tokens keep `var(--org-primary…, …)`), values are validated per token kind and never stored as free text. Catalog entries of `kind: "theme"`; the web catalog renders them through the `catalog.sections` slot. Guide: [`docs/themes`](docs/themes/README.md).
- **Quotes and proposals (P5.21):** scoped owner handlers and commerce SDK interfaces replace peer implementation imports. Approvals owns policy seeding; catalogs provide bounded item snapshots. Review: [`docs/architecture/p5-quotes-proposals.md`](docs/architecture/p5-quotes-proposals.md).

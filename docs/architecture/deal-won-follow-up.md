# Won deal follow-up

This integration reuses the ordinary `automations` plugin, the `deal.won` trigger contributed by deals, and the `create_task` action contributed by tasks. The [request template](examples/deal-won-follow-up.json) is a draft for the existing `POST /api/v1/automations` endpoint. It is not installed or published automatically, and is independent of interface plugins. Replace `activity_type_id` with the UUID of an active activity type before submitting it. The Portuguese task title is scenario configuration, not a new UI translation.

## Contracts and authority

The native path consumes `aphel-contract-automation`: `AutomationTrigger`, `AutomationAction`, `AutomationGateway`, and `TaskOperations`. The event envelope supplies the deal reference; the engine loads the authorized record and resolves its owner. The closing payload does not supply the owner. Deals publishes its own event and tasks owns task validation, persistence, audit and events. Neither producer depends on this automation or on the other producer.

The public `tasks@1.0.0` operations `tasks.create` and `tasks.types` remain available independently. This recipe calls the native `TaskOperations` contract, not those JSON operations or a WASM bridge. No new `provides.contracts`, runtime manifest, required module dependency or provider substitution is introduced. Contributions are filtered by enabled owner. Install/enable producers before configuring and publishing the rule; inspect the existing automation catalog for `deal.won`, `create_task`, and `deals.deal`. Missing contributions are unavailable, not permission grants. This recipe introduces no mandatory dependency cycle.

Configuration and publication require `automations.manage`; publication checks action permissions, including `tasks.create`. Async execution uses the active publisher's current access, not the event author's or a WASM installer's authority. The publisher needs `deals.read` on the source and `tasks.create`; normal task validation also checks its type, assignee and linked record. Catalog, run inspection, and activity type selection may need their existing read permissions. An inactive/missing publisher produces `publisher_unavailable`; lost source access produces `record_not_accessible`; lost task creation permission fails the step with `permission_denied`. No system scope is passed to task creation.

## Recovery boundary

Runs are unique by automation and event/record trigger key. The worker serializes runs for the automation/record, reloads run state after acquiring the lock, and skips finished runs. Previously successful steps are reused. Pause/inactive status and cycle/depth/rate protection are checked again on retries.

`TaskSpec` carries the run and step identities. Its native Rust contract now requires providers of `TaskOperations` to recover the same task for that key; alternative implementations must honor this before claiming retry safety. This is a coordinated source change to the in-tree native contract, not a change to `tasks@1.0.0` JSON inputs or runtime package compatibility. The tasks adapter derives a stable UUID v7 from the run's timestamp and a SHA-256 digest of the namespaced run/step key. It uses that UUID for both the task and the existing `MutationReceipt`. Task insert, validation hooks, custom fields, audit, domain event and receipt commit in one existing transaction. A receipt lookup returns the same task ID after a crash between commit and step recording; the insert-once receipt arbitrates concurrent attempts. Permission is checked before replay. A rolled-back transaction leaves no receipt. A commit acknowledgement error is resolved by looking up the receipt. No new receipt table, queue or registry is created.

`create_task` can now retry transient errors through the existing engine. The native worker job is already persisted/deferred; no WASM `defer-effect` call is involved. The public JSON `tasks.create` operation remains non-durable and must not be advertised as suitable for a WASM deferred invoke merely because this native adapter is recoverable.

Consistency is asynchronous: winning the deal commits independently of the follow-up task. A later permission loss or disabled participant can prevent completion; inspect the existing run and step diagnostics. Reopening and winning again is a new event/run and may create another task. Removing the automation's run history destroys its deduplication identity; do not delete/recreate the automation to retry an uncertain outcome. A committed task later deleted by a user is not recreated by replay. Effects of arbitrary action hooks and external services have no exactly-once guarantee.

## Validation still required

No installation was changed. In an existing authorized environment, first resolve the real activity type, submit the draft, use its existing dry-run route with the selected deal, then explicitly publish via `POST /api/v1/automations/{id}/publish`. Inspect `GET /api/v1/automations/{id}/runs` and the individual run/steps, plus the existing linked tasks UI. No new UI or profile section is required.

Confirm one owner-assigned linked task on a valid win, the same result on duplicate event delivery, and another task only on a new win event. Exercise failures before commit, ambiguous commit acknowledgement, after commit/before step recording, and concurrent delivery. Confirm receipt/task/audit/outbox rollback together and retry retains the original task ID. Check pause during queued work/retry, disabled automations/deals/tasks, missing type/owner, revoked permissions and inactive publisher. An unavailable action reports `unknown action create_task`; a missing source handler is inaccessible/not found or a registry validation error, with no task write. Errors before step construction can remain job/run errors instead of step diagnostics. Disabling deals stops new producer events; it is not a promise to cancel already committed tasks. Removing tasks removes its action/service. Re-enable only after inspecting persisted runs; no automatic replay of terminal failures is promised.

Check causation propagation on the task event and cycle/depth protection, installation order, and independent producer use with the automation paused/removed. Compilation/probe do not prove these SQL, HTTP or worker behaviors. These checks remain pending under the prohibition on scratch instances and changes to real installations.

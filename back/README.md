# aphel

Backend of the Aphel CRM, built from [rust-backend-template](https://github.com/Viniciusadm/rust-backend-template), with a hexagonal (ports and adapters) layout: a pure domain, use cases that reach I/O only through traits, and concrete adapters (axum, sqlx with MySQL, Argon2, lettre) wired at the edges.

## Requirements

- Rust **1.94+** (edition 2024, required by sqlx 0.9)
- MySQL 8 for the endpoints that persist data (the docker compose at the repository root provides it)

Main crates: axum 0.8, sqlx 0.9 (MySQL, rustls), clap 4, utoipa 5 (+ utoipa-axum 0.2, utoipa-scalar 0.3), argon2 0.6, lettre 0.11 (SMTP), sha2 + getrandom, tower-http 0.7, uuid 1 (v7).

## Run locally

The only `.env` lives at the repository root; the binary looks for it in the current folder and its parents, so running from `back/` finds it. Copy the example and adjust `DATABASE_URL` and `APP_ENCRYPTION_KEY` if needed. The `.env` holds only infrastructure settings; the public address, outgoing email (SMTP), file storage and the other organization settings are edited on screen after the installer runs (see [docs/configuration.md](../docs/configuration.md)):

```bash
cp ../.env.example ../.env
```

Start the API. Without `DATABASE_URL` it still starts, but the endpoints that need the database answer 503. Migrations in [`kernel/migrations`](kernel/migrations) run on boot unless `RUN_MIGRATIONS` is off.

```bash
cargo run
```

## Command line

The binary is a CLI ([`app/src/cli`](app/src/cli)); each subcommand lives in its own file there, so new subcommands plug in the same way.

| Command | What it does |
| --- | --- |
| `aphel` or `aphel serve` | Starts the HTTP server; runs pending migrations first unless `RUN_MIGRATIONS` is off |
| `aphel migrate` | Applies pending migrations and exits (requires `DATABASE_URL`) |
| `aphel db reset --confirm <database>` | Permanently deletes and recreates the database from `DATABASE_URL`, then applies core and compiled module migrations so the installer is available again. Stop the server and workers first; requires DROP and CREATE privileges. Stored files are kept |
| `aphel openapi` | Prints the OpenAPI document as JSON to stdout |
| `aphel worker` | Runs the background job worker and the scheduler until SIGTERM/CTRL+C (see [Background jobs](#background-jobs-worker-and-scheduler)) |
| `aphel serve --with-worker` | HTTP server plus worker and scheduler in the same process, for simple installs |
| `aphel secrets generate-key` | Prints a new random `APP_ENCRYPTION_KEY` (base64, 32 bytes) |
| `aphel secrets rotate` | Re-encrypts every stored secret with `APP_ENCRYPTION_KEY`; keys being retired go in `APP_ENCRYPTION_PREVIOUS_KEYS` (see [docs/configuration.md](../docs/configuration.md#secret-encryption)) |
| `aphel search reindex [--record-type <type>]` | Rebuilds the global search index in batches (idempotent), custom objects included (`--record-type custom.<key>` reindexes only that object); see [docs/architecture/search.md](../docs/architecture/search.md) |
| `aphel org export --output <zip> [--without-files] [--as <e-mail>]` / `aphel org import <zip>` | Full backup of the installation (records, relationships, files, configuration, members and manifest) and its restoration into an empty installation (not installed yet; the installer offers the same restore as `POST /api/v1/installer/restore`); see [docs/data/org-export-format.md](../docs/data/org-export-format.md) |
| `aphel --help` | Lists the subcommands |

With cargo (the workspace default member is the `aphel` binary): `cargo run -- serve`, `cargo run -- migrate`, `cargo run -- openapi`. `aphel modules list|doctor|hooks [--markdown]|uninstall <key> [--purge]` inspects the modules of the build. Logs go to stderr (filter with `RUST_LOG`, default `info`), so stdout stays clean for `openapi`.

| `GET /api/docs` | Interactive API reference (Scalar) |

### OpenAPI

Every route is annotated with `#[utoipa::path]` and registered through `utoipa_axum::router::OpenApiRouter` with `routes!(handler)`, so the document in `/api/openapi.json` is built from the same router that serves the requests. DTOs derive `ToSchema`. The base document (title, tags, the `session_cookie` security scheme) is in [`kernel/src/api/docs.rs`](kernel/src/api/docs.rs).

[`openapi.json`](openapi.json) is a committed copy of the document; the frontend uses it as a fallback to generate its types. Regenerate it whenever a route or DTO changes:

```bash
cargo run -q -- openapi > openapi.json
```

The test `committed_openapi_json_is_up_to_date` fails while the committed file is stale.

### Responses

Errors always use the same envelope, produced from `AppError` by [`kernel/src/api/error.rs`](kernel/src/api/error.rs) (`ApiError` implements `IntoResponse`, so handlers return `Result<_, ApiError>` and use `?`):

```json
{ "error": { "code": "validation_error", "message": "invalid pagination parameters", "details": { "fields": [{ "field": "per_page", "message": "must be an integer between 1 and 100" }] } } }
```

`details` is `null` unless the error carries structured data (`AppError::InvalidFields`). Internal and persistence errors are logged and answered with a generic message. Malformed JSON bodies are rejected in the envelope by the `JsonBody<T>` extractor, which handlers use instead of `axum::Json`.

Listings answer `Page<T>`, serialized as `{ "data": [...], "meta": { "total", "page", "per_page" } }`, and single items answer `Data<T>`, serialized as `{ "data": { ... } }` (both in [`kernel/src/api/dto/common.rs`](kernel/src/api/dto/common.rs)). Listings read `?page=&per_page=` with the `Pagination` extractor ([`kernel/src/api/extractors/pagination.rs`](kernel/src/api/extractors/pagination.rs)): `page` defaults to 1 and must be at least 1, `per_page` defaults to 25 and must be between 1 and 100. Invalid values answer 422 `validation_error` with the offending fields in `details`. `Pagination::offset()` and `limit()` feed the SQL query; document the parameters with `params(PaginationQuery)` in `#[utoipa::path]`.

### Idempotency

Every `POST` under `/api/v1` (except `/auth/*` and `/installer`, which set cookies) accepts `Idempotency-Key` ([`kernel/src/api/idempotency.rs`](kernel/src/api/idempotency.rs), table `idempotency_keys`): the key is scoped by the SHA-256 of the credential and fingerprinted by method, path with query and body. The same key and body within 24 h replay the stored status and body with `Idempotent-Replayed: true`; another body answers 422 `idempotency_key_reused`; a request still running answers 409 `idempotency_key_in_progress` (taken over after 10 minutes). Only non-5xx, non-429 responses up to 1 MB are stored; the hourly `idempotency.purge` job deletes expired keys.

### Request id and logs

Every request gets an `x-request-id` (a UUID v7 generated by the server, or the value the client sent), returned in the response and recorded in the `http_request` span of the logs together with method and path ([`kernel/src/api/telemetry.rs`](kernel/src/api/telemetry.rs)). The span never includes headers or the query string, and `Authorization`, `Cookie` and `Set-Cookie` are marked as sensitive, so credentials never reach the logs.

## Authentication, tenancy and authorization

- **Sessions.** Login, the installer and invitation acceptance create a row in `sessions` and set the `aphel_session` cookie (`HttpOnly`, `SameSite=Lax`, `Secure` when the saved public address is `https`). The cookie carries 32 random bytes in hex; only their SHA-256 is stored. Sessions last 30 days, `last_seen_at` is refreshed at most once a minute, and logout, logout-all, password reset and deactivation revoke them. Email tokens (`user_tokens`: verification 48 h, reset 1 h, invitation 7 days) follow the same rule and are single use.
- **CSRF.** Every non-GET request under the API must send `X-Requested-With: aphel` (middleware in [`kernel/src/api/csrf.rs`](kernel/src/api/csrf.rs)); the web client adds it. Requests with `Authorization: Bearer` are exempt (the cookie is then ignored), and so is every path under `/api/v1/public/` (public module routes, `/api/v1/public/<key>/…`) and `/api/v1/hooks/` (`csrf::is_public_path`).
- **API tokens.** `api_tokens` stores the SHA-256 of `aphel_<prefix>_<secret>` (shown once), the scopes, expiration, last use (refreshed at most once a minute or when the IP changes) and revocation. `AuthContext` accepts `Authorization: Bearer aphel_…` besides the cookie; the token acts as its creator through `AccessScope::through_api_token`, whose permissions are the intersection of the token scopes (`<resource>:read|write`, derived from the permission catalog: `read` → `:read`, any other action → `:write`) with the creator's permissions loaded at each request, so a removed permission or a deactivated user stops the token (401 `invalid_api_token`). A permission missing only because of the scope answers 403 `insufficient_scope`. Events and audit entries record `Actor::ApiToken(<token id>)` (`Actor::from_scope`). Session and account routes (`/auth/*`, `/api-tokens`) use `SessionContext` and answer 403 `api_token_not_allowed` to a token. Requests with a Bearer token go through an in-memory sliding window per token (Settings → API tokens → Limits, default 600 requests per 60 seconds) that adds `X-RateLimit-Limit/Remaining/Reset` and answers 429 with `Retry-After`. The OpenAPI document offers the `api_token` scheme on every operation that accepts a session, except session-only tags.
- **Rate limit.** In memory, per process ([`kernel/src/api/rate_limit.rs`](kernel/src/api/rate_limit.rs)): login by IP + email, forgot-password and resend-verification by IP/user.
- **`AuthContext`** ([`kernel/src/api/extractors/auth.rs`](kernel/src/api/extractors/auth.rs)) is the single extractor: it validates the cookie or the `Bearer` token, resolves the session, the user and the `AccessScope`, and refuses users that are not `active` (invited or deactivated) and sessions still waiting for the second factor. **`SessionContext`** is used by account routes that refuse API tokens. There is no organization switch: one installation serves one company.
- **`AccessScope`** ([`kernel/src/domain/access/access_scope.rs`](kernel/src/domain/access/access_scope.rs): `user_id`, `role_key`, expanded `team_ids` including sub-teams, `PermissionSet`, plus the API token, the automation and the enabled modules) is built once per request by `build_access_scope` from `users.role_id`. Use cases and repositories that read business data take `&AccessScope` to authorize and apply the record scope; work without an actor (jobs, consumers, boot) uses `AccessScope::system()`, which holds every permission.
- **Authorization pattern: explicit call inside the use case.** Handlers extract `AuthContext` and pass `&tenant.scope` to the use case, which calls `scope.require(&Permission::X)?` (403 `permission_denied`) or `scope.record_filter(&Permission::X)?` through the `Authorizer` trait ([`kernel/src/application/access/authorizer.rs`](kernel/src/application/access/authorizer.rs)). There is no `Require<P>` extractor: keeping the check in the use case means the fakes-based tests cover it.
- **Permissions** are stable dotted strings (`people.read`, `settings.manage`, `users.manage`…) in `Permission` constants plus `permission_catalog()`; future modules add constants (or parse runtime strings). Each grant in `role_permissions` has a scope `own` / `team` / `organization`; `record_filter` turns it into `RecordScopeFilter::{Owner, Teams, Organization}`, which the query engine translates to SQL. The system role `admin` is granted everything at organization scope, including permissions created later; `manager` gets record permissions at team scope and `member` read/create/update/delete at own scope.

## CRM modules

- **Notes visibility.** A `private` note is visible only to its author, **administrators included**: for anyone else it answers 404 `note_not_found` and never shows up in listings or in the timeline; its body is written as `"[redacted]"` in the audit log and no `note.*` event carries a body. Reading notes needs `notes.read` and read access to the record; creating needs `notes.create`. Team notes are edited or deleted by the author with `notes.update`/`notes.delete`, or by someone whose scope for those permissions covers the author (organization, or a team the author belongs to); only the author changes the visibility.
- **Deal activity.** Activity events (`activity.created|updated|completed|reopened`) carry `record_type`, `record_id`, `links` and `occurred_at`; the `deals.last_activity` consumer moves `deals.last_activity_at` forward for the deals they reference.
- **Defaults are deactivated, not deleted.** Lost reasons and activity types are only deactivated, because the boot sync seeds them again when none is left.
- **Dashboard widgets.** A widget implements `WidgetProvider<P: DashboardPorts>` (`key`, `required_permissions`/`is_available`, `normalize_settings`, `data`) and is registered in `WidgetRegistry::builtin()` ([`modules/dashboard/src/engine`](modules/dashboard/src/engine)); `DashboardUseCases::with_registry` accepts more providers. Aggregates build a `QueryPlan` through `resolve_query` with the read scope and reuse `build_query(Count)` from the query compiler, so organization, soft delete, archive and own/team always apply; periods (`today`, `yesterday`, `last_7_days`, `last_30_days`, `week`, `last_week`, `month`, `last_month`, `quarter`, `last_quarter`, `year`, `last_year`, `custom`) are resolved in the organization time zone. Widgets may use the aggregation engine (`AggregateEngine::new(context.ports.query())`) and honour the selected person or team (`context.with_subject`/`subject_filter`) and `compare_to_previous`. Recent activity only lists allow-listed events of records the user can read; note events need `notes.read`, a team note or authorship, and a readable parent, and never carry the body. Saving the layout is a personal preference: no event and no audit entry.
- **Notifications.** Tables `notifications` (unique `(user_id, dedupe_key)`, `in_app` flag, `read_at`, `emailed_at`) and `notification_preferences` (one row per user, kind and channel overriding the defaults). Kinds: `task_assigned`, `task_due`, `deal_assigned`, `deal_stage_changed`, `note_mention`, `daily_digest` (email only), `export_ready`, `export_failed`, `import_finished`, `import_failed`; channels `in_app`/`email`. Defaults: in-app on for every kind; email on for assignments, due tasks and mentions; digest off. The `notifications.events` consumer turns `activity.created|updated`, `deal.created|owner_changed|stage_changed`, `note.created|updated` (`mentioned_user_ids`) and `export.*`/`import.*` (`requested_by`) into notifications, skipping the actor, inactive members and muted kinds, and enqueues `notification.email` in the same transaction (dedupe key `event:<event id>:<kind>`, so redelivery is harmless). Task reminders belong to the `reminders` module (`reminders.deliver` every minute and `reminders.tasks_due_today` every 5 min, in each user's time zone); `notification.daily_digest` (hourly, acts at 08:00 local) emails the tasks of the day to users who opted in. `WorkerRuntime::with_notifications(mailer, public_base_url)` registers all of it (links use the saved public address).
- **Reminders and recurrence.** Each activity has `reminder_minutes_before` (default 60 on create, `null` for none; `reminder_at` and `reminder_sent_at` are re-armed when the due date or the offset changes or the activity reopens). `reminders.deliver` (every minute, registered by `with_notifications`) sends `task_due` (`window: reminder`) for due task reminders and `reminder` for the personal `reminders` table, both through `dispatch` (dedupe by id and time) and skips anything older than 24 h; `notification.task_reminders` only keeps the 08:00 "due today" warning. Recurring tasks belong to a series in `task_recurrences` (rule `daily`/`weekly` with weekdays/`monthly` with day — clamped to the last day of the month —/`yearly`, `interval`, `until` or `count`, local anchor in the organization time zone, and a template of the occurrence). Completing an occurrence creates the next one in the same transaction (`activity.created` + audit), once per `(recurrence_id, recurrence_index)`; `PATCH` with `apply_to=following` updates the template, `recurrence` replaces the rule and `recurrence: null` ends the series.
- **Security events.** Table `security_events` (`kernel/application/security`): sign-ins, failures, lockouts, two-factor, password, sessions, API tokens and permission changes, written through `SecurityEventRecorder` (`state.security_events`) outside the business transaction. The MySQL recorder tags `login_succeeded` with a device key (browser + system + kind + /24 or /48 network) and, after recording, enqueues `security.email` for a sign-in from a device the account never used (not on the first tracked sign-in), password changes and two-factor on/off; `WorkerRuntime::with_security_emails(mailer, app_base_url)` sends them through the global SMTP. The login monitor locks an e-mail + IP after `LOGIN_LOCKOUT_ATTEMPTS` failures within `LOGIN_LOCKOUT_WINDOW_SECS` since the last success (429 `login_locked`, `login_locked` recorded once per lock).
- **Mentions.** Notes mention users with `@[name](user:<id>)`; new mentions must be active members (422 on `body`, at most 50 per note), private notes never notify, and a mention on a record the user cannot read stores no title, record or link and never the note body. Note previews in the timeline show `@name`.
- **Import and export.** `POST /api/v1/imports` (multipart `file`, `record_type`, optional `retry_of`) stores the CSV in `files`, detects the encoding (UTF-8 with or without BOM, otherwise Windows-1252) and the delimiter (`,` `;` tab `|`), and answers the first 20 rows plus a mapping suggested by normalized name against field keys, labels and pt-BR synonyms. `PUT .../mapping` saves one field key (or `null`) per column plus the duplicate options (`duplicate_key` email/phone/domain/name, `duplicate_strategy` skip/update/create, `create_missing_companies`); `POST .../validate` is a dry run; `POST .../start` stores `import_rows` (`pending`) and queues `import.run`, which writes each row through the module use cases (validation, custom fields, event and audit per record) in batches of 200 with up to 4 parallel writes. A row marked `imported`, `skipped` or `failed` is never processed again. Record fields accept an id or a label (company by name/domain, created when missing; stage by name) and user fields a member email. The failed rows go to a CSV in `files` (`error_file_id`); uploading it fixed with `retry_of` reimports only those rows with the same mapping, and `POST .../retry-failed` requeues them unchanged. `POST /api/v1/exports` (`<type>.export`) queues `export.run`, which reads the records with the listing filter, sort, search and the requester's own/team scope rebuilt in the worker, writes CSV (UTF-8 with BOM) or XLSX with the chosen columns into `files` owned by the requester, and neutralizes spreadsheet formulas (`'` prefix). Jobs end with `import.completed|failed` / `export.completed|failed` (actor `system`, requester in the payload); the audit log gets `import.started|retried|completed|failed` and `export.requested|completed|failed`. Importable types: contact, company, deal; exportable: those and activity. `WorkerRuntime::with_data_transfer(storage)` registers the jobs.
- **Duplicates and merge.** Rules in `duplicate_rules` (people: `email`, `phone`, `name_company` = similar normalized name and same company; organizations: `domain`, `name`; all enabled by default). Pairs live in `duplicate_candidates` (`pending`/`dismissed`/`merged`, ordered pair unique) and are filled by the daily `duplicates.scan` job (`POST /duplicates/scan` queues it on demand) and right after `POST /people|organizations`, whose response carries `possible_duplicates` as a warning. Candidate rows are derived data and publish no event; dismissing publishes `duplicate.dismissed`. `POST /duplicates/merge` needs update on the primary and delete on the duplicate; in one transaction it applies the chosen value of each field (system and custom, through `CustomFieldWriter`), moves tasks, activity links, notes, attachments, taggings, record references in custom fields, deals and company links (people) or people and deals (organizations) to the primary, soft deletes the duplicate, writes `record_merges` (flattened, so chains point to the last survivor) and publishes `contact.merged`/`company.merged` with an audit entry on both records. `GET /people|organizations/{merged id}` answers the survivor, and the survivor timeline includes the events of the records merged into it (`domain_events` is never rewritten). Deals are not mergeable.
- **Trash.** Soft deleted people, organizations and deals are listed in `GET /trash` (`settings.manage`; merged records are hidden) and can be restored (`<type>.restored`) or purged (`<type>.purged`: custom values, notes, attachments, taggings and candidates are deleted, tasks lose the link). The daily `trash.purge` job purges records deleted longer ago than `trash_settings.retention_days` (default 30, 1–365, `PUT /trash/settings`) with actor `system`.
- **Global search.** `GET /api/v1/search?q=&types=&limit=` searches every registered record type through `search_index` + `search_index_terms` (text per field, `FULLTEXT ... WITH PARSER ngram`, stored lowercase without accents, phones as digits). Only searchable, non-sensitive text/e-mail/phone/URL fields are indexed; at query time only the fields visible to the role are matched, each type needs its read permission and the candidates are revalidated through the record query executor (own/team scope, soft delete, archive, deal pipeline restriction). The `search.index` consumer reindexes the record of every `<type>.*` event (and `merged_id`), `field.updated|activated|deactivated` enqueue `search.reindex` for the type, and migration `1512` queues the first full reindex. Details in [`../docs/architecture/search.md`](../docs/architecture/search.md).
- **Custom objects and relationships.** Administrators create record types `custom.<key>` (`custom_objects`, records in `custom_records` + typed custom field values) and relationships between any pair of `company`, `contact`, `deal`, `product` and custom objects (`relationship_definitions`, links in `record_relations`). The installation registry (`RecordTypeCatalog`, a single cache read through `state.registry()` and versioned by `organization_settings.custom_schema_version`, so the server and the worker pick up changes without restarting; in the worker `CatalogJobHandler`/`CatalogEventConsumer` resolve the current registry on every run) makes them work in every generic feature: record queries, `relation.field` filters and `related` filter nodes (core listings included), aggregations grouped by a single related record, saved views, layouts, field permissions, search, import (`relations.<key>` columns), export, tags, notes, attachments, timeline, outgoing webhooks (`custom.<key>.*`) and the `custom_objects` package section. Deleting a record on the `from` side of a `restrict` relationship answers 409 `record_has_relations` (checked in the delete transaction). Details in [`../docs/architecture/custom-objects.md`](../docs/architecture/custom-objects.md).
- **Configuration packages.** Each section of an `aphel-config` package is a `ConfigSection<Tx>` (`export`, `validate`, `plan`, `apply`) registered in `builtin_sections` ([`modules/config_packages/src/infrastructure/ports.rs`](modules/config_packages/src/infrastructure/ports.rs)): fields, workflow (stages and stage rules), lost reasons, activity types, tags, layouts, views and dashboard, installed in that order. Items are matched by stable key; workflow, stages, lost reasons, tags and views keep theirs in `config_item_keys` (derived from the name until the first install). The plan never deletes and never touches business records; conflicts are skipped unless the request decides `apply` on a resolvable one, and the plan fingerprint must match at apply time (`409 plan_outdated`). The `dashboard` section writes the organization default layout (`dashboard_default_layouts`), used when a user has not saved one. Templates are the JSON files in [`kernel/config-packages/templates`](kernel/config-packages/templates), embedded with `rust-embed`.

## Installation

- **Installer.** `organization_settings` is the single-row table (`id = 1`) of the company data. The wizard is available while it is empty; `POST /api/v1/installer` claims it inside the transaction that creates the row (`SELECT NOT EXISTS(SELECT 1 FROM organization_settings FOR UPDATE)`), so concurrent attempts create a single organization and the losers get 404. The same transaction creates the administrator, seeds the system fields and CRM defaults (`seed_system_fields`, `seed_crm_defaults`) and saves the public address (the browser origin, editable later). Optional steps of the wizard configure the outgoing email and, instead of a new installation, restore a backup (`POST /api/v1/installer/restore`, the same restore as `aphel org import`). The installation publishes `installation.completed` with its audit entry, then the handler starts the session through the regular login. There is no public registration: other users join by invitation.

## Embedded frontend

The React app in [`../web`](../web) is served by this binary. [`kernel/src/api/web.rs`](kernel/src/api/web.rs) embeds `../../web/dist` (relative to `back/kernel`) with `rust-embed` and answers every route that no handler matched: existing files are served as they are, and any other path gets `index.html` so client-side routing works. Unknown `/api/*` paths still return the JSON 404; `/api/docs` and `/api/openapi.json` are real routes and never reach the SPA.

- **Release:** run `../build.sh`. It regenerates the module registries (`modules sync`), builds the frontend and then `cargo build --release -p aphel`, so `dist/` ends up inside a single binary. Build the frontend first, otherwise the binary ships without it.
- **Development:** run `cargo run` and `npm run dev` in `web/`. In debug builds `rust-embed` reads `dist/` from disk, and the Vite dev server proxies `/api` to port 3001, so you keep hot reload.

## Architecture

Dependencies point inward: `api` depends on `application`, which depends on `domain`. `infrastructure` implements the traits (ports) declared in `application`, and handlers build their use case per request.

| Path | What it is |
| --- | --- |
| [`kernel/src/domain`](kernel/src/domain) | Pure types and rules, with no axum, sqlx or serde: value objects (typed ids such as `UserId`, `Email`, `NonEmptyString`, `Secret`), `User`, `Organization` (the company data of the installation), `access` (`Permission`, `RecordScope`, `RoleKey`, system roles, `AccessScope`, `RecordScopeFilter`) and `fields` (`FieldType`, `FieldDefinition`, `FieldConfig`, `FieldValue` and the per-type validation). |
| [`kernel/src/application`](kernel/src/application) | Use cases and ports. `auth` (`AuthUseCases<P: AuthPorts>`: login, sessions, email verification, password reset, invitations), `installer`, `access` (`AccessRepository`, the `Authorizer` trait and `build_access_scope`), `organizations` (company data and the on-screen settings, `OrganizationConfigCatalog`), `mail` (`Mailer` port and pt-BR templates) and `security` (`PasswordHasher`, `SecureTokens`, `Clock`). New ids are UUID v7. |
| [`kernel/src/infrastructure`](kernel/src/infrastructure) | Adapters that implement the ports: `Argon2PasswordHasher`, `Sha256SecureTokens`, `SystemClock`, `SmtpMailer`/`MemoryMailer`, the MySQL repositories and `MySqlAuthPorts`, which wires them for `AuthUseCases`. |
| [`kernel/src/database`](kernel/src/database) | Connection pool, transactions and the embedded migrator (`database::migrations`). |
| [`kernel/src/config`](kernel/src/config) | `AppConfig::from_env()`. |
| [`kernel/src/errors`](kernel/src/errors) | `AppError`, the single error type, with stable codes. |
| [`kernel/src/api`](kernel/src/api) | HTTP layer: `AppState` (pool, mailer resolved per send, dynamic file storage, organization settings, record type registry, auth settings, rate limits), DTOs, extractors (`AuthContext`, `SessionContext`, `ClientInfo`, `JsonBody`, `Pagination`), session cookie, CSRF middleware, rate limiter, the error envelope, OpenAPI docs, request id and tracing, and the routes. |
| [`app/src/cli`](app/src/cli) | The `aphel` command line and its subcommands. |
| [`kernel/src`](kernel/src) | Crate `aphel-kernel`, the platform: `domain`, `application`, `infrastructure` and `api` (the rows above), the module runtime (`modules`: `Module`, `AppBuilder`/`App`, hooks, services, migrations, the global `app()`), records pipeline, generic record write helpers and contributed fields (`records`), `AppState`, the use case context `Ctx` (`context.rs`), the worker runtime and `KernelModule` (`kernel_module.rs`: platform routes, tags, permissions, notification kinds, record guards and platform workers). Platform migrations live in [`kernel/migrations`](kernel/migrations). |
| [`modules`](modules) | One crate per business module (`aphel-mod-<key>`, `modules/<key>/src` + `modules/<key>/migrations`), each with `lib.rs` (`impl Module`), `domain.rs`, `service.rs` (use cases as `async fn(ctx: &Ctx<'_>, ..)`), `store.rs` (concrete SQL stores), `http.rs` (routes, DTOs, record handler) and `hooks.rs`. A module depends on `aphel-kernel` and on the modules it uses, aliased by key (`leads::LeadQualifying`); cycles are impossible, so mutual needs go through hooks, services or typed contributions. |
| [`plugins`](plugins) | Local third-party plugins, compiled only when listed in `aphel.modules.toml` (example: [`plugins/lead_pro`](plugins/lead_pro)). |
| [`app`](app) | Crate `aphel`, the binary: `main.rs` (builds the `App` from `src/modules.rs` and installs it), the CLI and the generated registry [`app/src/modules.rs`](app/src/modules.rs). |
| [`xtask`](xtask) | `cargo run -p xtask -- modules sync [--check]` (`make modules`): reads [`aphel.modules.toml`](aphel.modules.toml) and generates `app/Cargo.toml` dependencies, `app/src/modules.rs` and the web registry. |

Rules the layout follows:

- No global state or service locator. `AppState` holds only infrastructure; each handler builds its use case.
- The domain does not know the framework.
- Every error goes through `AppError` and is mapped to HTTP in `app_error()`.
- Every route has a `#[utoipa::path]` annotation and shows up in `/api/openapi.json`.
- The kernel never depends on a module; modules never form cycles.
- Use cases in the kernel (`kernel/src/application`) are generic over their ports; every business module drops the ports and work over `Ctx` and concrete stores.

## Optional modules

The integration modules (`ai`, `enrichment`, `esign`, `google`, `insights`, `forms`, `messaging`, `microsoft`, `sso`, `proposals`) are plain module crates in `modules/<key>` and follow the same conventions as every module: HTTP routes under `/api/v1/<key>` (kebab-case, such as `/api/v1/forms`), public routes under `/api/v1/public/<key>/` (every path under `/api/v1/public/` and `/api/v1/hooks/` is exempt from the CSRF header), tables prefixed with `<key>_`, job kinds prefixed with `<key>.` and web pages at `/<key>`. Extension points with several implementations (SSO login providers, mailbox providers, calendar availability, telephony providers, config sections, CLI commands, CRM seeds, time triggers, timeline events) are typed contributions: `app.contribute::<T>(Arc::new(..))`, read with `App::contributions::<T>()` (enabled modules) or `App::all_contributions`. Module settings come from `aphel_kernel::modules::module_settings` and their secrets use `module_secret_key`.

Exception to the "no global state" rule: the `App` is installed once by `main` (`aphel_kernel::modules::install_app`) and read with `app()`, and the process `AppState` is installed once (`aphel_kernel::state::install_runtime_state`, by the router, the worker runtime and the modules CLI) so contracts that receive no context, such as `MailboxProvider`, can reach the database and the vault with `runtime_state()`. Guide: [`docs/modules`](../docs/modules/README.md).

## Adding a feature

A new business feature (for example `warranties`) is a crate in `modules/warranties/` (or `plugins/warranties/` for a third-party plugin):

1. `Cargo.toml` with `aphel-kernel.workspace = true`, the module crates it uses (`deals = { package = "aphel-mod-deals", path = "../deals" }`) and the external crates from `[workspace.dependencies]`.
2. `src/lib.rs`: `impl Module` with the `Manifest` (dependencies with `depends_on`/`optional` for every module whose tables it references, `enabled_by_default()` or `required()`, migrations from `migrations/0001_*.sql`, optional `uninstall_sql`) and `register(&mut AppBuilder)` (record type, routes, OpenAPI tag, permissions with `grant_to`, public events, notification kinds, hooks with `declare_hook` for its own, services, automation triggers and actions, jobs, consumers and schedules).
3. `domain.rs`, `service.rs`, `store.rs`, `http.rs` and `hooks.rs` as above.
4. A line in [`aphel.modules.toml`](aphel.modules.toml) and `make modules` (regenerates `app/Cargo.toml`, `app/src/modules.rs` and `web/src/modules.generated.ts`).

Only platform code (needed by the kernel itself) goes in `kernel/src`. Full guide with the `lead_pro` example: [`docs/modules/README.md`](../docs/modules/README.md).

## Domain events and audit log

- **Outbox.** `EventPublisher<MySqlTx>` is implemented by `MySqlEventPublisher` ([`kernel/src/infrastructure/events`](kernel/src/infrastructure/events)), which inserts the `DomainEvent` into `domain_events` with the transaction it receives, so the event exists only if the use case commits. `dispatched_at` stays `NULL` until the worker job `outbox.dispatch` hands the event to the consumers. `domain_event_from_row` rebuilds a `DomainEvent` from a row selected with `DOMAIN_EVENT_COLUMNS`.
- **Audit.** `AuditLog<MySqlTx>` is implemented by `MySqlAuditLog` ([`kernel/src/infrastructure/audit`](kernel/src/infrastructure/audit)), writing to `audit_logs` (action, record reference, actor, `changes` as a JSON array of `{ field, old, new }`, ip) in the same transaction.
- **Diffs.** `diff_changes(&old, &new, &DiffOptions)` ([`kernel/src/application/audit/diff.rs`](kernel/src/application/audit/diff.rs)) compares the first-level fields of two `Serialize` values and returns `Vec<FieldChange>`. `DiffOptions::default().ignoring(&["updated_at"]).redacting(&["pin"])` skips ignored fields and writes `"[redacted]"` for sensitive ones (only when they changed). `password`, `password_hash`, `token`, `secret`, `api_key` and fields ending in `_password`, `_secret`, `_token`, `_token_hash` are always redacted. `diff_values` does the same for `serde_json::Value`, and `Value::Null` stands for "no snapshot" on creation or deletion.
- **Query.** `GET /api/v1/audit-logs?record_type=&record_id=&actor=&from=&to=&page=&per_page=` (needs `audit.read`) lists the entries of the installation, most recent first. `actor` is the actor id, `from`/`to` are inclusive RFC 3339 instants; user actors come with name and email.

## Secrets and public events

- **Secret vault.** `SecretVault<MySqlTx>` ([`kernel/src/application/secrets`](kernel/src/application/secrets)) stores secrets by `SecretKey { owner_type, owner_id, name }` inside the caller's transaction (`store`, `remove`, `remove_owner`), reads them with `reveal` and answers which keys exist with `configured`. `MySqlSecretVault` ([`kernel/src/infrastructure/secrets`](kernel/src/infrastructure/secrets)) encrypts with AES-256-GCM (`APP_ENCRYPTION_KEY`), binding each ciphertext to owner type, owner and name as associated data (company secrets use `SecretKey::organization(name)`, owner id `default`), and records the key id so `aphel secrets rotate` can re-encrypt. It is `state.secrets` in the API and `WorkerRuntime::secrets()` in the worker; without a key both are `UnavailableSecretVault`. Secrets never go back through the API, logs or audit entries: responses expose only whether a secret is configured.
- **Public events.** `public_event_catalog()` ([`kernel/src/application/public_events`](kernel/src/application/public_events)) lists the stable event types exposed to integrations (`GET /api/v1/events/catalog`, [`docs/api/events.md`](../docs/api/events.md)). `PublicEventRenderer::render(&DomainEvent)` builds the public body (`PublicEvent::to_json()`): the API DTO of the record, loaded through the regular use cases with the worker scope, plus `previous`. `ApiPublicEventRenderer::shared(pool)` ([`modules/webhooks/src/outgoing/renderer.rs`](modules/webhooks/src/outgoing/renderer.rs)) is the implementation; it answers `None` for internal events and for records no longer visible.

## Files and attachments

Files are stored through the `FileStorage` port ([`kernel/src/application/shared/storage.rs`](kernel/src/application/shared/storage.rs)), implemented with `object_store` by `ObjectFileStorage` ([`kernel/src/infrastructure/storage`](kernel/src/infrastructure/storage)). The driver is an organization setting (Settings → File storage: local disk, `./storage` by default, or any S3 compatible service with bucket, region, endpoint, access key, plain `http` for local services and path style; the secret key lives in the secret vault). `DynamicFileStorage` is the `state.storage` of the API and of the worker: it resolves the current driver from the settings (cache invalidated on save) and rebuilds the `object_store` client with `build_file_storage` when it changes. Changing the driver does not copy existing files. `POST /api/v1/organization/settings/storage/test` writes, reads and deletes an object without saving. The upload limit (Settings → General, 25 MB by default) is enforced while the multipart body is read (413 `file_too_large`).

For a local S3 compatible service, `docker compose --profile s3 up -d` (also `--profile minio`) starts SeaweedFS on `OBJECT_STORE_PORT` (8333) and creates the `OBJECT_STORE_BUCKET` bucket (`aphel`); it accepts any credentials, so in the storage settings use endpoint `http://127.0.0.1:8333`, any access key and secret, and allow `http`.

- **Tables.** `files` (storage key, sanitized original name, detected MIME type, size, SHA-256 checksum, uploader, `deleted_at`) and `attachments` (file → `RecordRef`, unique per file and record, indexed by `(record_type, record_id)`).
- **Upload.** `POST /api/v1/files` (multipart, field `file`, optional `record_type` + `record_id` to attach in the same request). The file must not be empty nor exceed the upload limit of the organization settings (Settings → General, 25 MB by default); the MIME type is detected from the content (`infer`), never from the extension or the client `Content-Type`, and must be in `ALLOWED_MIME_TYPES` ([`kernel/src/application/files/content.rs`](kernel/src/application/files/content.rs): common images, PDF, plain text/CSV, Office/OpenDocument, RTF, zip, mp3/mp4). Content without a known signature is accepted only as UTF-8 text (`text/plain`, or `text/csv` for `.csv`) and rejected when it starts with markup, so HTML, SVG and XML are refused, as well as executables (422 `file_type_not_allowed`). The name loses any path, control and bidi characters and is limited to 200 characters. The storage key is `<yyyy>/<mm>/<file uuid v7>` and never contains the name. The object is written first; if the database transaction fails it is deleted.
- **Download.** `GET /api/v1/files/{id}` streams the content with the detected `Content-Type`, `Content-Disposition: attachment` (ASCII fallback plus `filename*` UTF-8), `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store` and a sandboxing CSP. Who can read: the uploader, anyone with `settings.manage`, or anyone with read access to one of the records the file is attached to. Everything else answers 404 `file_not_found`, so existence never leaks. Downloads always go through the server, also with S3; `presigned_get` is implemented by the S3 driver for later use.
- **Attachments.** `GET /api/v1/attachments?record_type=&record_id=` (read access to the record, paginated), `POST /api/v1/attachments` with `{ file_id, record_type, record_id }` (update access to the record and read access to the file; 409 `already_attached`) and `DELETE /api/v1/attachments/{id}` (update access; the file is kept). Each mutation publishes `attachment.added` / `attachment.removed` (and the upload `file.uploaded`) and writes the audit entry in the same transaction.
- **Record access.** The `RecordAccessChecker` port (`can_read`, `can_update`) decides access to the target record. In MySQL it is `MySqlRecordAccessChecker` ([`kernel/src/infrastructure/records`](kernel/src/infrastructure/records)): the record type must be in the `RecordTypeRegistry` (otherwise 422 `unsupported_record_type`), the record must exist and not be soft deleted, and it must be visible under the own/team/organization scope of the type's read permission (`can_read`) or `update_permission` (`can_update`). `PermissionRecordAccessChecker` only checks the permission and is kept for fakes.

## Custom fields, record queries and saved views

The full design is in [`../docs/architecture/custom-fields.md`](../docs/architecture/custom-fields.md). In short:

- **Registry.** Each core record type is declared once in `RecordTypeRegistry::builtin()` (the CRM types `company`, `contact`, `deal`, `activity` and `product` live in [`kernel/src/application/fields/builtin.rs`](kernel/src/application/fields/builtin.rs)) ([`kernel/src/application/fields/registry.rs`](kernel/src/application/fields/registry.rs)): table, owner / `deleted_at` / `archived_at` columns, read permission, title field, system fields (key → column, type, filterable, sortable, searchable) and relations. Identifiers are validated on registration and are the only names that ever reach SQL. `AppState.record_types` is a `RecordTypeCatalog`, a single cache of the installation that adds the active custom objects (`custom.<key>`, stored in `custom_records` with an `object_id` partition) and the relations of the configurable relationships; resolve it with `state.registry().await?` (or `CatalogJobHandler`/`CatalogEventConsumer` in the worker). It is versioned by `organization_settings.custom_schema_version` and invalidated when objects or relationships change (`state.record_types.invalidate()`), in `serve` and in the worker. See [`../docs/architecture/custom-objects.md`](../docs/architecture/custom-objects.md).
- **CRM defaults.** The `crm` blueprint applies its configuration packages (`blueprints/crm/config`) after install through `BlueprintConfigurator` (implemented by `config_packages`): the workflow with its stages, lost reasons, task types, call outcomes, deal team roles, lifecycle and approval policies.
- **Seeding.** System fields are written to `field_definitions` (`is_system = true`) by the installer (`seed_system_fields`) and by `sync_system_fields` on `serve`, `worker` and `migrate` (idempotent).
- **Values.** `CustomFieldWriter::apply(&mut tx, scope, &record, &values, WriteMode)` validates every value (type, limits, options, required, references, uniqueness) and returns per-key `InvalidFields` errors (`custom_fields.<key>`) or the list of `FieldChange` for the audit diff; `CustomFieldReader::load` reads N records in one query. Values live in typed columns of `custom_field_values` and in `custom_field_multi_values`.
- **Queries.** `RecordQueryEngine::query(scope, record_type, RecordQuery)` checks the read permission, resolves the filter AST against the fields (unknown keys, operators or values become 422 with the path, such as `filter.conditions.1.value`), and the compiler in [`kernel/src/infrastructure/query`](kernel/src/infrastructure/query) builds bound SQL with organization, soft delete, archive and own/team scope conditions. It returns a page of ids plus the total; modules load the rows by id. `RecordQueryParams` reads `?filter=<json>&sort=-a,b&search=&archived=` for module listings.
- **Views.** `ViewUseCases` stores filter, sort, columns and settings with `private` / `team` / `organization` visibility (organization views and the organization default need `settings.manage`) and a default view per user.

## Background jobs, worker and scheduler

Jobs live in the MySQL table `jobs` (migration `0330`) and recurring schedules in `scheduled_jobs` (`0331`). The port is `JobQueue<MySqlTx>` ([`kernel/src/application/shared/jobs.rs`](kernel/src/application/shared/jobs.rs)), implemented by `MySqlJobQueue` ([`kernel/src/infrastructure/jobs`](kernel/src/infrastructure/jobs)).

| Command | What it does |
| --- | --- |
| `aphel worker` | Runs migrations (unless `RUN_MIGRATIONS` is off), upserts the default schedules, then runs `WORKER_CONCURRENCY` job loops, the scheduler and the expired-lock recovery until SIGTERM/CTRL+C |
| `aphel serve --with-worker` | Same worker inside the HTTP process; both stop together on SIGTERM/CTRL+C |

| Variable | Default | Purpose |
| --- | --- | --- |
| `WORKER_CONCURRENCY` | `4` | Jobs processed in parallel by one worker process |
| `WORKER_POLL_INTERVAL_MS` | `1000` | First wait between polls when the queue is empty; it doubles up to 5 s while the queue stays empty |
| `WORKER_JOB_TIMEOUT_SECS` | `300` | Maximum run time of one job; past it the job fails with `job timed out` and follows the retry rules. Locks older than this plus 60 s are considered abandoned |
| `SCHEDULER_INTERVAL_SECS` | `5` | How often the scheduler looks for due `scheduled_jobs` |

- **Enqueue.** `jobs.enqueue(&mut tx, Job::new("kind", payload))` inside the use case transaction (the job exists only if it commits), or `enqueue_now(job)` with its own connection. Builders: `on_queue`, `run_at` (default: now), `with_max_attempts` (default 5), `with_unique_key`.
- **`unique_key`.** A key is occupied while its job is pending or running: enqueueing another job with the same key returns `EnqueueOutcome::Duplicate` (not an error). When the job finishes or fails for good, the worker sets `unique_key` to `NULL`, so the key can be used again.
- **Reservation.** Each loop picks the oldest due job with `SELECT … FOR UPDATE SKIP LOCKED`, sets `locked_at`/`locked_by` and increments `attempts` in a short transaction, then runs the handler outside it. Two workers never get the same job. While the queue is empty only one loop polls; the others sleep until a job is enqueued in the same process (after commit), the scheduler or the outbox enqueues jobs, or another loop reserves a job, which wakes one more loop at a time.
- **Retries.** A failing job (error, panic, timeout or unknown kind) goes back to the queue with exponential backoff (`10 s · 2^(attempt-1)`, capped at 1 h, `RetryPolicy`) until `max_attempts`; then `failed_at` is set. `last_error` keeps the `AppError` message truncated to 2000 characters and never the payload, so do not put secrets in error messages.
- **Abandoned jobs.** Jobs locked for longer than the job timeout plus 60 s (worker killed) are released to run again, or failed when they have no attempts left.
- **Shutdown.** SIGTERM/CTRL+C stops picking new jobs and waits for the running ones (bounded by the job timeout).
- **Handlers.** Implement `JobHandler { fn kind(); async fn handle(&JobContext, Value) }` and register it from a module: `app.job(|env| Arc::new(MyHandler::new(env.pool.clone())))` in `Module::register` (the runtime is built with `WorkerRuntime::from_app`). Jobs of a kind without handler fail with `no job handler is registered for kind …`.
- **Schedules.** `ScheduledJobDefinition::new("kind", "0 0 3 * * *")` (cron with seconds, from the `cron` crate) registered with `app.schedule(...)`; on boot the runtime upserts one row per kind, keeping `next_run_at` when the expression did not change and never re-enabling a schedule disabled in the table. Each tick locks the due rows with `SKIP LOCKED`, enqueues them with `unique_key = scheduled:<kind>:<due time>` and moves `next_run_at` to the next fire time after now (missed runs are not replayed). Schedules of a disabled module only move `next_run_at`; nothing is enqueued until the module is enabled again.
- **Outbox dispatch.** The built-in job `outbox.dispatch` runs right after every committed transaction that published events (requested by the event publisher after commit, at most once per second per process, which also wakes the local worker) and every 30 s as a safety net (`*/30 * * * * *`). It locks up to 100 undispatched `domain_events` ordered by `occurred_at` with `SKIP LOCKED`, enqueues one `event.consume` job per event and accepting consumer (`unique_key = event:<event id>:<consumer>`), and marks `dispatched_at` in the same transaction. One run keeps dispatching batches while they come back full, for up to 20 s (`OUTBOX_DISPATCH_TIME_BUDGET`), and then enqueues a follow-up dispatch, so a bulk import does not delay other events by minutes. Each delivery is retried on its own, so a failing consumer neither blocks the outbox nor makes other consumers see the event twice. Delivery is at least once: consumers must be idempotent.
- **Cleanup.** The built-in job `jobs.cleanup` (hourly, `0 17 * * * *`) deletes jobs finished more than 7 days ago and failed more than 30 days ago.
- **Consumers.** Implement `EventConsumer { fn name(); fn accepts(event_type); async fn consume(&DomainEvent) }` with a stable unique `name` and register it with `app.consumer(|env| Arc::new(MyConsumer))`. The registered consumers are listed per module in the table below.
- **Stats.** `GET /api/v1/system/jobs/stats` (needs `system.manage`) returns pending (due), scheduled (future `run_at`), running and failed counts, overall and per queue, plus the oldest pending `run_at` and its age in seconds.
